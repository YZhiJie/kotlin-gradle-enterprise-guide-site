2.2 协程基础：挂起函数与构建器 ​

协程（coroutine）是轻量级线程：成千上万个协程可以复用少量线程。suspend 标记的函数可以「挂起」等待异步结果而不阻塞线程。

kotlin
// CoroutineBasics.kt —— 协程三种构建器
import kotlinx.coroutines.*

fun main() = runBlocking {                       // 桥接阻塞与挂起世界（仅 main/测试用）
    val job: Job = launch {                      // launch：启动「即发即忘」协程
        delay(100L)                              // 挂起 100ms，不阻塞线程
        println("launch 完成")
    }

    val deferred: Deferred<Int> = async {      // async：启动有返回值的协程
        delay(50L)
        42
    }

    println("async 结果 = ${deferred.await()}")  // await 挂起等待结果
    job.join()                                   // 等待 launch 完成
    println("当前线程: ${Thread.currentThread().name}")
}

// StructuredConcurrency.kt —— coroutineScope 与 supervisorScope
import kotlinx.coroutines.*

suspend fun loadDashboard(): String = coroutineScope {     // 任一子失败则全部取消
    val user = async { fetchUser() }
    val orders = async { fetchOrders() }
    "用户=${user.await()}, 订单数=${orders.await().size}"
}

suspend fun loadFeedSafe(): List<String> = supervisorScope { // 子失败互不影响
    val tasks = List(5) { i ->
        async {
            if (i == 2) throw RuntimeException("第 $i 个源失败")
            "内容$i"
        }
    }
    tasks.mapNotNull { runCatching { it.await() }.getOrNull() } // 降级：跳过失败源
}

suspend fun fetchUser(): String { delay(10); return "张三" }
suspend fun fetchOrders(): List<String> { delay(20); return listOf("A1", "A2") }

fun main() = runBlocking {
    println(loadDashboard())
    println(loadFeedSafe())
}

协程异常传播与 Job 状态机 ​

理解异常传播，先要理解 Job 的状态机。普通 launch/async 启动后进入 Active；只有 CoroutineStart.LAZY 才会先停留在 New，调用 start()/join() 后才转 Active：

    Completing --> Completed: 所有子协程完成

    Cancelling --> Cancelled: 子协程全部收尾完毕

    Cancelled --> [*]

launch 与 async 对异常的处理是两条完全不同的路径：

  • launch：异常在发生的瞬间立即沿 Job 树向上传播，父 Job 进入 Cancelling 并取消兄弟协程；根协程（或 SupervisorJob 的直接子级）可由 CoroutineExceptionHandler（CEH）兜底。
  • async：异常被封装进 Deferred，只有调用 await() 时才重新抛出；在 async 协程内安装 CEH 无效——它永远拿不到这个异常。
  • 普通 Job vs SupervisorJob：普通 Job 奉行「一损俱损」，任一子失败即取消整个父作用域；SupervisorJob/supervisorScope 切断向下传播，一个子失败不影响兄弟（参见 2.3 的聚合示例）。

kotlin
import kotlinx.coroutines.*

fun main(): Unit = runBlocking {            // 显式 Unit：保证编译器生成 main(String[]) 桥接
    val handler = CoroutineExceptionHandler { _, e ->
        println("CEH 兜底捕获: ${e.message}") // 只做日志上报与是否杀进程的决策
    }
    // SupervisorJob + handler：模拟 viewModelScope 的边界配置
    val scope = CoroutineScope(SupervisorJob() + Dispatchers.Default + handler)

    // ① launch：异常立即向上传播，由边界 CEH 捕获，无需 try-catch
    scope.launch {
        throw RuntimeException("launch 子协程炸了")
    }.join()                                     // join 不会重新抛出异常

    // ② async：异常被 Deferred 持有，await 才抛；async 内部装 CEH 也无效
    val deferred = scope.async {
        throw RuntimeException("async 子协程炸了")
    }
    runCatching { deferred.await() }              // ✅ 业务降级必须写在 await 处
        .onFailure { println("await 处业务降级: ${it.message}") }
}

取消与资源清理 ​

取消不是「立即杀线程」，而是协作式的：协程必须在挂起点（delay、emit、withContext 等）或显式调用 ensureActive() 时才会响应取消。纯 CPU 循环若不检查，会导致 job.cancel() 后任务仍在跑。

mermaid
flowchart LR
    A[调用 cancel()] --> B{协程处于挂起点?}
    B -- 是 --> C[抛 CancellationException，进入 finally]
    B -- 否 --> D[继续运行当前代码块]
    D --> E{下次挂起/ensureActive}
    E --> C
    C --> F{清理里有挂起调用?}
    F -- 是 --> G[withContext NonCancellable]
    F -- 否 --> H[直接释放资源]
    G --> I[协程结束 Cancelled]
    H --> I

// 文件: CancellationCleanupDemo.kt —— withTimeoutOrNull / NonCancellable / ensureActive / finally
// 配套章节：02-kotlin-advanced.md 2.3「取消与资源清理」、mastery-coroutines-deep-dive.md D2.4
// 依赖：kotlinx-coroutines-core 1.9.0
// 运行：见同目录 README.md

import kotlinx.coroutines.*

suspend fun fetchWithDeadline(): String? = withTimeoutOrNull(100) {
    delay(300)                                        // 超时后抛 TimeoutCancellationException 并被吞掉
    "远端结果"
}

/** 用 finally + NonCancellable 保证清理动作一定执行完（关闭连接、提交偏移量、flush 日志）。 */
suspend fun useResource(job: Job) {
    try {
        repeat(100) { i ->
            currentCoroutineContext().ensureActive()   // 协作式取消：在循环里主动检查，避免「不理取消」
            delay(10)
            if (i == 3) job.cancel()                  // 模拟外部取消
        }
    } finally {
        withContext(NonCancellable) {                 // 已取消的上下文里仍能执行挂起清理
            delay(50)                                 // 模拟关闭连接需要时间
            println("  finally：资源已释放（NonCancellable 保证完成）")
        }
    }
}

fun main(): Unit = runBlocking {
    println("① withTimeoutOrNull(100ms)：结果 = ${fetchWithDeadline()}（超时返回 null，不抛异常）")

    println("② 协作式取消 + finally 清理：")
    val job = launch { useResource(coroutineContext[Job]!!) }
    job.join()
    println("   job 状态 = ${job.isCancelled}（期望 true）")

    println("③ 对比：取消后直接做挂起清理会被立即中断")
    val badJob = launch {
        try {
            delay(1000)
        } finally {
            delay(50)                             // ❌ 已取消，这里会立刻抛 CancellationException
            println("  这行通常不会执行")
        }
    }
    delay(50)
    badJob.cancelAndJoin()
    println("   结论：清理动作里有挂起调用时，必须包在 withContext(NonCancellable) 里")
}

命名与调试 ​

协程出错时最痛苦的是「日志里全是 DefaultDispatcher-worker-3，不知道是哪个业务」。三个低成本手段：

  1. CoroutineName：给关键链路命名，调试模式下会拼进线程名，日志框架也能从上下文取出。
  2. 调试模式：JVM 参数 -Dkotlinx.coroutines.debug=on，线程名会变成 ... @拉取订单#3，协程创建栈也会保留。
  3. 协程 dump：引入 kotlinx-coroutines-debug（仅测试/排障环境），调用 DebugProbes.dumpCoroutines() 打印整棵 Job 树；生产环境用线程 dump（jstack）观察阻塞点。

2.4 Channel 与 Flow 家族 ​

Channel 是协程间的通信管道（类似阻塞队列的挂起版）；Flow 是声明式的冷数据流，StateFlow/SharedFlow 是热流。

kotlin
// FlowDemo.kt —— Flow 构建、操作符与异常处理
import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

fun tickerFlow(): Flow<Int> = flow {             // flow{} 构建冷流
    var count = 0
    while (true) {
        emit(count++)                              // emit 挂起式发射
        delay(50)
        if (count == 3) throw RuntimeException("模拟下游故障")
    }
}

fun main() = runBlocking {
    tickerFlow()
        .map { it * 10 }                           // 变换
        .filter { it % 20 == 0 }                   // 过滤
        .onEach { println("收到: $it") }
        .catch { e -> println("捕获异常: ${e.message}") }  // catch 捕获上游异常
        .flowOn(Dispatchers.Default)               // 上游切到计算线程池
        .collect()                                 // 冷流只有被 collect 才开始发射

    // StateFlow：永远持有最新值，适合 UI 状态
    val state = MutableStateFlow("加载中")
    state.value = "就绪"
    println("StateFlow 当前值: ${state.value}")

    // SharedFlow：可配置重放（replay）的事件总线，适合一次性事件
    val events = MutableSharedFlow<String>(replay = 0)
    launch {
        delay(10)
        events.emit("下单成功")
    }
    println("SharedFlow 事件: ${events.first()}")
}

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

// 上游：每 20ms 产出一个编号；下游故意慢（每个处理 80ms）
private fun source(): Flow<Int> = flow {
    repeat(4) { i ->
        println("  上游发射 $i")
        emit(i)
        delay(20)
    }
}

private suspend fun slowCollect(name: String, flow: Flow<Int>) {
    println("【$name】")
    val start = System.currentTimeMillis()
    val received = mutableListOf<Int>()
    flow.collect { i ->
        delay(80)                       // 模拟下游慢处理
        received += i
        println("  下游处理完 $i")
    }
    println("  收到=$received，耗时=${System.currentTimeMillis() - start}ms\n")
}

@OptIn(FlowPreview::class)
fun main(): Unit = runBlocking {
    // ① 默认 collect：上下游串行，上游必须等下游处理完才能继续发射
    slowCollect("默认 collect（无缓冲）", source())

    // ② buffer：上下游流水线化，上游不必等下游；下游仍然一个不落地处理全部元素
    slowCollect("buffer(64)", source().buffer(64))

    // ③ conflate：缓冲只保留「最新一个」，中间值被丢弃（适合只要最新状态的场景）
    slowCollect("conflate", source().conflate())

    // ④ collectLatest：新值到来时取消上一次尚未完成的收集（适合搜索框、UI 刷新）
    println("【collectLatest】")
    val seen = mutableListOf<Int>()
    source().collectLatest { i ->
        seen += i
        delay(80)                       // 被下一个值打断时，这里不会打印「处理完」
        println("  下游处理完 $i（未被取消）")
    }
    println("  触发过的值=$seen（后面的被取消，只有最后一个能完成）\n")

    // ⑤ sample：按固定采样间隔取值，间隔内的元素直接丢弃（适合监控指标上报）
    println("【sample(50ms)】")
    source().sample(50).collect { println("  采样到 $it") }
}

// 配套章节：02-kotlin-advanced.md 2.4「并发度与限流」、mastery-coroutines-deep-dive.md D2.3
// 依赖：kotlinx-coroutines-core 1.9.0

import kotlinx.coroutines.*
import kotlinx.coroutines.sync.*
import java.util.concurrent.atomic.AtomicInteger
import kotlin.system.measureTimeMillis

@OptIn(ExperimentalCoroutinesApi::class)
fun main(): Unit = runBlocking(Dispatchers.Default) {
    // ① Mutex：互斥访问共享可变状态。注意 Mutex 是「挂起锁」，不会阻塞线程
    var counter = 0
    val mutex = Mutex()
    coroutineScope {
        repeat(100) {
            launch {
                mutex.withLock {
                    counter++                     // 临界区：同一时刻只有一个协程进入
                }
            }
        }
    }
    println("① Mutex 保护后的计数 = $counter（期望 100）")

    // ② Semaphore：限制同时进行的数量，适合「最多 N 个并发请求」的闸门
    val semaphore = Semaphore(permits = 3)
    val running = AtomicInteger()
    val peak = AtomicInteger()
    val elapsed = measureTimeMillis {
        coroutineScope {
            repeat(12) {
                launch {
                    semaphore.withPermit {
                        val now = running.incrementAndGet()
                        peak.updateAndGet { p -> maxOf(p, now) }
                        delay(60)                 // 模拟一次外部调用
                        running.decrementAndGet()
                    }
                }
            }
        }
    }
    println("② Semaphore(3)：峰值并发 = ${peak.get()}（期望 ≤ 3），耗时 = ${elapsed}ms")

    // ③ limitedParallelism：限制「真正占线程的并行度」，适合 CPU 密集型分段
    //    注意：它限制的是同时运行的线程数，不是「在途协程数」——delay 挂起的协程不占线程
    val cpuDispatcher = Dispatchers.Default.limitedParallelism(2)
    val cpuRunning = AtomicInteger()
    val cpuPeak = AtomicInteger()
    coroutineScope {
        repeat(8) {
            launch(cpuDispatcher) {
                val now = cpuRunning.incrementAndGet()
                cpuPeak.updateAndGet { p -> maxOf(p, now) }
                val deadline = System.nanoTime() + 30_000_000
                while (System.nanoTime() < deadline) {   // 忙等 30ms，真实占住线程
                    // 模拟 CPU 工作
                }
                cpuRunning.decrementAndGet()
            }
        }
    }
    println("③ limitedParallelism(2)：峰值并行数 = ${cpuPeak.get()}（期望 ≤ 2）")

    // ④ 选型提示：Mutex 保护「状态」，Semaphore 限制「同时进行的任务数」（含挂起中的任务），
    //    limitedParallelism 划出「专属线程并发度」；三者语义不同，不要互相替代。
}

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.awaitClose
import kotlinx.coroutines.flow.*

/** 一个典型的老式回调 API：注册监听、返回取消句柄。 */
private class LegacyTimer {
    private var listener: ((Int) -> Unit)? = null

    fun start(onTick: (Int) -> Unit) {
        listener = onTick
    }

    fun stop() {
        listener = null
    }

    fun tick(value: Int) {
        listener?.invoke(value)
    }
}

/** callbackFlow：把「注册/反注册」型回调变成冷流；awaitClose 保证收集结束一定反注册。 */
private fun timerFlow(timer: LegacyTimer): Flow<Int> = callbackFlow {
    val callback: (Int) -> Unit = { value -> trySend(value) }  // 回调里只能用 trySend / trySendBlocking
    timer.start(callback)
    awaitClose { timer.stop() }                       // 收集者取消或结束时执行清理
}

/** channelFlow：需要并发 emit（多个子协程同时产出）时用它，emit 线程安全。 */
private fun mergedFlow(): Flow<String> = channelFlow {
    launch { send("来自协程 A") }
    launch { send("来自协程 B") }
}

fun main(): Unit = runBlocking {
    val timer = LegacyTimer()

    // 模拟外部驱动：另一个协程给 timer 打点（真实场景是传感器/消息队列回调）
    val tickerJob = launch(Dispatchers.Default) {
        repeat(5) { i ->
            delay(20)
            timer.tick(i)
        }
    }

    // ① callbackFlow：收集 3 个事件后主动结束，awaitClose 会把监听反注册
    val ticks = timerFlow(timer).take(3).toList()
    println("① callbackFlow 收到 3 个事件：$ticks")
    tickerJob.join()

    // ② channelFlow：多个生产者并发发送，顺序不保证但不会丢
    val merged = mergedFlow().toList()
    println("② channelFlow 合并结果：$merged")

    // ③ 关键区别：
    //    callbackFlow 用于「适配回调」，awaitClose 是资源释放的生命线；
    //    channelFlow 用于「构建期并发发送」，内部自带缓冲区与结构化并发。
}

// 运行：见同目录 README.md

import kotlinx.coroutines.*
import java.util.concurrent.CompletableFuture
import kotlin.coroutines.resume
import kotlin.coroutines.resumeWithException

/** CompletableFuture → suspend：挂起点等 Java 异步结果，取消时同步取消底层任务。 */
suspend fun <T> CompletableFuture<T>.awaitResult(): T = suspendCancellableCoroutine { cont ->
    whenComplete { value, error ->
        if (error == null) cont.resume(value) else cont.resumeWithException(error)
    }
    cont.invokeOnCancellation { cancel(true) }       // 协程被取消 → 底层任务也取消
}

/** suspend → CompletableFuture：把协程结果交给只认 CF 的老代码（如 Servlet 异步、第三方 SDK）。 */
fun <T> CoroutineScope.futureOf(block: suspend CoroutineScope.() -> T): CompletableFuture<T> {
    val result = CompletableFuture<T>()
    launch {
        try {
            result.complete(block())
        } catch (t: Throwable) {
            result.completeExceptionally(t)
        }
    }
    return result
}

// 模拟一个还在用 CompletableFuture 的老 SDK
private fun legacyLookup(id: String): CompletableFuture<String> =
    CompletableFuture.supplyAsync {
        Thread.sleep(80)                            // 阻塞式实现，发生在 ForkJoinPool 线程
        "用户-$id"
    }

private suspend fun loadUser(id: String): String {
    val name = legacyLookup(id).awaitResult()       // 挂起等待，业务代码保持顺序可读
    return "$name（由 ${Thread.currentThread().name} 恢复）"
}

fun main(): Unit = runBlocking {
    // ① CompletableFuture → suspend
    println("① awaitResult：${loadUser("1001")}")

    // ② suspend → CompletableFuture，再挂起等它完成（非协程线程则可用 get()/thenApply）
    val cf = futureOf { loadUser("1002") }
    println("② futureOf + awaitResult：${cf.awaitResult()}")

    // ③ 异常也要能跨边界传递
    val failed = CompletableFuture<String>().apply {
        completeExceptionally(IllegalArgumentException("下游 404"))
    }
    try {
        failed.awaitResult()
    } catch (e: Exception) {
        println("③ 异常透传：${e.message}")
    }

    // ④ 线程提醒：suspend 恢复线程由 CF 的完成线程决定，跨线程访问 UI/ThreadLocal 时必须 withContext
    println("   main 结尾线程：${Thread.currentThread().name}")
}

2.5 泛型与型变 ​

型变（variance）解决「List<String> 能否赋给 List<Any>」的问题。Kotlin 使用声明处型变：在类声明处标注，使用处免标注。

kotlin
// Variance.kt —— out / in / 星投影
interface Producer<out T> {                  // out：只产出 T，可协变
    fun produce(): T
}

interface Consumer<in T> {                   // in：只消费 T，可逆变
    fun consume(item: T)
}

class StringProducer : Producer<String> {
    override fun produce() = "订单数据"
}

class AnyConsumer : Consumer<Any> {
    override fun consume(item: Any) = println("消费: $item")
}

fun printAll(items: List<*>) {               // 星投影：未知类型的只读视图
    items.forEach { println(it) }
}

fun main() {
    val p: Producer<Any> = StringProducer()  // 协变：String 生产者可当 Any 生产者
    val c: Consumer<String> = AnyConsumer()  // 逆变：Any 消费者可当 String 消费者
    c.consume(p.produce())
    printAll(listOf(1, "two", 3.0))
}

2.6 委托 ​

委托（delegation）把属性或接口的实现交给另一个对象，是「组合优于继承」的语法级支持。

kotlin
// Delegates.kt —— 标准委托与自定义委托
import kotlin.properties.Delegates
import kotlin.properties.ReadWriteProperty
import kotlin.reflect.KProperty

// 自定义委托：带审计日志的属性
class Audited<T>(private var value: T) : ReadWriteProperty<Any?, T> {
    override fun getValue(thisRef: Any?, property: KProperty<*>) = value
    override fun setValue(thisRef: Any?, property: KProperty<*>, newValue: T) {
        println("审计: ${property.name} 由 $value 改为 $newValue")   // 关键行：写入拦截
        value = newValue
    }
}

class FeatureFlags {
    val darkMode: Boolean by lazy {                        // 首次访问才计算，默认线程安全

        true

        println("maxRetry: $old -> $new")
    }
    var region: String by Audited("cn-north")              // 使用自定义委托
}

fun main() {
    val flags = FeatureFlags()
    println(flags.darkMode)                                // 触发 lazy 初始化
    println(flags.darkMode)                                // 直接命中缓存

    flags.region = "cn-south"
}

2.7 内联函数与 reified ​

inline 让编译器把函数体与 lambda 直接展开到调用处，消除匿名类开销；reified（具体化）让泛型类型在运行时可用：

kotlin
// InlineReified.kt —— inline 与 reified
inline fun <reified T> Any?.safeCast(): T? = this as? T   // reified 后可写 as? T

inline fun measure(name: String, block: () -> Unit) {     // 内联后无 lambda 对象分配
    val start = System.nanoTime()
    block()
    println("$name 耗时 ${(System.nanoTime() - start) / 1000}us")
}

    val value: Any = "hello"
    val str: String? = value.safeCast()                   // 无需传 Class 参数
    val num: Int? = value.safeCast()                      // null，类型不匹配
    println("str=$str num=$num")

    measure("百万次累加") {
        var sum = 0L
        repeat(1_000_000) { sum += it }
    }

2.9 DSL 构建 ​

带接收者的 lambda（lambda with receiver）是 Kotlin DSL 的核心，Gradle Kotlin DSL、Ktor 路由、Compose UI 均由此而来：

kotlin
// DslDemo.kt —— 自研类型安全 HTML DSL
@DslMarker
annotation class HtmlDsl                                 // 限制隐式接收者，防止嵌套污染

@HtmlDsl
class Tag(val name: String, private val text: String? = null) {
    private val children = mutableListOf<Tag>()
    operator fun Tag.unaryPlus() { this@Tag.children += this }  // +tag 添加子节点（显式分发接收者，避免 @DslMarker 下误挂到自身）
    fun render(): String {
        val body = text ?: children.joinToString("") { it.render() }
        return "<$name>$body</$name>"                    // text 非空时为叶子文本节点
    }
}

fun Tag.div(block: Tag.() -> Unit) { +Tag("div").apply(block) }
fun Tag.span(text: String) { +Tag("span", text) }        // ✅ 文本作为文本节点原样输出，而非当作标签名
fun html(block: Tag.() -> Unit): String = Tag("html").apply(block).render()

fun main() {
    val page = html {
        div {
            span("Kotlin DSL")                             // 嵌套结构即代码结构
            div { span("类型安全") }
        }
    }
    println(page)
}

企业级场景分析 ​

场景一：高并发网关的协程治理 ​

某电商网关峰值 5 万 QPS，从线程池模型迁移到 Kotlin 协程后，单机线程数从 800 降到 24（CPU 核数×2），但上线初期出现两类典型事故：

  1. 协程泄漏：早期代码在 GlobalScope 中发起「日志上报」协程，服务滚动发布时累积数十万个悬挂协程，堆外内存持续上涨。整改：全部改为注入与请求生命周期绑定的作用域，并用 supervisorScope 隔离旁路任务。
  2. 阻塞污染 IO 调度器：某 SDK 内部是阻塞 JDBC 调用，直接运行在 Dispatchers.IO 默认 64 线程上限上，高峰期线程耗尽导致全站超时。整改：为遗留阻塞调用单独创建 Executors.newFixedThreadPool(200).asCoroutineDispatcher() 的隔离调度器，并配合 Micrometer 监控队列深度。

经验：协程只解决「等待」的成本，不解决「隔离」的问题——隔离仍需显式调度器与舱壁（bulkhead）设计（Resilience4j 见第 4 章）。

场景二：大型 Android 团队的 Flow 状态治理 ​

30 人 Android 团队曾混用 LiveData、RxJava、Callback 三套异步范式，内存泄漏与状态不一致频发。统一迁移到 StateFlow（页面状态）+ SharedFlow（一次性事件，如 Toast/导航）后：

  • 用 WhileSubscribed(5000) 控制上游共享，避免旋转屏幕时重复请求；
  • 用 stateIn/shareIn 将冷流转热流，配合第 7 章的 Turbine 做状态断言测试；
  • 通过 detekt 自定义规则禁止在 UI 层直接 collect（必须 repeatOnLifecycle，见第 5 章）。

实践任务 ​

  1. ★ 用 async/await 并发调用两个模拟接口（各 delay 随机 50~200ms），打印总耗时，验证并发快于串行。
  2. ★★ 用 supervisorScope + mapNotNull 实现「10 个数据源任意失败不拖垮整体」的聚合函数，要求返回成功结果与失败原因列表。
  3. ★★ 设计 interface Repository<out T> 与 interface Cache<in T>，写一个既能把 StringRepository 赋给 Repository<Any>、又能把 AnyCache 用作 Cache<String> 的示例。
  4. ★★★ 编写自定义委托 PreferenceDelegate，把属性读写映射到 Map<String, Any?>（模拟 SharedPreferences），支持 by PreferenceDelegate("key", default) 语法。
  5. ★★★ 扩展 2.9 的 DSL：支持属性（div("class" to "container") 形式）与 @DslMarker 隔离，并用 reified 写一个 flow 泛型节点工厂。

小结与自测 ​

要点回顾：挂起 ≠ 阻塞；结构化并发靠 coroutineScope 保证无泄漏；StateFlow 管状态、SharedFlow 管事件；型变口诀「生产者 out、消费者 in」；inline+reified 保留泛型；KSP 替代反射与 KAPT；DSL = 带接收者 lambda + @DslMarker。

自测题：

  1. coroutineScope 与 supervisorScope 在子协程失败时的行为差异是什么？
  2. 为什么 StateFlow 适合 UI 状态而 SharedFlow(replay=0) 适合 Toast 事件？
  3. List<*> 与 List<Any?> 有何区别？
  4. by lazy 的三种线程安全模式分别适用于什么场景？
  5. KSP 相比 KAPT 的两个核心优势是什么？
参考答案（点击展开）
  1. coroutineScope 中任一子失败会取消全部兄弟协程并向上抛；supervisorScope 中子失败相互独立，需各自处理。
  2. StateFlow 总是有当前值且新订阅者立即收到最新状态，适合表示「此刻界面长什么样」；Toast 是一次性消费事件，重放会导致旋转屏幕后重复弹出，故用 replay=0。
  3. List<*> 是「某种未知具体类型」的只读投影，不能写入；List<Any?> 元素类型明确为 Any?，可写入任意对象。
  4. SYNCHRONIZED（默认，多线程安全）、PUBLICATION（允许多次计算但只发布一个，无锁读）、NONE（单线程，零开销）。
  5. 速度更快（无需生成 Java stub，构建提速 2 倍以上）；原生理解 Kotlin 语法（可处理 Kotlin 特有的挂起函数、值类等符号）。
