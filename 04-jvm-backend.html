第 4 章 JVM 后端企业级开发 ​

本章以 Spring Boot 3 + Kotlin 为主线、Ktor 为补充，覆盖从 Web 层、数据层到微服务治理与可观测性的完整后端技术栈。

4.0 学习目标 ​

完成本章后，你将能够：

  1. 搭建 Spring Boot 3 + Kotlin 工程，使用构造器注入与协程式 WebFlux 端点。
  2. 基于 R2DBC（或 Data JPA）实现响应式数据访问，并用 Exposed 完成轻量 ORM 映射。
  3. 使用 Ktor 快速构建轻量 HTTP 服务，理解其与 Spring 的取舍。
  4. 落地配置管理、服务发现、gRPC 通信与 Resilience4j 容错。
  5. 建立结构化日志与 Micrometer 指标追踪的可观测性体系。

依赖注入与分层 ​

kotlin
// OrderService.kt —— 构造器注入（推荐）
package com.shop.order

import org.springframework.stereotype.Service
import org.springframework.web.bind.annotation.*

data class Order(val id: Long, val item: String, val amount: Long)

@Service
class OrderService(
    private val repository: OrderRepository        // val + 构造器注入：不可变、易测试
) {
    suspend fun findById(id: Long): Order {
        validate(id)                                     // 入口先做参数校验（快速失败）
        return repository.findById(id) ?: throw NoSuchElementException("订单 $id 不存在")
    }

    fun validate(id: Long) {
        require(id > 0) { "订单 id 必须为正数: $id" }     // 非 suspend：非法参数直接拒绝，不访问仓库
    }
}

@RestController
@RequestMapping("/orders")
class OrderController(private val service: OrderService) {

    @GetMapping("/{id}")
    suspend fun get(@PathVariable id: Long): Order = service.findById(id)  // suspend 端点
}

// OrderRepository.kt —— 协程式 Repository
package com.shop.order

import org.springframework.data.repository.kotlin.CoroutineCrudRepository
import kotlinx.coroutines.flow.Flow

// ✅ 协程 Repository 直接继承 CoroutineCrudRepository（不要继承 ReactiveCrudRepository 再手写 suspend 方法）
interface OrderRepository : CoroutineCrudRepository<OrderEntity, Long> {
    // findById 已由父接口提供：suspend fun findById(id: Long): OrderEntity?（返回可空，未命中即 null）
    fun findByItem(item: String): Flow<OrderEntity>     // 派生查询：多值结果自动映射为 Flow
}

4.3 Exposed ORM ​

Exposed 是 JetBrains 官方轻量 ORM，提供类型安全 SQL DSL，适合不想引入完整 JPA 的场景：

kotlin
// ExposedDemo.kt —— DSL 风格表定义与查询
import org.jetbrains.exposed.sql.*
import org.jetbrains.exposed.sql.transactions.transaction

object Orders : Table("orders") {                    // 表即 object
    val id = long("id").autoIncrement()
    val item = varchar("item", 64)
    val amount = long("amount")
    override val primaryKey = PrimaryKey(id)
}

fun main() {
    Database.connect("jdbc:h2:mem:shop", driver = "org.h2.Driver")

    transaction {                                    // 事务块
        SchemaUtils.create(Orders)                   // 建表
        Orders.insert {
            it[item] = "机械键盘"
            it[amount] = 39900
        }
        val total = Orders
            .select(Orders.amount.sum())
            .where { Orders.amount greater 10000 }   // 类型安全条件
            .single()[Orders.amount.sum()]
        println("万元订单总额: $total 分")
    }
}

4.4 Ktor 服务端 ​

Ktor 适合轻量服务、BFF、内部工具：启动毫秒级、协程原生、路由即 DSL。

kotlin
// KtorServer.kt —— 一个完整可运行的 Ktor 服务
import io.ktor.server.application.*
import io.ktor.server.engine.*
import io.ktor.server.netty.*
import io.ktor.server.plugins.contentnegotiation.*
import io.ktor.serialization.kotlinx.json.*
import io.ktor.server.response.*
import io.ktor.server.routing.*
import kotlinx.serialization.Serializable

@Serializable
data class Health(val status: String, val uptime: Long)

fun main() {
    val startedAt = System.currentTimeMillis()
    embeddedServer(Netty, port = 8080) {             // Netty 引擎内嵌启动
        install(ContentNegotiation) { json() }       // kotlinx.serialization 序列化
        routing {
            get("/health") {
                call.respond(Health("UP", System.currentTimeMillis() - startedAt))
            }
            route("/api/orders") {
                get("/{id}") {
                    val id = call.parameters["id"]?.toLongOrNull()
                        ?: return@get call.respondText("非法 id", status = io.ktor.http.HttpStatusCode.BadRequest)
                    call.respond(mapOf("id" to id, "item" to "demo"))
                }
            }
        }
    }.start(wait = true)
}

Resilience4j 容错 ​

kotlin
// ResilientCaller.kt —— 熔断 + 重试 + 超时组合
package com.shop.resilience

import io.github.resilience4j.circuitbreaker.CircuitBreaker
import io.github.resilience4j.kotlin.circuitbreaker.executeSuspendFunction
import io.github.resilience4j.kotlin.retry.executeSuspendFunction
import io.github.resilience4j.retry.Retry
import kotlinx.coroutines.withTimeout

class InventoryGateway(
    private val client: InventoryClient,
    breaker: CircuitBreaker,
    retry: Retry
) {
    suspend fun deduct(sku: String, count: Int): Boolean =
        breaker.executeSuspendFunction {                 // 熔断：失败率超阈值直接拒绝
            retry.executeSuspendFunction {               // 重试：瞬时故障自动恢复
                withTimeout(1500) {                      // 超时：防止线程被拖死
                    client.deduct(sku, count)
                }
            }
        }
}

4.7 日志与可观测性 ​

kotlin
// Logging.kt —— 结构化日志与指标
package com.shop.observability

import io.micrometer.core.instrument.MeterRegistry
import io.micrometer.core.instrument.Timer
import org.slf4j.LoggerFactory
import org.springframework.stereotype.Service

@Service
class CheckoutService(registry: MeterRegistry) {
    private val log = LoggerFactory.getLogger(javaClass)  // SLF4J 门面 + Logback 实现
    private val checkoutTimer: Timer = registry.timer("shop.checkout.duration")

    suspend fun checkout(orderId: Long): Boolean {
        log.info("checkout start orderId={}", orderId)    // 占位符，避免字符串拼接
        return checkoutTimer.recordCallable {
            // ... 业务逻辑
            log.info("checkout done orderId={}", orderId)
            true
        } ?: false
    }
}

企业级场景分析 ​

场景一：秒杀下单链路的响应式改造 ​

某电商「下单链路」原 Spring MVC + JPA，大促 2 万 QPS 时 Tomcat 线程池打满、RT 飙到 2s。改造路径：

  1. Web 层 MVC → WebFlux + suspend 端点；数据层 JPA → R2DBC（PostgreSQL），库存扣减走 Redis Lua（原子性）。
  2. 遗留的阻塞风控 SDK 用 Dispatchers.IO 隔离池调用，并对该池做 Micrometer 监控（活跃线程、队列深度）。
  3. 结果：单机支撑 QPS 提升 6 倍，P99 从 2s 降到 180ms；代价是团队需要适应「全链路非阻塞」纪律——任何一处 .block() 都会让收益归零，因此 CI 加入 detekt 规则禁止生产代码出现 runBlocking（第 7、9 章）。

场景二：BFF 层选 Ktor 的边界 ​

某公司 App 首页聚合 12 个下游接口，用 Ktor 做 BFF：supervisorScope + async 并发聚合，单接口失败降级为占位数据，首页 P99 控制在 300ms。但当团队需要从 BFF 直接访问 MySQL、接入 Spring Security OAuth2 时，Ktor 生态成本急剧上升，最终该服务迁移回 Spring Boot。结论：Ktor 的甜区是「无状态、聚合、协议转换」；涉及复杂事务与安全体系时选 Spring。

场景三：金融级配置与审计 ​

金融类服务要求配置变更可审计：所有 application-*.yml 走 Git + CODEOWNERS（第 9 章），配置中心（Nacos）开启变更审批与版本回滚；密钥全部经 KMS 解密后注入，日志中对密钥字段做脱敏（Logback PatternLayout 自定义 converter）。一次误把数据库密码提交到 Git 的事故后，团队在 CI 加入 gitleaks 扫描（第 8 章）。

实践任务 ​

  1. ★ 用 start.spring.io 生成 Kotlin + WebFlux 工程，写一个 suspend 端点 /echo 原样返回请求体，用 curl 验证。
  2. ★★ 用 Exposed 实现「用户-订单」两张表，完成「查询某用户金额 Top3 订单」的 DSL 查询，并用 H2 内存库跑通 main 函数。
  3. ★★ 用 Ktor 实现一个聚合接口 /dashboard：supervisorScope 内并发请求两个 delay 模拟的下游，任一失败降级为 "N/A"，返回聚合 JSON。
  4. ★★★ 为任务 1 的服务接入 Resilience4j：对下游调用配置 50% 失败率熔断、2 次重试、1s 超时，写集成测试验证熔断打开后快速失败。
  5. ★★★ 接入 Actuator + Micrometer：自定义 shop.order.created 计数器与下单耗时直方图，访问 /actuator/prometheus 截图（或保存输出）确认指标存在。

小结与自测 ​

要点回顾：Kotlin + Spring 必配 plugin.spring；WebFlux 协程端点全链路非阻塞；Exposed 适合轻量场景；Ktor 甜区在 BFF/聚合；容错三件套缺一不可；可观测性 = 日志 + 指标 + 追踪。

自测题：

  1. 为什么 Kotlin 写 Spring 必须加 kotlin("plugin.spring") 插件？
  2. WebFlux 协程服务中调用阻塞 JDBC 的正确做法是什么？
  3. implementation("kotlinx-coroutines-reactor") 解决了什么问题？
  4. 熔断器与重试同时使用时的合理顺序是什么？为什么？
  5. 什么时候应该选 Ktor 而不是 Spring Boot？
参考答案（点击展开）
  1. Kotlin 类默认 final，Spring 的 CGLIB 代理（@Transactional/@Async 等）需要 open 类，该插件自动为被 Spring 注解的类打开。
  2. 用 withContext(Dispatchers.IO)（或专用隔离调度器）包裹，避免阻塞事件循环线程。
  3. 让 Reactor 的 Mono/Flux 与协程/Flow 互操作，使 suspend 端点能接入 WebFlux 响应式链。
  4. 外层熔断、内层重试（熔断包裹重试）：重试引起的连续失败会被熔断统计并及时切断；反过来则重试会穿透熔断。
  5. 服务轻量、以聚合/协议转换为主、团队愿意自组装生态时；需要成熟数据/安全/云生态时选 Spring。
