第 6 章 性能优化与安全 ​

性能决定体验下限，安全决定生死红线。本章横跨 JVM 服务端与 Android 两端，给出可落地的调优手段与防护清单。

上一章：第 5 章 Android 企业级开发 ｜ 下一章：第 7 章 测试策略与质量保障

6.0 学习目标 ​

完成本章后，你将能够：

  1. 解释 JVM 内存模型，针对服务特征选择 G1/ZGC 并用 JFR 定位性能瓶颈。
  2. 完成 Android 启动优化、用 LeakCanary 排查内存泄漏、执行包体积瘦身。
  3. 编写 ProGuard/R8 keep 规则，平衡混淆强度与功能正确性。
  4. 使用 Android Keystore 管理密钥并实现加解密。
  5. 落地 HTTPS、证书固定（Certificate Pinning），并对照 OWASP Mobile Top 10 逐项防护。

# gc-tuning.sh —— 两组典型 JVM 参数（二选一）
# 方案 A：G1，8G 堆，通用微服务（JDK 17 默认）
java -Xms8g -Xmx8g \

     -jar app.jar

# 方案 B：ZGC，16G+ 堆，延迟敏感交易服务（JDK 21）

     -XX:+UseZGC -XX:+ZGenerational \
     -jar app.jar

调优顺序（⚠️ 切忌上来就改参数）：

  1. 先量化：JFR 录制 + GC 日志确认「真的是 GC 问题」而非锁竞争/下游慢。
  2. 再选器：堆 <16G 且 P99 要求 100ms 级 → G1 足够；堆 ≥16G 或要求 <10ms → ZGC（JDK 21 分代 ZGC 吞吐损失已很小）。
  3. 后调参：只动 -Xmx、MaxGCPauseMillis 等少数参数，每改一项压测一轮。

Baseline Profile 与 Macrobenchmark ​

原理：未优化的 App 首次执行代码走「解释执行 → JIT 热点编译」，冷启动与首屏滚动因此偏慢。Baseline Profile 是一份「类/方法白名单」，ART 在应用安装（或 Play 商店下发）时据此把关键路径直接 AOT 预编译，首启即享本地代码性能，冷启动与核心列表滚动普遍提速 20%~40%。配套的 Macrobenchmark 负责生成 Profile 并做性能回归度量，形成闭环：

R8 full mode ​

AGP 8 起 R8 默认运行在 full mode（AGP 7 及以前为 compat mode），两者关键差异：

  • compat mode：保留一组隐式默认 keep 兜底，尽量模拟 ProGuard 的保守行为，许多反射调用「碰巧」能活下来。
  • full mode：没有默认兜底，R8 只依据显式 keep 规则与代码可达性裁剪，优化（内联、类合并、参数移除）更激进，包更小、启动更快。
  • 受冲击最大的三类用法：反射（Gson 反射版、Class.forName）、JNI 回调、序列化框架按字段名读写——升级 AGP 8 后线上「debug 正常、release 崩溃」基本都源于此。可用 android.enableR8.fullMode=false 临时回退，但只应作为排查手段。
text
# 文件: proguard-rules.pro —— full mode 企业模板增补片段（叠加在 6.4 基础模板之上）
# 1. 保留泛型签名：Gson TypeToken、Moshi Types.newParameterizedType 反射必需
-keepattributes Signature
# 2. 保留内部类/闭包信息：匿名内部类、伴生对象反射不丢指向
-keepattributes InnerClasses,EnclosingMethod
# 3. 保留注解、异常表、行号（mapping 还原可读堆栈）
-keepattributes RuntimeVisibleAnnotations,*Annotation*,Exceptions,SourceFile,LineNumberTable

# 4. @Keep 精确标注：给确实被反射使用的类/成员打点，优于粗暴的整包 -keep
-keep @androidx.annotation.Keep class * { *; }
-keepclassmembers class * {
    @androidx.annotation.Keep *;
}

# 5. 泛型 Type Token 子类（Response<Page<Order>> 这类嵌套泛型解析）
-keep class * extends com.google.gson.reflect.TypeToken
-keep class com.google.gson.reflect.TypeToken { *; }

6.5 加解密与密钥管理 ​

密钥管理的铁律：密钥不落代码、不落配置文件、不落 Git。Android 用 Keystore，服务端用 KMS/Vault。

kotlin
// KeystoreCrypto.kt —— Keystore 内生成密钥并加密
package com.shop.security

import android.security.keystore.KeyGenParameterSpec
import android.security.keystore.KeyProperties
import java.security.KeyStore
import javax.crypto.Cipher
import javax.crypto.KeyGenerator
import javax.crypto.SecretKey
import javax.crypto.spec.GCMParameterSpec

object KeystoreCrypto {
    private const val ALIAS = "shop_token_key"

    private fun getOrCreateKey(): SecretKey {
        val ks = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
        (ks.getEntry(ALIAS, null) as? KeyStore.SecretKeyEntry)?.let { return it.secretKey }
        val spec = KeyGenParameterSpec.Builder(
            ALIAS, KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT
        )
            .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
            .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
            .setUserAuthenticationRequired(false)         // 金融场景可要求生物识别
            .build()
        return KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
            .apply { init(spec) }.generateKey()           // 密钥只存在于 TEE/SE，导不出来
    }

    fun encrypt(plain: ByteArray): Pair<ByteArray, ByteArray> {
        val cipher = Cipher.getInstance("AES/GCM/NoPadding")
        cipher.init(Cipher.ENCRYPT_MODE, getOrCreateKey())
        return cipher.doFinal(plain) to cipher.iv         // (密文, IV) 分开存储
    }

    fun decrypt(cipherText: ByteArray, iv: ByteArray): ByteArray {
        val cipher = Cipher.getInstance("AES/GCM/NoPadding")
        cipher.init(Cipher.DECRYPT_MODE, getOrCreateKey(), GCMParameterSpec(128, iv))
        return cipher.doFinal(cipherText)
    }
}

企业级场景分析 ​

场景一：金融类 App 合规整改 ​

某银行 App 接受监管渗透测试后收到 23 项整改，典型项：日志打印身份证后 6 位（M10）、抓包可改转账金额（M3）、Root 设备可运行（M7）。整改组合：release 构建用 R8 移除 Log.d/v（-assumenosideeffects）、全链路证书固定 + 请求签名（HMAC-SHA256 防篡改）、接入 SafetyNet/Play Integrity 并做服务端校验而非仅本地判断（本地检测可被 hook）。经验：所有「客户端校验」都必须假设可被绕过，最终校验在服务端。

场景二：交易撮合服务的 ZGC 迁移 ​

某券商撮合服务（堆 32G）用 G1 时 Full GC 偶发 800ms 停顿，盘中触发风控告警。迁移 JDK 21 分代 ZGC 后停顿稳定在 0.5ms 内，吞吐损失约 5%，通过扩容 1 个实例对冲。经验：延迟敏感服务先评估 ZGC/Shenandoah；调参救不了大堆 G1 的 Full GC，换收集器才是正解。

场景三：LeakCanary 治理专项 ​

某 App 用户画像显示低端机 OOM 率 0.8%。团队发起「泄漏清零」专项：CI 上跑 Monkey + LeakCanary（leakcanary-android-instrumentation），泄漏即失败；两周修复 41 处（Top3：静态 View 引用、未注销的广播、匿名内部类 Handler），OOM 率降至 0.15%，商店评分 +0.2。

实践任务 ​

  1. ★ 给一个 Spring Boot 服务加 G1 GC 日志参数，压测 1 分钟后用日志分析工具（或肉眼）统计 Young GC 次数与平均停顿。
  2. ★★ 在 Android demo 中故意制造一个单例持有 Activity 的泄漏，用 LeakCanary 捕获并截图引用链，再修复它。
  3. ★★ 编写 R8 keep 规则保护一个 Gson 数据类与一个 JNI 类，打 release 包验证功能与混淆效果（jadx 查看）。
  4. ★★★ 用 Keystore 实现 Token 的加密存储与读取，卸载重装后验证旧密文不可解（并说明工程上如何应对）。
  5. ★★★ 为 OkHttp 配置证书固定（含备份 pin），用 Charles 抓包验证失败，再用 debug 变体放行抓包。

小结与自测 ​

要点回顾：GC 先诊断后调参，大堆低延迟选 ZGC；Android 启动靠 Baseline Profile + 初始化收敛；泄漏治理靠 LeakCanary + CI 门禁；keep 规则随发版归档 mapping；密钥不出 Keystore/KMS；客户端校验永远可被绕过。

自测题：

  1. 什么特征的服务应该选 ZGC 而不是 G1？
  2. 为什么证书固定必须配置备份 pin？
  3. AES/GCM 加密时 IV 能否硬编码？为什么？
  4. isMinifyEnabled=true 与 isShrinkResources=true 的区别？
  5. 为什么 Root 检测不能只放在客户端做？
参考答案（点击展开）
  1. 堆 ≥16G 或停顿要求 <10ms 的延迟敏感服务；ZGC 停顿与堆大小无关，稳定在亚毫秒级。
  2. 主证书到期或 CA 更换时，没有备份 pin 会导致所有已发布 App 无法联网，属于可用性事故。
  3. 不能。GCM 模式下同一密钥重复使用 IV 会导致密钥流复用，攻击者可恢复明文甚至伪造密文；IV 必须每次随机生成并随密文存储。
  4. 前者做代码层面的混淆/压缩/裁剪；后者移除代码中未被引用的资源文件，需前者开启才生效。
  5. 客户端环境不可信，本地检测结果可被 Xposed/Frida 篡改；必须由服务端结合 Play Integrity 等服务端判定结果做最终决策。
