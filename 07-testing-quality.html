第 7 章 测试策略与质量保障 ​

测试不是成本而是杠杆：本章从测试金字塔出发，覆盖单元、协程、UI、契约测试与静态分析，最后用质量门禁把规范钉死在 CI 上。

上一章：第 6 章 性能优化与安全 ｜ 下一章：第 8 章 构建部署与 CI/CD

代码块定位：带 src=examples/... 的代码块由脚本从 examples/ 的真实文件渲染，并参与编译校验；未带 src= 的是纯示意片段（例如 com.shop 包名），用于说明机制，不保证可直接复制运行。

7.0 学习目标 ​

完成本章后，你将能够：

  1. 按测试金字塔规划团队测试投入，避免「冰淇淋蛋筒」反模式。
  2. 用 JUnit 5 + MockK + Kotest 编写高表达力的单元测试。
  3. 用 runTest 与 Turbine 测试协程与 Flow。
  4. 编写 Android 本地单测（Robolectric）与 Espresso/Compose UI 测试，了解 Pact 契约测试。
  5. 配置 JaCoCo 覆盖率、detekt + ktlint 静态分析，并在 CI 建立质量门禁。
  6. 用 jvm-test-suite 拆分快慢测试、用 test fixtures 复用测试数据，按分片并行执行。
  7. 用 ArchUnit 固化架构约束，用 PIT 变异测试与覆盖率门禁验证「测试是否有效」，并治理 flaky 用例。

7.3 JUnit 5 与 MockK ​

kotlin
// OrderServiceTest.kt —— JUnit 5 + MockK 标准组合
package com.shop.order

import io.mockk.*
import kotlinx.coroutines.test.runTest
import org.junit.jupiter.api.Assertions.*
import org.junit.jupiter.api.BeforeEach
import org.junit.jupiter.api.Test
import org.junit.jupiter.params.ParameterizedTest
import org.junit.jupiter.params.provider.ValueSource

class OrderServiceTest {

    private val repository = mockk<OrderRepository>()      // 接口 mock
    private lateinit var service: OrderService

    @BeforeEach
    fun setUp() {
        service = OrderService(repository)                 // 构造器注入天然可测
    }

    @Test
    fun `订单存在时返回订单`() = runTest {                 // runTest 见 7.4
        coEvery { repository.findById(1L) } returns Order(1L, "键盘", 39900)  // 协程 mock 用 coEvery
        val order = service.findById(1L)
        assertEquals("键盘", order.item)
        coVerify(exactly = 1) { repository.findById(1L) }  // 验证调用次数
    }

    @Test
    fun `订单不存在时抛出异常`() = runTest {
        coEvery { repository.findById(99L) } returns null
        assertThrows(NoSuchElementException::class.java) {
            kotlinx.coroutines.runBlocking { service.findById(99L) }
        }
    }

    @ParameterizedTest
    @ValueSource(longs = [-1L, 0L, Long.MIN_VALUE])        // 参数化：边界值批量验证
    fun `非法 id 直接拒绝`(id: Long) {                     // validate 为非 suspend 普通函数
        assertThrows(IllegalArgumentException::class.java) {
            service.validate(id)                          // 第 4 章 OrderService.validate
        }
        confirmVerified(repository)                        // 确保未访问仓库（快速失败）
    }
}

7.4 协程与 Flow 测试 ​

kotlin
// OrderViewModelTest.kt —— runTest + Turbine
package com.shop.feature.order

import app.cash.turbine.test
import io.mockk.coEvery
import io.mockk.mockk
import kotlinx.coroutines.ExperimentalCoroutinesApi
import kotlinx.coroutines.test.*
import org.junit.jupiter.api.AfterEach
import org.junit.jupiter.api.Assertions.assertEquals
import org.junit.jupiter.api.BeforeEach
import org.junit.jupiter.api.Test

@OptIn(ExperimentalCoroutinesApi::class)
class OrderViewModelTest {

    @BeforeEach
    fun setup() {
        Dispatchers.setMain(StandardTestDispatcher())          // 替换 viewModelScope 依赖的 Main 调度器
    }

    @AfterEach
    fun tearDown() {
        Dispatchers.resetMain()                               // 还原 Main，避免污染其他测试类
    }

    @Test
    fun `刷新成功后状态流转 loading 到数据`() = runTest {       // 虚拟时间：delay 立即完成
        val useCase = mockk<GetOrdersUseCase>()
        coEvery { useCase() } returns listOf(Order(1, "A", 100))
        val viewModel = OrderViewModel(useCase)

        viewModel.uiState.test {                                // Turbine 收集 Flow 断言
            assertEquals(OrderUiState(), awaitItem())           // 初始态
            viewModel.onEvent(OrderEvent.Refresh)
            assertEquals(true, awaitItem().loading)             // 加载中
            assertEquals(1, awaitItem().orders.size)            // 数据就绪
            cancelAndIgnoreRemainingEvents()
        }
    }

    @Test
    fun `虚拟时间精确控制 debounce`() = runTest {
        val scheduler = testScheduler
        var fired = 0
        backgroundScope.launch(kotlinx.coroutines.UnconfinedTestDispatcher(scheduler)) {
            kotlinx.coroutines.delay(5000)
            fired++
        }
        scheduler.advanceTimeBy(4999)                           // 手动推进虚拟时钟
        assertEquals(0, fired)
        scheduler.advanceTimeBy(1)
        assertEquals(1, fired)
    }
}

7.5 Kotest 规格风格与属性测试 ​

kotlin
// DiscountSpec.kt —— Kotest BehaviorSpec + 属性测试
package com.shop.pricing

import io.kotest.core.spec.style.BehaviorSpec
import io.kotest.matchers.shouldBe
import io.kotest.property.Arb
import io.kotest.property.arbitrary.long
import io.kotest.property.checkAll

class DiscountSpec : BehaviorSpec({

    Given("满 100 减 10 的优惠规则") {
        val rule = FullReductionRule(threshold = 100_00, off = 10_00)

        When("金额达到门槛") {
            Then("减免 10 元") {
                rule.apply(150_00) shouldBe 140_00
            }
        }
        When("金额不足门槛") {
            Then("保持原价") {
                rule.apply(99_99) shouldBe 99_99
            }
        }
    }

    Given("任意金额的属性约束") {
        checkAll(Arb.long(0..1_000_00)) { amount ->       // 随机生成 100 组输入
            val result = FullReductionRule(100_00, 10_00).apply(amount)
            (result <= amount) shouldBe true              // 不变量：优惠后绝不超过原价
        }
    }
})

Spring 测试切片（WebFlux / R2DBC） ​

Spring Boot Test 的测试切片（test slice）只装配某一层所需组件：@WebFluxTest 仅加载 WebFlux 基础设施与指定 @Controller，服务层不实例化而用 Mock 打桩，单个用例毫秒级；数据库切片同理只装仓库层。

kotlin
// 文件: order-web/src/test/kotlin/com/shop/order/OrderControllerSliceTest.kt —— @WebFluxTest + WebTestClient
package com.shop.order

import kotlinx.coroutines.flow.flowOf
import org.junit.jupiter.api.Test
import org.mockito.kotlin.whenever
import org.springframework.beans.factory.annotation.Autowired
import org.springframework.boot.test.autoconfigure.web.reactive.WebFluxTest
import org.springframework.test.context.bean.override.mockito.MockitoBean
import org.springframework.test.web.reactive.server.WebTestClient

@WebFluxTest(OrderController::class)                  // 只装配 Web 层：路由/序列化/参数校验生效，服务与 DB 不启动
class OrderControllerSliceTest {

    @Autowired
    lateinit var webTestClient: WebTestClient

    // Spring Boot 3.4+ 原生 @MockitoBean（替代已废弃的 @MockBean）；
    // Kotlin 下要 mock final 类 / suspend 函数，更推荐 com.ninja-squad:springmockk 提供的 @MockkBean
    @MockitoBean
    lateinit var service: OrderService

    @Test
    fun `订单列表返回 200 与 JSON 数组`() {
        whenever(service.listAll()).thenReturn(flowOf(Order(1L, "键盘", 39900)))

        webTestClient.get().uri("/orders").exchange()
            .expectStatus().isOk
            .expectBody()
            .jsonPath("$[0].item").isEqualTo("键盘")
    }
}

切片与全量集成测试的选择决策：

目标注解装配范围单类成本外部依赖
路由 / 参数校验 / JSON 序列化@WebFluxTest（Servlet 栈用 @WebMvcTest）仅 Web 层 + Mock 服务毫秒级无
数据库映射 / SQL / 迁移@DataR2dbcTest（JDBC 栈用 @DataJpaTest）数据源 + 仓库百毫秒~秒级Testcontainers + Docker
跨层链路 / 自动配置正确性@SpringBootTest完整 ApplicationContext秒~十秒视工程而定
外部 HTTP / 消息契约@SpringBootTest + MockServer/WireMock全量上下文 + 打桩外部依赖最慢Docker

经验：@SpringBootTest(webEnvironment = RANDOM_PORT) 启动完整上下文成本最高，控制在测试总量 10% 以内只保关键链路，其余按层切片；相同配置的切片会共享同一个上下文缓存，不要在测试里手工关闭 context。

运行方式：./gradlew test；依赖 spring-boot-starter-test（含 WebTestClient、JUnit 5、Mockito；用 @MockkBean 需再加 com.ninja-squad:springmockk:4.0.x）以及 org.testcontainers:postgresql、org.springframework.boot:spring-boot-testcontainers。数据库切片要求本机/CI 有可用的 Docker 守护进程（本地启动 Docker Desktop；GitHub Actions runner 原生支持）。

7.7 契约测试（Pact）简介 ​

微服务间接口变更是集成事故重灾区。Pact 采用消费者驱动契约（Consumer-Driven Contract）：

  1. 消费者（如 App 网关）写测试声明「我期望 GET /orders/1 返回这样的 JSON」；
  2. 生成交互文件（pact file）发布到 Pact Broker；
  3. 提供方（订单服务）CI 中回放 pact，验证自己是否满足契约。
kotlin
// OrderPactTest.kt —— 消费者侧契约示例（JUnit 5 + pact-jvm）
package com.shop.contract

import au.com.dius.pact.consumer.dsl.PactDslWithProvider
import au.com.dius.pact.consumer.junit5.PactConsumerTestExt
import au.com.dius.pact.consumer.junit5.PactTestFor
import au.com.dius.pact.core.model.PactSpecVersion
import au.com.dius.pact.core.model.RequestResponsePact
import au.com.dius.pact.core.model.annotations.Pact
import org.junit.jupiter.api.Test
import org.junit.jupiter.api.extension.ExtendWith
import java.net.http.HttpClient
import java.net.http.HttpRequest
import java.net.URI

@ExtendWith(PactConsumerTestExt::class)
@PactTestFor(providerName = "order-service", pactVersion = PactSpecVersion.V3)
class OrderPactTest {

    @Pact(consumer = "app-gateway")
    fun orderDetailPact(builder: PactDslWithProvider): RequestResponsePact =
        builder
            .given("订单 1 存在")
            .uponReceiving("查询订单详情")
            .path("/orders/1")
            .method("GET")
            .willRespondWith()
            .status(200)
            .body("""{"id":1,"item":"键盘","amount":39900}""")
            .toPact()

    @Test

7.9 测试分层工程化：test suite 与 test fixtures ​

7.10 ArchUnit：把架构约束变成测试 ​

模块边界靠自觉一定会失守。ArchUnit 读取字节码做静态分析，把「谁能依赖谁」写成可执行断言：

kotlin
// 文件: src/test/kotlin/com/example/backend/architecture/ArchitectureTest.kt —— ArchUnit 架构约束
// 配套章节：07-testing-quality.md 7.9（ArchUnit）、mastery-test-engineering.md D6.2
package com.example.backend.architecture

import com.tngtech.archunit.core.importer.ImportOption
import com.tngtech.archunit.junit.AnalyzeClasses
import com.tngtech.archunit.junit.ArchTest
import com.tngtech.archunit.lang.ArchRule
import com.tngtech.archunit.lang.syntax.ArchRuleDefinition.classes
import com.tngtech.archunit.lang.syntax.ArchRuleDefinition.noClasses
import org.springframework.stereotype.Service
import org.springframework.web.bind.annotation.RestController
import org.springframework.web.bind.annotation.RestControllerAdvice

// DoNotIncludeTests：只分析生产 classes，否则测试类自己的 JUnit 注解会命中「生产代码不依赖测试库」规则
@AnalyzeClasses(
    packages = ["com.example.backend"],
    importOptions = [ImportOption.DoNotIncludeTests::class],
)
class ArchitectureTest {

    // 命名约束：Web 入口必须叫 *Controller，业务服务必须叫 *Service，评审前由机器兜底
    @ArchTest
    val controllerNaming: ArchRule = classes()
        .that().areAnnotatedWith(RestController::class.java)
        .should().haveSimpleNameEndingWith("Controller")

    @ArchTest
    val serviceNaming: ArchRule = classes()
        .that().areAnnotatedWith(Service::class.java)
        .should().haveSimpleNameEndingWith("Service")

    // 依赖方向：生产代码不得依赖测试库（防止 mock 工具被打进运行时 classpath）
    @ArchTest
    val productionMustNotDependOnTestLibraries: ArchRule = noClasses()
        .that().resideInAPackage("com.example.backend..")
        .should().dependOnClassesThat()
        .resideInAnyPackage("org.junit..", "io.mockk..", "org.assertj..")

    // 分层约束：Web 注解只允许出现在 Controller 与统一异常处理器上，Service/工具类不得直接感知 HTTP
    @ArchTest
    val webAnnotationsOnlyInControllers: ArchRule = noClasses()
        .that().resideInAPackage("com.example.backend..")
        .and().areNotAnnotatedWith(RestController::class.java)
        .and().areNotAnnotatedWith(RestControllerAdvice::class.java)
        .should().dependOnClassesThat()
        .resideInAPackage("org.springframework.web.bind.annotation..")
}

// 文件: core/src/main/kotlin/demo/core/PriceCalculator.kt —— 供 PIT 变异测试演示的纯函数
// 配套章节：07-testing-quality.md 7.9~7.11（变异测试 / 覆盖率门禁）、mastery-test-engineering.md
package demo.core

object PriceCalculator {

    const val DISCOUNT_THRESHOLD_CENTS = 100_00L      // 满 100 元减 10 元
    const val DISCOUNT_CENTS = 10_00L

    /** 单笔金额满减：边界值 `== 阈值` 也享受优惠，这是 PIT 最容易暴露的变异点。 */
    fun discount(amountCents: Long): Long {
        require(amountCents >= 0) { "金额不能为负：$amountCents" }
        return if (amountCents >= DISCOUNT_THRESHOLD_CENTS) {
            amountCents - DISCOUNT_CENTS
        } else {
            amountCents
        }
    }

    fun total(items: List<Long>): Long = items.sumOf { discount(it) }

    fun checkoutSummary(items: List<Long>): String {
        val original = items.sum()
        val payable = total(items)
        return "原价 $original 分，优惠 ${original - payable} 分，应付 $payable 分"
    }
}

    }

企业级场景分析 ​

场景一：从「测试摆设」到「质量门禁」 ​

某公司测试代码 3 万行但线上事故不断，复盘发现：CI 只跑测试不校验结果 flaky 用例占 18%，团队习惯性「重跑几次绿了就行」。整改三步：

  1. flaky 用例隔离：标记 @Tag("flaky") 移出主流水线，限期修复否则删除——宁可少测，不要假绿；
  2. 门禁落地：JaCoCo 行覆盖 <70% 或 detekt 新增告警即阻断合并，存量告警冻结为基线（baseline），只禁增量；
  3. 变更测试选择：用 Gradle 的模块依赖图只跑受影响模块测试，PR 反馈从 40 分钟压到 8 分钟，测试反而越跑越勤。

场景二：支付链路的契约测试救场 ​

钱包团队升级「退款接口」字段（fee → refundFee）未通知收银台团队，预发环境才暴露，险些造成结算事故。引入 Pact 后，提供方每次发版必须回放全部消费者契约，字段级 breaking change 在提供方 CI 即失败。一年拦截 11 次接口破坏。经验：联调靠人、契约靠机器，跨团队接口必须有自动化契约兜底。

场景三：金融 App 的 UI 测试稳定性 ​

某银行 App 的 200 条 Espresso 用例成功率长期在 60% 徘徊。根因是硬编码 Thread.sleep 等待。全部改用 IdlingResource/Compose 的 waitUntil 后成功率升至 98%；再按「核心链路 20 条」精简执行集，全量用例转 nightly。经验：UI 测试的价值 = 稳定性 × 覆盖核心度，盲目追求数量是负资产。

场景四：5000 个用例的 12 分钟反馈 ​

某中台工程测试全量 38 分钟，PR 平均等待 1 小时。四步改造：

  1. 分层：Testcontainers/Spring 集成测试迁入 integrationTest suite，只跑 push 后；
  2. 并行：maxParallelForks=4 + JUnit 类级并行，单机耗时降 62%；
  3. 分片：按类名哈希切成 4 片进 CI matrix，墙钟时间从 38 分钟降到 11 分钟；
  4. 隔离：11 条 flaky 用例移入独立任务并限期修复，重跑率从 23% 降到 3%。

经验：反馈时间 = 测试总量 × 单测成本 ÷ 并行度，三个因子都有可操作手段；先分层再做并行，顺序反了会放大资源争抢。

实践任务 ​

  1. ★ 为一个「购物车计算」纯函数写 JUnit 5 参数化测试：覆盖空列表、单商品、满减边界三组以上数据。
  2. ★★ 用 MockK 测试第 4 章 ResilientCaller：mock 客户端连续失败，断言熔断后抛出 CallNotPermittedException。
  3. ★★ 用 runTest + Turbine 测试第 5 章 OrderViewModel 的失败路径：useCase 抛异常后 error 字段被正确设置。
  4. ★★★ 用 Kotest 属性测试验证「任意金额应用任意合法优惠规则后，结果 ∈ [0, 原价]」。
  5. ★★★ 在工程中接入 JaCoCo 覆盖率门禁 70% + detekt + ktlint，制造一次故意违规验证 CI 阻断生效。
  6. ★★ 把现有测试拆成 test 与 integrationTest 两个 suite，并让 integrationTest 只依赖 Testcontainers。
  7. ★★★ 给核心包配 PIT，目标变异覆盖率 80%；找出 3 个存活变异体并补断言。
  8. ★★★ 用脚本按类名哈希分片，在 CI matrix 中并行 4 片，记录墙钟时间对比。

小结与自测 ​

要点回顾：金字塔 70/20/10；MockK 是 Kotlin 测试标配；runTest 虚拟时间 + Turbine 断言 Flow；UI 测试只保核心链路；Pact 用契约替代人肉联调；门禁管增量不管存量；flaky 用例零容忍；测试工程化 = 分层 + fixtures + 并行分片 + ArchUnit + 变异测试。

自测题：

  1. 为什么大量 UI 测试是反模式？
  2. coEvery 与 every 的区别？
  3. runTest 中 delay(10_000) 为什么不会真的等 10 秒？
  4. 覆盖率 100% 为什么不是合理目标？
  5. Pact 的消费者驱动契约如何防止接口破坏？
  6. maxParallelForks 与 JUnit 的 junit.jupiter.execution.parallel.enabled 有什么区别？
  7. 变异测试报告里「存活变异体（survived）」说明了什么？
  8. 为什么 ArchUnit 分析时必须排除测试类？
参考答案（点击展开）
  1. UI 测试慢、脆弱、维护成本高，占比过大会拖垮反馈速度，最终被弃跑；核心链路少量 UI 测试 + 大量单测才是健康结构。
  2. coEvery 用于 stub 挂起函数（suspend），every 用于普通函数；用错会在运行期报 ClassCastException。
  3. runTest 使用 TestCoroutineScheduler 虚拟时间，delay 只是把任务排进虚拟时钟队列，立即按虚拟时间推进。
  4. 追求 100% 会催生无意义断言与实现细节的脆弱测试，维护成本超过收益；70%/85% 的基线 + 评审把关核心逻辑更可持续。
  5. 消费者把期望的交互固化为 pact 文件，提供方 CI 每次回放全部契约，任何破坏既有契约的变更（删字段、改类型）都会导致提供方构建失败，问题在发布前暴露。
  6. maxParallelForks 开多个独立 JVM 进程，隔离彻底但内存开销大（每个 fork 一套堆）；JUnit 并行在单 JVM 内多线程跑，启动快但共享状态风险高。二者应组合使用并确保测试无共享可变状态。
  7. 测试执行了变异后的代码但仍然通过，说明断言没有覆盖被改动行为（如只断言返回非空、没断言具体值），需要补精确断言。
  8. 测试类自身依赖 JUnit、MockK 等测试库；不排除时，「生产代码不得依赖测试库」规则会把测试代码判为违规，产生假阳性。
