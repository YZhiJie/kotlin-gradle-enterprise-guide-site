第 9 章 团队协作与代码规范 ​

代码写给人看，顺带能让机器运行。本章把前八章的技术能力收敛为可执行的团队制度：规范、评审、工作流与决策记录。

9.0 学习目标 ​

完成本章后，你将能够：

  1. 陈述 Kotlin 官方编码规范要点，并结合阿里/谷歌规范形成团队约定。
  2. 用 detekt + ktlint 的统一配置把规范固化为自动化检查。
  3. 对比 Trunk-Based 与 GitFlow，为团队选择并落地 Git 工作流。
  4. 使用 Conventional Commits 编写结构化提交信息，驱动自动化版本管理。
  5. 执行高质量 Code Review，编写 ADR 记录架构决策，并用 CODEOWNERS 管理多模块仓库责任边界。

9.2 Kotlin 编码规范要点 ​

Kotlin 官方规范（kotlinlang.org/docs/coding-conventions.html）是基线，以下为高频落地条款与两大厂规范的增量约定：

kotlin
// CodingStyle.kt —— 规范正误对照
package com.shop.order            // 包名全小写，层级反映目录

import java.time.LocalDate        // import 不用通配符（阿里/谷歌均禁止 import *）

class OrderValidator {            // 类名 UpperCamelCase

    companion object {
        private const val MAX_ITEMS = 99          // 常量 UPPER_SNAKE_CASE
    }

    fun validate(items: List<String>): Boolean {  // 函数 lowerCamelCase
        if (items.isEmpty()) return false         // ✅ 早返回（guard clause）

        val totalLength = items.sumOf { it.length }
        return totalLength <= MAX_ITEMS * 10
    }
}

// ❌ 反例：一个函数三个职责、魔法数字、布尔参数
fun process(data: List<String>, flag: Boolean): Int {
    // ...（略）缺少单一职责与命名语义
    return 0
}

团队附录（在官方规范之上的常见企业约定）：

约定规则理由
函数长度≤ 40 行（detekt LongMethod）超出即拆分
圈复杂度≤ 10（detekt CyclomaticComplexMethod）测试路径可控
参数个数≤ 5（detekt LongParameterList）超出用数据类聚合
布尔参数禁止（改用枚举/密封类）process(data, true) 无语义
公开 API必须显式声明返回类型Kotlin 推断让 API 变更难以评审
!!生产代码禁用（detekt 自定义规则）见第 1 章
  • ✅ 谷歌风格强调「可读性 > 个人表达」；阿里规范（Java 版思路同样适用 Kotlin）强调「空集合返回、Optional/可空二选一、日志必带上下文」。
  • ⚠️ 规范争议（如 var 的使用边界）由团队投票一次定稿，写入 CODING_GUIDE.md，之后交由工具执行，评审会上不再争论格式。

9.3 detekt / ktlint 团队统一配置 ​

yaml
# config/detekt/detekt.yml —— 团队规则集（节选）
complexity:
  LongMethod:
    threshold: 40                       # 函数行数上限
  CyclomaticComplexMethod:
    threshold: 10
  LongParameterList:
    functionThreshold: 5
style:
  MagicNumber:
    ignoreNumbers: ['-1', '0', '1', '2']
  ReturnCount:
    max: 3
  ForbiddenComment:
    values: ['TODO:', 'FIXME:']       # 禁止裸 TODO/FIXME 合入主干（必须带工单号）；detekt 配置键是 values 不是 comments
coroutines:
  GlobalCoroutineUsage:
    active: true                        # 禁止 GlobalScope（第 2 章）
  SleepInsteadOfDelay:
    active: true                        # 协程内禁止 Thread.sleep，必须用 delay
  # ⚠️ 「生产代码禁止 runBlocking」无内置规则：可编写自定义 detekt 规则（detekt-generator）
  # 或用 ArchUnit 在测试层固化
naming:
  FunctionNaming:
    ignoreAnnotated: ['Composable']     # Compose 函数允许大写开头

维度Trunk-BasedGitFlow
分支寿命小时~天周~月
合并冲突小而频繁大而集中

  • ✅ 实践趋势：后端一律 Trunk-Based；App 发版制团队用「Trunk-Based + release 分支」的简化 GitFlow（日常合 main，发版拉 release 分支，hotfix cherry-pick 回 main）。
  • ⚠️ 未完成的功能用 Feature Flag 隐藏而非长分支隔离——长分支是合并地狱的根源。

9.6 Code Review 清单 ​

评审节奏约定：PR ≤ 400 行变更、24 小时内首响、评论分级（blocking: 必须改 / suggestion: 建议 / nit: 吹毛求疵可不改）。

text
# review-checklist.md —— 团队评审清单
正确性
□ 边界条件（空集合/null/极值）是否处理？
□ 并发与事务边界是否正确？（协程作用域、@Transactional 范围）
□ 失败路径是否有补偿/降级？

架构与设计
□ 模块依赖方向是否符合约定？（第 3/5 章）
□ 是否引入新的三方依赖？必要性评审过吗？
□ 公开 API 变更是否有 ADR 支撑？（9.7）

质量与安全
□ 关键逻辑是否有测试？（第 7 章门禁兜底）
□ 日志是否脱敏？是否打印密钥/身份证/手机号？（第 6 章）
□ 配置变更是否同步更新了文档与默认值？

可读性
□ 命名是否自解释？函数是否单一职责？
□ 是否有「只有作者懂」的魔法数字/隐含前提？

9.7 ADR 架构决策记录 ​

ADR（Architecture Decision Record）用轻量文档回答「当时为什么这么决定」，避免半年后无人敢改、也无人能说清历史。

markdown
<!-- docs/adr/0007-use-r2dbc-instead-of-jpa.md —— ADR 模板实例 -->
# ADR-0007: 订单服务数据层采用 R2DBC 而非 JPA

- 状态：已接受（2026-03-15）
- 决策人：订单服务组

## 背景
秒杀链路峰值 2 万 QPS，现有 Spring MVC + JPA 线程模型在压测中
Tomcat 线程池打满，P99 达 2s（见第 4 章场景一）。

## 选项
1. 保持 JPA，扩容 3 倍实例 —— 成本不可接受
2. WebFlux + R2DBC 全链路非阻塞 —— 改造量大但治本
3. WebFlux + JPA（阻塞隔离池）—— 折中，但事务管理复杂

## 决策
选择方案 2。风控 SDK 等遗留阻塞调用用独立调度器隔离。

## 后果
- 正面：单机 QPS ×6，P99 降至 180ms
- 负面：团队需遵守「全链路非阻塞」纪律；CI 增加 runBlocking 禁则
- 关联：detekt 规则见 config/detekt/detekt.yml

9.8 多模块仓库的 CODEOWNERS ​

text

# 语法：路径模式  @负责人/团队；多条规则命中同一文件时「最后匹配的生效」（last match wins）

企业级场景分析 ​

场景一：从「规范文档」到「规范自动化」 ​

某 50 人团队有 30 页编码规范 Wiki，但评审会上 60% 时间仍在争论格式与命名。整改：把 Wiki 中可机器判定的 47 条规则全部转为 ktlint/detekt 配置（含 3 条自定义规则：禁 !!、禁 GlobalScope、公开函数必须显式返回类型），评审清单只保留机器判不了的 12 条。三个月后评审平均耗时从 45 分钟降到 15 分钟，格式类评论归零。教训：规范的执行力与自动化程度成正比，靠人盯人的规范必然腐化。

场景二：App 团队的工作流迁移 ​

某 App 团队用标准 GitFlow，develop 与 20 个 feature 长分支并行，每次发版合并冲突需要 2 人日。迁移到「Trunk-Based + release 分支」：日常全部短分支合 main（CI 门禁 + Feature Flag 隐藏未完成功能），发版日拉 release/x.y 只做 bugfix，hotfix cherry-pick 回 main。首个季度发版冲突工时降为 0.5 人日，发布频率从双周提升到每周。关键前提：CI 门禁足够强（第 7、8 章），否则主干会变垃圾场。

场景三：金融团队的 ADR 审计价值 ​

某支付团队接受外部审计，被要求说明「为何密钥轮换采用双密钥并行而非即时切换」。团队直接提供一年前的 ADR-0012（含监管条文引用与压测数据），审计一次通过。同期另一个无 ADR 的团队为同样问题重新开会论证三天。经验：合规行业里，决策过程的可追溯性与决策正确性同等重要。

实践任务 ​

  1. ★ 为工程配置 ktlint + detekt（复用第 7 章成果），故意提交一处 MagicNumber 与一处超长函数，观察拦截输出。
  2. ★★ 用 Conventional Commits 重写你最近 5 条提交信息，并标注每条触发的版本变更类型。
  3. ★★ 在练习仓库配置 CODEOWNERS：两个目录归属不同「团队」（可用小号或同事账号模拟），验证 PR 自动指派。
  4. ★★★ 为你的项目写一篇 ADR：记录「DI 框架选 Hilt 还是 Koin」或「工作流选 TBD 还是 GitFlow」的完整权衡过程。
  5. ★★★ 制定团队评审清单 v1.0（结合 9.6 模板裁剪为不超过 15 条），并在一次真实 PR 中应用，记录发现的 1 个机器查不出的问题。

小结与自测 ​

要点回顾：规范的生命力在自动化；工作流匹配发布节奏（服务 TBD、客户端简化 GitFlow）；提交信息结构化才能驱动自动发版；评审管机器管不了的；ADR 保存权衡过程；CODEOWNERS 让责任边界显式化。

自测题：

  1. 为什么 ktlint 与 detekt 要同时存在而不是二选一？
  2. Trunk-Based 落地的两个硬前提是什么？
  3. feat(order)!: 中的 ! 表示什么？（等价写法是什么）
  4. ADR 被推翻时应该修改原文吗？为什么？
  5. CODEOWNERS 中多条规则匹配同一文件时，哪条生效？
参考答案（点击展开）
  1. ktlint 专注代码格式（零争议、可自动修复），detekt 专注语义与代码气味（圈复杂度、协程误用等），职责互补且后者可自定义规则。
  2. 足够强的 CI 门禁（自动化测试与静态分析兜底）与 Feature Flag 机制（未完成功能不进用户视野）。
  3. 表示破坏性变更，等价于 footer 写 BREAKING CHANGE:，触发 MAJOR 版本升级。
  4. 不应该。ADR 是历史快照，被推翻时新增一篇状态为「取代 ADR-xxxx」的记录，保留完整决策演进轨迹。
  5. 文件中靠后的规则优先（last match wins），因此兜底规则 * 必须放在最前面，专项规则放后面。
