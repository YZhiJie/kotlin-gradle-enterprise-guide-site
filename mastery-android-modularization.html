专题 · Android 多模块与变体（D4） ​

目标：把一个「所有代码都塞在 :app」的 Android 工程，改造成依赖方向可执行、变体可枚举、数据可迁移、DI 可装配的多模块工程，并用真实构建数据判断改造是否值得。

对应正文：第 5 章 5.6 模块化 ｜ 5.7 多渠道与 BuildVariant 可运行示例：examples/android-app（10 个模块，assembleDebug / assembleRelease 均通过）

D4.0 目标读者与前置 ​

  • 目标读者：Android 架构师、平台/构建工程师、准备做组件化改造的 Tech Lead。
  • 前置：能读懂 Kotlin DSL 与 Version Catalog；理解 implementation / api 两种依赖配置；知道 BuildType 与 flavor 的基本概念（第 5 章 5.7）。
  • 不适用：只有一两个页面的小 App。模块化的固定成本（构建脚本、约定插件、跨模块导航）通常要 5~8 个业务模块才能摊平。

D4.1 痛点：单模块工程的四个必然结局 ​

现象根因后果
改一行代码等 5~15 分钟所有源码在同一个 Kotlin 编译任务里反馈慢，开发者开始绕过构建（不编译就提交）
UI 层直接查 DAO / 直接用 Retrofit没有模块边界，impl 对所有人可见换存储、换网络库时改动面失控
渠道差异靠 if (flavor == "demo")变体差异散落在业务代码渠道包互相污染，测试无法穷举
release 包突然变大 / 崩溃test-only 代码或调试实现被打进生产包线上事故，且很难定位来源

模块化不是「目录更整齐」，而是把上述四件事分别交给编译器、构建系统、source set、依赖配置去强制。

D4.3 api / impl 拆分：让编译器替你守分层 ​

Gradle 的 api 与 implementation 不是风格差异，而是编译类路径的可见性：

  • api(project(":core:data:api"))：依赖我的模块也能看到 :core:data:api 里的类型；
  • implementation(project(":core:data:impl"))：只有我自己能看，别人编译时看不到。

因此数据层拆成两半：

examples/android-app/core/data/api/src/main/kotlin/com/example/guide/core/data/api/TodoRepository.kt
kotlin

    suspend fun add(title: String, priority: Int = 0)

判断是否该拆 api/impl 的三个信号：

  1. 有实现细节你不想让上层看见（数据库实体、网络 DTO、第三方 SDK 类型）；
  2. 同一契约未来可能有两种实现（本地 Room / 远端 API / Fake 测试）；
  3. 你希望测试替换实现，而不是 mock 一堆静态方法。

不该拆的情况：模块只有一个 30 行的工具类、没有实现细节可藏。为拆而拆只会增加构建脚本与认知负担。

D4.4 约定插件：把重复配置收敛到一行 ​

多模块工程最大的隐性成本是「每个模块都要复制一遍 SDK、Java 版本、测试依赖」。示例复用 gradle-demo 的组合构建模式：includeBuild("build-logic") + 共享 libs.versions.toml。

// 文件: build-logic/convention/src/main/kotlin/shop/AndroidLibraryConventionPlugin.kt
package shop

import com.android.build.api.dsl.LibraryExtension
import org.gradle.api.JavaVersion
import org.gradle.api.Plugin
import org.gradle.api.Project
import org.gradle.api.artifacts.VersionCatalogsExtension
import org.gradle.kotlin.dsl.configure
import org.gradle.kotlin.dsl.dependencies
import org.jetbrains.kotlin.gradle.dsl.JvmTarget
import org.jetbrains.kotlin.gradle.dsl.KotlinAndroidProjectExtension

/**
 * shop.android.library —— 所有 Android Library 模块的公共约定：
 * 1. 统一 compileSdk / minSdk / build-tools，避免各模块漂移；
 * 2. 统一 Java 17 与 Kotlin JVM target；
 * 3. 统一协程与单元测试依赖；
 * 4. unit test 对 Android stub 方法返回默认值，便于纯 JVM 测试。
 */
class AndroidLibraryConventionPlugin : Plugin<Project> {
    override fun apply(target: Project): Unit = with(target) {
        pluginManager.apply("com.android.library")
        pluginManager.apply("org.jetbrains.kotlin.android")

        val libs = extensions.getByType(VersionCatalogsExtension::class.java).named("libs")
        val compileSdk = libs.findVersion("compileSdk").get().requiredVersion.toInt()
        val minSdk = libs.findVersion("minSdk").get().requiredVersion.toInt()
        val buildTools = libs.findVersion("buildTools").get().requiredVersion

        extensions.configure<LibraryExtension> {
            this.compileSdk = compileSdk
            buildToolsVersion = buildTools
            defaultConfig {
                this.minSdk = minSdk
            }
            compileOptions {
                sourceCompatibility = JavaVersion.VERSION_17
                targetCompatibility = JavaVersion.VERSION_17
            }
            testOptions {
                unitTests.isReturnDefaultValues = true
            }
        }

        extensions.configure<KotlinAndroidProjectExtension> {
            compilerOptions {
                jvmTarget.set(JvmTarget.JVM_17)
            }
        }

        dependencies {
            add("implementation", libs.findLibrary("kotlinx-coroutines-android").get())
            add("testImplementation", libs.findLibrary("junit4").get())
            add("testImplementation", libs.findLibrary("kotlinx-coroutines-test").get())
        }
    }
}

D4.5 边界强制校验：Gradle 任务 vs ArchUnit vs lint ​

规则写在文档里必然失效。示例在 build-logic 里实现 shop.module.boundaries，在配置阶段读取各模块声明的工程依赖，命中规则就让构建失败：

examples/android-app/build-logic/convention/src/main/kotlin/shop/ModuleBoundaryPlugin.kt
kotlin
// 文件: build-logic/convention/src/main/kotlin/shop/ModuleBoundaryPlugin.kt
package shop

import org.gradle.api.DefaultTask
import org.gradle.api.GradleException
import org.gradle.api.Plugin
import org.gradle.api.Project
import org.gradle.api.artifacts.ProjectDependency
import org.gradle.api.provider.ListProperty
import org.gradle.api.tasks.Input
import org.gradle.api.tasks.TaskAction

/**
 * shop.module.boundaries —— 模块依赖边界校验（D4）。
 *
 * 为什么不选 ArchUnit / lint：
 * - ArchUnit 校验的是「字节码里的包依赖」，需要先编译全部模块，反馈慢，且无法覆盖 Gradle 依赖方向；
 * - lint 自定义规则门槛高、跨模块依赖图仍需额外建模；
 * - 自定义 Gradle 任务直接读 Declared Dependencies，配置阶段即可判定，几毫秒完成，且能精确到 configuration 名
 *   （这正是 test-only 模块这类规则需要的维度）。
 *
 * 规则在配置阶段计算并作为 Task 输入固化，执行阶段不再访问其他 Project，兼容配置缓存。
 */
class ModuleBoundaryPlugin : Plugin<Project> {
    override fun apply(target: Project) {
        target.gradle.projectsEvaluated {
            val violations = collectViolations(target)
            target.tasks.register("checkModuleBoundaries", ModuleBoundaryTask::class.java) {
                group = "verification"
                description = "校验模块依赖方向：feature 不互赖、core 不依赖 feature、api 不依赖 impl、测试模块只进测试配置"
                this.violations.set(violations)
            }
        }
    }

    private fun collectViolations(root: Project): List<String> {
        val result = mutableListOf<String>()
        root.subprojects.sortedBy { it.path }.forEach { project ->
            val from = project.path
            // 只看声明式依赖，不做 resolve：避免触发网络与配置开销
            project.configurations.forEach { configuration ->
                val name = configuration.name
                // 配置名大小写混用：implementation/api 为小写，debugImplementation 为驼峰，统一转小写判断
                val lower = name.lowercase()
                if (!lower.endsWith("implementation") &&
                    !lower.endsWith("api") &&
                    !lower.endsWith("runtimeonly") &&
                    !lower.endsWith("compileonly")
                ) {
                    return@forEach
                }
                configuration.dependencies.withType(ProjectDependency::class.java).forEach { dependency ->
                    val to = dependency.dependencyProject.path
                    val reason = checkRule(from, to, name)
                    if (reason != null) {
                        result += "$from -> $to ($name)：$reason"
                    }
                }
            }
        }
        return result.distinct().sorted()
    }

    private fun checkRule(from: String, to: String, configuration: String): String? {
        if (to == ":app") {
            return "任何模块都不允许反向依赖壳工程 :app"
        }

        val fromFeature = featureName(from)
        val toFeature = featureName(to)
        if (fromFeature != null && toFeature != null && fromFeature != toFeature) {
            return "Feature 之间禁止直接依赖实现模块，请依赖对方的 *:api 模块或通过导航事件解耦"
        }

        if (from.startsWith(":core:") && toFeature != null) {
            return "Core 层不允许依赖 Feature 层"
        }

        if (from == ":core:model" && to != from) {
            return ":core:model 是领域模型，必须保持零工程依赖"
        }

        if (from == ":core:data:api" && to == ":core:data:impl") {
            return "API 模块不能依赖实现模块（依赖方向必须是 impl -> api）"
        }

        // test-only 模块：只允许出现在名字含 test 的配置中（testImplementation / androidTestImplementation 等）
        if (to == ":core:testing" && !configuration.contains("test", ignoreCase = true)) {
            return ":core:testing 是 test-only 模块，只能出现在测试配置"
        }

        return null
    }

    private fun featureName(path: String): String? =
        if (path.startsWith(":feature:")) path.split(":").getOrNull(2) else null
}

abstract class ModuleBoundaryTask : DefaultTask() {

    @get:Input
    abstract val violations: ListProperty<String>

    @TaskAction
    fun check() {
        val found = violations.get()
        if (found.isEmpty()) {
            logger.lifecycle("模块依赖边界校验通过：feature 不互赖、core 不依赖 feature、api 不依赖 impl、测试模块只进测试配置")
            return
        }
        throw GradleException(
            buildString {
                append("发现 ").append(found.size).append(" 处模块依赖边界违规：\n")
                found.forEach { append("  - ").append(it).append('\n') }

四条规则：

  1. :core:model 零工程依赖；
  2. :core:* 不得依赖 :feature:* / :app；
  3. 不同 feature 之间禁止直接依赖实现模块（同 feature 的 impl -> api 允许）；
  4. :core:testing 只能出现在名字含 test 的配置。

为什么选 Gradle 任务：

  • 反馈最快：配置阶段就能判定，不需要先编译；
  • 维度正确：能区分 implementation / testImplementation / demoImplementation，这正是 test-only 模块规则需要的；
  • 成本最低：约 100 行 Kotlin，随模块图自动生效。

ArchUnit 适合补充什么：包级分层（如 ui 不得直接 import data）、注解使用规范、类命名。它工作在字节码层，必须先编译，因此不适合做「模块依赖方向」的第一道闸。

lint 自定义规则适合什么：源码级的 API 使用限制（如禁止直接 new Thread()）、资源命名。它无法替代依赖图校验。

D4.6.1 androidComponents.onVariants 的职责边界 ​

onVariants 是 AGP 8 提供的变体感知配置入口，适合做：

  • 按变体注入 BuildConfig 字段（示例的 API_BASE_URL / CHANNEL）；
  • 按变体开关特性（如 minifiedEnabled、enableAndroidTest）；
  • 收集变体元数据生成报告（示例的 variantMatrix 任务）。

不适合做：

  • 修改依赖坐标（依赖应在 DSL 的 dependencies 中用 demoImplementation 声明）；
  • 在回调里启动耗时操作（它在配置阶段执行）；
  • 读取 Project 的可变状态（会破坏配置缓存）。

// 文件: core/data/impl/src/main/kotlin/com/example/guide/core/data/impl/settings/DataStoreSettingsRepository.kt
package com.example.guide.core.data.impl.settings

import android.content.Context
import androidx.datastore.core.DataStore
import androidx.datastore.preferences.core.Preferences
import androidx.datastore.preferences.core.booleanPreferencesKey
import androidx.datastore.preferences.core.edit
import androidx.datastore.preferences.core.emptyPreferences
import androidx.datastore.preferences.preferencesDataStore
import com.example.guide.core.data.api.SettingsRepository
import kotlinx.coroutines.flow.Flow
import kotlinx.coroutines.flow.catch
import kotlinx.coroutines.flow.map
import java.io.IOException

// 一个 Context 文件只允许一个 DataStore 实例：用属性委托保证单例语义
private val Context.settingsDataStore: DataStore<Preferences> by preferencesDataStore(name = "settings")

/** DataStore 实现：类型安全、无 SharedPreferences 的 apply() 阻塞与 ANR 风险。 */
class DataStoreSettingsRepository(
    private val dataStore: DataStore<Preferences>
) : SettingsRepository {

    private val showCompletedKey = booleanPreferencesKey("show_completed")

    override val showCompleted: Flow<Boolean> = dataStore.data
        // 读取失败（文件损坏等）时降级为默认值，避免 UI 永久挂起
        .catch { error -> if (error is IOException) emit(emptyPreferences()) else throw error }
        .map { prefs -> prefs[showCompletedKey] ?: true }

    override suspend fun setShowCompleted(value: Boolean) {
        dataStore.edit { prefs -> prefs[showCompletedKey] = value }
    }
}

/** 给 Koin 模块用的工厂：Application Context 由 androidContext() 注入。 */
fun createSettingsRepository(context: Context): SettingsRepository =
    DataStoreSettingsRepository(context.applicationContext.settingsDataStore)

Feature 层把 Room 列表与偏好合并，任一数据源变化都会重算 UI：

examples/android-app/feature/todo/impl/src/main/kotlin/com/example/guide/feature/todo/impl/TodoViewModel.kt
kotlin
// 文件: feature/todo/impl/src/main/kotlin/com/example/guide/feature/todo/impl/TodoViewModel.kt
package com.example.guide.feature.todo.impl

import androidx.lifecycle.ViewModel
import androidx.lifecycle.viewModelScope
import com.example.guide.core.data.api.SettingsRepository
import com.example.guide.core.data.api.TodoRepository
import com.example.guide.core.model.Todo
import kotlinx.coroutines.flow.MutableStateFlow
import kotlinx.coroutines.flow.StateFlow
import kotlinx.coroutines.flow.asStateFlow
import kotlinx.coroutines.flow.combine
import kotlinx.coroutines.flow.update
import kotlinx.coroutines.launch

data class TodoUiState(
    val loading: Boolean = true,
    val todos: List<Todo> = emptyList(),
    val input: String = "",
    val showCompleted: Boolean = true
)

sealed interface TodoEvent {
    data class InputChanged(val value: String) : TodoEvent
    data object Add : TodoEvent
    data class Toggle(val id: Long, val done: Boolean) : TodoEvent
    data class Delete(val id: Long) : TodoEvent
    data class ToggleShowCompleted(val value: Boolean) : TodoEvent
}

class TodoViewModel(
    private val repository: TodoRepository,
    private val settings: SettingsRepository,
) : ViewModel() {

    private val _uiState = MutableStateFlow(TodoUiState())
    val uiState: StateFlow<TodoUiState> = _uiState.asStateFlow()

    init {
        // 两个数据源合并：Room 的 todos + DataStore 的偏好，任一变化都重算 UI 状态
        viewModelScope.launch {
            combine(repository.observeTodos(), settings.showCompleted) { todos, show ->
                todos to show
            }.collect { (todos, show) ->
                _uiState.update {
                    it.copy(
                        loading = false,
                        showCompleted = show,
                        todos = if (show) todos else todos.filterNot { todo -> todo.done }
                    )
                }
            }
        }
    }

    fun onEvent(event: TodoEvent) {
        when (event) {
            is TodoEvent.InputChanged ->
                _uiState.update { it.copy(input = event.value) }

            TodoEvent.Add -> {
                val title = _uiState.value.input.trim()
                if (title.isEmpty()) return
                _uiState.update { it.copy(input = "") }             // 先清空输入框
                viewModelScope.launch { repository.add(title) }     // 写库后 Flow 自动推送新列表
            }

            is TodoEvent.Toggle ->
                viewModelScope.launch { repository.setDone(event.id, event.done) }

            is TodoEvent.Delete ->
                viewModelScope.launch { repository.delete(event.id) }

            is TodoEvent.ToggleShowCompleted ->
                viewModelScope.launch { settings.setShowCompleted(event.value) }
        }
    }
}

package com.example.guide.core.data.impl.di

import androidx.room.Room
import com.example.guide.core.data.api.SettingsRepository
import com.example.guide.core.data.api.TodoRepository
import com.example.guide.core.data.impl.RoomTodoRepository

/**
 * 数据层 Koin 模块：壳工程在 startKoin 时装配。
 * - Room/DataStore 的构造细节只存在于本模块；

            .build()

    single<TodoRepository> { RoomTodoRepository(get()) }
    single<SettingsRepository> { createSettingsRepository(androidContext()) }
}

D4.9 实测：构建耗时与产物 ​

环境：macOS Apple Silicon、JDK 21、Gradle 8.10、--no-daemon、依赖已缓存、配置缓存可复用。

场景命令耗时产物
全量冷构建./gradlew :app:assembleDebug6sapp-demo-debug.apk 11 MB、app-full-debug.apk 11 MB
壳工程重建 ×2:app:clean + assembleDebug6s / 6s同上
Release:app:clean + assembleRelease6s两个 unsigned release APK，各 8.1 MB
单模块:feature:todo:impl:clean + assembleDebug8sAAR
边界校验checkModuleBoundaries<1s（无违规时）无产物，失败即阻断
变体矩阵variantMatrix<1sapp/build/reports/variant-matrix.txt

结论：

  1. 10 模块规模下，模块化不会让单次构建显著变快；它解决的是变更影响面与依赖失控，不是「立刻提速 10 倍」。
  2. 单模块构建耗时被 Gradle 启动与配置主导，因此「模块化提速」必须配合第 7 章（D7）的构建缓存与 CI 分片才有体感。
  3. 两个 flavor 的增量成本很低，因为 core 与 feature 的编译产物被复用；真正昂贵的是「每个 flavor 各自一套 Feature 实现且互不复用」。

症状高概率原因处理
Cannot find schema file .../1.json没先构建 v1 或未提交 schema切回 v1 构建生成并提交，再升 v2
AutoMigration 编译失败新增非空列缺 defaultValue补 @ColumnInfo(defaultValue = "0")

Kotlin 编译找不到 Feature 实现只写了 demoImplementation，却在 main 引用把引用移到对应 flavor source set
Koin NoDefinitionFoundException模块未 startKoin 或 ViewModel 未注册补 modules(...) / viewModelOf，并加 checkModules() 测试
