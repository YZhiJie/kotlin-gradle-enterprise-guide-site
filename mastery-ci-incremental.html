精通专题 · CI 增量与缓存 ​

专题定位：CI 优化的目标不是「让某一步更快」，而是让反馈时间可预测、可度量、可回归。本专题把流水线拆成三层增量，并给出每一层的度量口径与失效边界。

前置阅读：第 8 章 构建部署与 CI/CD 8.1~8.6（发布、镜像、K8s、基础流水线）；建议先读 D6 测试工程化 的分层与分片结论。

D7.0 目标读者与痛点 ​

角色典型痛点
DevOps每次 push 都全量跑，runner 分钟烧得快，但说不清哪些步骤真的必要
构建工程师缓存配了但命中率低，不知道是键设计错了还是任务输入声明错了
Tech LeadPR 排队 40 分钟，只能靠「重跑一次」绕过 flaky，反馈时间不可预测
平台负责人多工程、多模块仓库，流水线复制了 5 份，改一处要同步 5 处

本专题交付四类可执行机制：

  1. 选择——工程级 path filter → 模块级依赖图 → 任务级缓存，三层各自可关闭、可观测；
  2. 复用——workflow_call 复用工作流，编排层只负责「选谁跑、跑什么」；
  3. 度量——总墙钟 / 任务执行 / 配置阶段 / 缓存命中四类指标，每类都有读取位置；
  4. 发布——版本号与 CHANGELOG 由提交历史推导，发布动作本身不进入增量门禁。

D7.1 反馈时间模型：先把「慢」拆开 ​

一条流水线的端到端时间可以拆成五项：

text
反馈时间 = 排队等待 + 环境准备 + 配置阶段 + 任务执行 + 结果汇总
1
组成典型量级优化手段是否受「增量」影响
排队等待分钟级并发配额、concurrency 取消旧 run间接（少跑 job 才不排队）
环境准备10~60ssetup-java / setup-gradle 缓存、预构建镜像否
配置阶段1~10s配置缓存、减少项目数、避免配置期 I/O部分（模块选择减少配置对象）
任务执行10s~分钟模块选择、测试分片、并行 fork是
结果汇总秒级报告制品、失败即上传否

关键判断：小工程上「总墙钟」被配置阶段主导，模块选择几乎不改善体感；只有任务执行占比足够大（模块 × 测试量）时，增量才体现为墙钟收益。因此优化前必须先量出任务执行占总时长的比例，否则容易把「配置慢」误判为「测试慢」。

经验阈值：

  • 配置阶段 ≤ 总时长 20% 视为健康；
  • PR 反馈 ≤ 10 分钟，主干 ≤ 30 分钟；
  • 缓存命中率 ≥ 60%（任务级 FROM-CACHE + UP-TO-DATE 占比）。

三层是相乘关系：工程级跳过 → 模块级缩小矩阵 → 任务级把剩余工作变成缓存命中。任何一层失效都不应导致错误结果，只应退化为更慢。

D7.3 模块级分析：affected-modules 的原理 ​

脚本（scripts/affected-modules.mjs）只做四件事，刻意保持静态、无 Gradle 依赖：

  1. 读 settings.gradle.kts 的 include(...)，得到模块路径 → 目录映射（兼容 include("app") 与 include(":app")）；
  2. 读各模块 build.gradle.kts 中的 project(":x")，得到直接依赖；
  3. 把 git diff --name-only 的文件按最长目录前缀归属到模块（避免 :core 抢走 :core:data）；
  4. 沿依赖图做反向闭包：A 依赖 B，B 变更则 A 必须重建。
bash
# 指定文件（不依赖 git 历史，适合本地验证）
node scripts/affected-modules.mjs \
  --project examples/gradle-demo \
  --files core/src/main/kotlin/demo/core/PriceCalculator.kt \
  --tasks test
# → :core:test :app:test

# CI：按 base ref 计算，并输出 GitHub Actions matrix
node scripts/affected-modules.mjs \
  --project examples/gradle-demo --base "$BASE_SHA" --github-output
# count=2
# matrix=[{"module":":core","name":"core","tasks":":core:test"}, ...]

保守降级规则（宁可全量，不可漏跑）：

变更位置判定理由
build-logic/**全量约定插件影响所有模块
settings.gradle.kts / gradle.properties / gradle/libs.versions.toml全量工程级共享输入，无法精确归因
gradlew / wrapper / 工程根文件全量构建基础设施
无变更空矩阵所有模块 job 跳过

实测输出（examples/gradle-demo）：

变更结果
core/src/main/.../PriceCalculator.kt:core:test :app:test
app/src/...:app:test
build-logic/...全量 :app:test :core:test
无变更空
examples/android-app 上 HEAD~410 个模块全部受影响

⚠️ 这是模块级增量，不替代 Gradle 的任务级增量。二者叠加才有意义：模块选择减少任务数量，构建缓存减少单任务耗时。

D7.4 真实耗时对比与可复现度量 ​

在 examples/gradle-demo（2 模块、16 个测试、JDK 21、--no-daemon）上用 --profile 实测：

场景总构建时间任务执行时间说明
全量 clean test3.431s0.395s2 个模块都执行
增量 clean :core:test3.382s0.288s只执行 1 个模块
help（仅配置）≈5s0配置与启动开销

诚实结论：总墙钟几乎不变（−1.3%），因为配置阶段约 3 秒且无法被模块选择消除；任务执行下降 27%。在 CI 上配置与依赖解析被缓存后，任务执行占比上升，收益才会显现；模块数与单模块测试量越大，收益越接近线性。

可复现步骤：

bash
cd examples/gradle-demo
# 全量
./gradlew clean test --no-daemon --profile --build-cache
# 增量
./gradlew clean :core:test --no-daemon --profile --build-cache
# 读取 build/reports/profile/*.html 中的 Total Build Time 与 Task Execution 两行

D7.5 可复用工作流与编排 ​

三个文件构成一套可复制骨架（examples/ci/.github/workflows/）：

文件角色关键点
reusable-jvm.ymlJVM 构建复用单元workflow_call 输入 project-path / tasks / java-version / cache-read-only
reusable-android.ymlAndroid 构建复用单元额外注入 SDK，默认只构建 demoDebug
ci.yml编排层path filter → affected matrix → 调用复用工作流
yaml
# ci.yml 关键片段
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true          # 新提交取消旧 run；release.yml 不设，避免半成品 tag

job:
  gradle-demo:
    needs: affected
    strategy:
      fail-fast: false
      matrix:
        include: ${{ fromJSON(needs.affected.outputs.matrix) }}
    uses: ./.github/workflows/reusable-jvm.yml
    with:
      project-path: examples/gradle-demo
      tasks: ${{ matrix.tasks }}
      cache-read-only: ${{ github.event_name == 'pull_request' }}

设计要点：

  • 矩阵来自脚本，不是手写：matrix.include 的元素同时包含 module / name / tasks，job 名可读、制品名合法（脚本已把 : 替换为 -）；
  • fail-fast: false：一个模块失败不应掩盖其他模块的结果；
  • cache-read-only 只在 PR 为 true：PR 缓存不写回主干，避免不可信内容污染与配额挤占；
  • concurrency 放编排层：复用层被多个调用方共用，放里面会把不同工程的 run 互相关掉；
  • fetch-depth: 0 只给 affected job：diff 需要完整历史，其他 job 用浅克隆更快。

远程构建缓存 ​

本地缓存只服务单机。examples/gradle-demo/settings.gradle.kts 已内置环境变量驱动的远程缓存：

kotlin
val remoteCacheUrl = providers.environmentVariable("GRADLE_REMOTE_CACHE_URL").orNull
if (!remoteCacheUrl.isNullOrBlank()) {
    buildCache {
        remote<HttpBuildCache> {
            url = uri(remoteCacheUrl)
            isPush = providers.environmentVariable("CI").orNull == "true"   // 只让 CI 写
            isAllowUntrustedServer =
                providers.environmentVariable("GRADLE_REMOTE_CACHE_ALLOW_HTTP").orNull == "true"
            credentials {
                username = providers.environmentVariable("GRADLE_REMOTE_CACHE_USER").orNull
                password = providers.environmentVariable("GRADLE_REMOTE_CACHE_PASSWORD").orNull
            }
        }
    }
}

要点：

  • fetch-depth: 0 必须，否则读不到历史 tag；
  • 发布提交带 [skip ci]，避免「发版 → 触发 CI → 再发版」循环；
  • release.yml 不加 cancel-in-progress，发布被取消会留下半完成状态；
  • 需要预览时用 workflow_dispatch + --dry-run。

Gradle 库工程也可用 net.nemerosa.versioning 直接由 git tag 推导 project.version，但 CHANGELOG 仍需另外生成。

D7.8 排障路径 ​

现象先查常见根因修复
该跑的模块没跑affected 输出base 取错（push 用了 HEAD~1 而实际多提交）用 github.event.before 或 PR base sha
不该跑的模块跑了变更归属文件落在模块目录外 → 全量降级属正常保守行为；必要时补目录映射
缓存命中率低--info 日志自定义任务输入漏声明、绝对路径进输入补 @InputFiles / 用 @PathSensitive
缓存「命中但结果错」输入声明环境变量/时间未建模为输入改为 @Input 并禁用该任务缓存
PR 缓存写不进权限fork PR 只读、cache-read-only 生效预期行为，主干负责写入
发布重复触发提交信息发布提交未带 [skip ci]检查 .releaserc.json 的 git 插件配置
流水线互相取消concurrencygroup 粒度过粗（按 workflow 而非 ref）group 带 github.ref，发布单独配置

D7.9 实践任务 ​

  1. ★ 在 examples/gradle-demo 上用 --files 分别模拟 core / app / build-logic 变更，记录 affected 输出与预期是否一致。
  2. ★★ 用 --profile 复现全量与增量两组数据，算出任务执行占比，并解释为什么总墙钟变化很小。
  3. ★★ 把 examples/ci/.github/workflows/ 复制到自己的仓库，改 path filter 与 matrix 输入，观察一次 PR 的 job 图。
  4. ★★ 人为给一个自定义任务漏标 @InputFiles，观察缓存命中异常，再修复并对比。
  5. ★★★ 接入一台 HTTP 远程缓存（可用自建或云存储网关），验证「机器 A 构建、机器 B 命中」。
  6. ★★★ 设计一条 PR 流水线：文档改动 0 job、单模块改动 1 job、共享输入改动全量，并给出各场景的预期时长。

D7.10 自测题 ​

  1. 为什么小工程上「只跑一个模块」的总墙钟几乎不变？
  2. affected-modules 为什么对 build-logic 变更直接全量，而不是逐个模块分析？
  3. cache-read-only 为什么只在 PR 上开启？
  4. 缓存命中率低时，为什么先查任务输入声明而不是加大缓存？
  5. concurrency 应该放在复用工作流还是编排层？为什么？
  6. semantic-release 的发布提交为什么必须带 [skip ci]？

参考答案要点 ​

  1. 配置阶段（wrapper 启动、settings 求值、插件解析）是固定成本，模块选择只减少任务执行；小工程任务执行占比低。
  2. 约定插件被所有模块应用，其变更会影响每个模块的编译行为；静态脚本无法精确判断影响面，只能保守全量。
  3. PR 的缓存内容不可信且会挤占配额；只读可复用主干缓存，又不污染它。
  4. 命中率由输入哈希决定；输入漏声明会让「本应失效」的任务误命中或反复失效，缓存大小不是根因。
  5. 编排层。复用层的同一 group 会把不同调用方/不同工程的 run 互相取消。
  6. 发布提交由机器人推送，若不跳过会再次触发 CI（甚至再次发布），形成循环。
