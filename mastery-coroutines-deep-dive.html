D2 · 协程与 Flow 深水区 ​

第二部「精通专题」第二篇。目标不是再讲一遍 launch/async，而是把「背压、并发控制、取消语义、回调适配、Java 互操作、可观测性」这些上线后才会咬人的问题讲透。基础语法见 第 2 章 2.2~2.4。

D2.0 谁该读，解决什么痛点 ​

读者典型痛点读完能做什么
后端工程师下游慢导致内存暴涨；限流写在网关但服务内部仍打爆 DB按数据语义选背压策略，用 Semaphore 做进程内限流
Android 工程师collectLatest 取消了写库；旋转屏后事件重放区分 UI 流与业务流，正确使用 stateIn/shareIn
平台/架构师协程与 Reactor/Servlet 异步混用，取消不传播设计桥接层，统一取消与异常语义
测试/运维协程相关 Bug 无法复现，日志无线程上下文用虚拟时间测试 + CoroutineName/MDC 定位

一句话心智模型：协程解决「怎么并发」，Flow 解决「数据怎么流动」，Job 解决「什么时候停」。三者混在一起谈，就会写出「能跑但不可维护」的并发代码。

三条线各自有独立的「正确性标准」：

  1. 结构正确：任何协程都能追溯到父作用域，没有 GlobalScope 泄漏。
  2. 数据正确：该丢的丢、该留的留，下游看到的数据语义与业务预期一致。
  3. 资源正确：取消/超时/异常路径下，连接、监听器、文件句柄都被释放。

D2.2 背压：先定义数据语义，再选操作符 ​

背压不是「加个 buffer 就完事」。先回答一个问题：这类数据丢了会怎样？

mermaid
flowchart LR
    Q{丢了会怎样?} -- 业务事故 --> K[不能丢<br/>buffer / 有界队列 + 降级]
    Q -- 只影响体验 --> L{只要最新?}
    L -- 是 --> M[conflate]
    L -- 旧处理应作废 --> N[collectLatest]
    Q -- 只用于观测 --> O[sample / debounce]

操作符语义下游看到的数据代价
buffer(capacity)流水线化，不丢全量内存（容量 × 元素大小）
conflate()合并，只留最新跳跃的序列中间状态丢失
collectLatest {}新值取消旧处理最终一致下游必须可取消
sample(ms)定时取样稀疏序列间隔内数据丢失
debounce(ms)静默期后取最后一个稳定值增加延迟

对照实验（完整代码见示例）：

examples/coroutines/BackpressureDemo.kt可在线运行
kotlin
// 文件: BackpressureDemo.kt —— buffer / conflate / collectLatest / sample 的丢弃与合并策略
// 配套章节：02-kotlin-advanced.md 2.4「背压与缓冲策略」、mastery-coroutines-deep-dive.md D2.2
// 依赖：kotlinx-coroutines-core 1.9.0
// 运行：见同目录 README.md

import kotlinx.coroutines.*
import kotlinx.coroutines.flow.*

// 上游：每 20ms 产出一个编号；下游故意慢（每个处理 80ms）
private fun source(): Flow<Int> = flow {
    repeat(4) { i ->
        println("  上游发射 $i")
        emit(i)
        delay(20)
    }
}

private suspend fun slowCollect(name: String, flow: Flow<Int>) {
    println("【$name】")
    val start = System.currentTimeMillis()
    val received = mutableListOf<Int>()
    flow.collect { i ->
        delay(80)                       // 模拟下游慢处理
        received += i
        println("  下游处理完 $i")
    }
    println("  收到=$received，耗时=${System.currentTimeMillis() - start}ms\n")
}

@OptIn(FlowPreview::class)
fun main(): Unit = runBlocking {
    // ① 默认 collect：上下游串行，上游必须等下游处理完才能继续发射
    slowCollect("默认 collect（无缓冲）", source())

    // ② buffer：上下游流水线化，上游不必等下游；下游仍然一个不落地处理全部元素
    slowCollect("buffer(64)", source().buffer(64))

    // ③ conflate：缓冲只保留「最新一个」，中间值被丢弃（适合只要最新状态的场景）
    slowCollect("conflate", source().conflate())

    // ④ collectLatest：新值到来时取消上一次尚未完成的收集（适合搜索框、UI 刷新）
    println("【collectLatest】")
    val seen = mutableListOf<Int>()
    source().collectLatest { i ->
        seen += i
        delay(80)                       // 被下一个值打断时，这里不会打印「处理完」
        println("  下游处理完 $i（未被取消）")
    }
    println("  触发过的值=$seen（后面的被取消，只有最后一个能完成）\n")

    // ⑤ sample：按固定采样间隔取值，间隔内的元素直接丢弃（适合监控指标上报）
    println("【sample(50ms)】")
    source().sample(50).collect { println("  采样到 $it") }
}

选型结论：

  • 账务、订单、审计：默认 collect 或 buffer，绝不 conflate。
  • 行情、进度、定位：conflate，下游只渲染最新状态。
  • 搜索联想、地图重绘：collectLatest，并确保下游没有不可取消的副作用。
  • 指标上报：sample；UI 输入校验：debounce。

⚠️ buffer 只是把「阻塞」换成「内存」。有界缓冲 + BufferOverflow.DROP_OLDEST + 丢弃计数指标，才是生产可用组合。

D2.3 并发控制：Mutex / Semaphore / limitedParallelism ​

问题工具检查方式
共享可变状态被并发修改Mutex.withLock单测断言最终值 = 期望值
同时打到下游的请求太多Semaphore(n).withPermit埋点统计峰值在途数 ≤ n
CPU 密集任务打满调度器limitedParallelism(n)统计峰值并行线程数 ≤ n
需要「同一 key 串行」Mutex Map / SharedFlow 分组压测观察同 key 顺序
examples/coroutines/ConcurrencyControlDemo.kt可在线运行
kotlin
// 文件: ConcurrencyControlDemo.kt —— Mutex / Semaphore / limitedParallelism 的并发度控制
// 配套章节：02-kotlin-advanced.md 2.4「并发度与限流」、mastery-coroutines-deep-dive.md D2.3
// 依赖：kotlinx-coroutines-core 1.9.0
// 运行：见同目录 README.md

import kotlinx.coroutines.*
import kotlinx.coroutines.sync.*
import java.util.concurrent.atomic.AtomicInteger
import kotlin.system.measureTimeMillis

@OptIn(ExperimentalCoroutinesApi::class)
fun main(): Unit = runBlocking(Dispatchers.Default) {
    // ① Mutex：互斥访问共享可变状态。注意 Mutex 是「挂起锁」，不会阻塞线程
    var counter = 0
    val mutex = Mutex()
    coroutineScope {
        repeat(100) {
            launch {
                mutex.withLock {
                    counter++                     // 临界区：同一时刻只有一个协程进入
                }
            }
        }
    }
    println("① Mutex 保护后的计数 = $counter（期望 100）")

    // ② Semaphore：限制同时进行的数量，适合「最多 N 个并发请求」的闸门
    val semaphore = Semaphore(permits = 3)
    val running = AtomicInteger()
    val peak = AtomicInteger()
    val elapsed = measureTimeMillis {
        coroutineScope {
            repeat(12) {
                launch {
                    semaphore.withPermit {
                        val now = running.incrementAndGet()
                        peak.updateAndGet { p -> maxOf(p, now) }
                        delay(60)                 // 模拟一次外部调用
                        running.decrementAndGet()
                    }
                }
            }
        }
    }
    println("② Semaphore(3)：峰值并发 = ${peak.get()}（期望 ≤ 3），耗时 = ${elapsed}ms")

    // ③ limitedParallelism：限制「真正占线程的并行度」，适合 CPU 密集型分段
    //    注意：它限制的是同时运行的线程数，不是「在途协程数」——delay 挂起的协程不占线程
    val cpuDispatcher = Dispatchers.Default.limitedParallelism(2)
    val cpuRunning = AtomicInteger()
    val cpuPeak = AtomicInteger()
    coroutineScope {
        repeat(8) {
            launch(cpuDispatcher) {
                val now = cpuRunning.incrementAndGet()
                cpuPeak.updateAndGet { p -> maxOf(p, now) }
                val deadline = System.nanoTime() + 30_000_000
                while (System.nanoTime() < deadline) {   // 忙等 30ms，真实占住线程
                    // 模拟 CPU 工作
                }
                cpuRunning.decrementAndGet()
            }
        }
    }
    println("③ limitedParallelism(2)：峰值并行数 = ${cpuPeak.get()}（期望 ≤ 2）")

    // ④ 选型提示：Mutex 保护「状态」，Semaphore 限制「同时进行的任务数」（含挂起中的任务），
    //    limitedParallelism 划出「专属线程并发度」；三者语义不同，不要互相替代。
}

三个易错点：

  1. Semaphore 限制的是「在途任务」，limitedParallelism 限制的是「占线程任务」。delay 期间协程不占线程，用线程数评估限流会低估压力。
  2. Mutex 不可重入，嵌套 withLock 会死锁；需要重入时用 ReentrantLock 并接受阻塞线程。
  3. 不要在 withLock 里做慢 IO。锁只保护「状态变更」的几行代码，IO 放锁外。

D2.4 取消与清理：企业级资源安全 ​

取消是协作式的，且清理代码本身也可能被取消。三层防线：

    B --> C[try/finally]
    C --> D{清理里有挂起调用?}
    D -- 是 --> E[withContext NonCancellable]
    D -- 否 --> F[同步释放]
    E --> G[关闭连接 / flush / 提交]
    F --> G
    G --> H[Job 进入 Cancelled]

// 文件: CancellationCleanupDemo.kt —— withTimeoutOrNull / NonCancellable / ensureActive / finally
// 配套章节：02-kotlin-advanced.md 2.3「取消与资源清理」、mastery-coroutines-deep-dive.md D2.4
// 依赖：kotlinx-coroutines-core 1.9.0
// 运行：见同目录 README.md

import kotlinx.coroutines.*

suspend fun fetchWithDeadline(): String? = withTimeoutOrNull(100) {
    delay(300)                                        // 超时后抛 TimeoutCancellationException 并被吞掉
    "远端结果"
}

/** 用 finally + NonCancellable 保证清理动作一定执行完（关闭连接、提交偏移量、flush 日志）。 */
suspend fun useResource(job: Job) {
    try {
        repeat(100) { i ->
            currentCoroutineContext().ensureActive()   // 协作式取消：在循环里主动检查，避免「不理取消」
            delay(10)
            if (i == 3) job.cancel()                  // 模拟外部取消
        }
    } finally {
        withContext(NonCancellable) {                 // 已取消的上下文里仍能执行挂起清理
            delay(50)                                 // 模拟关闭连接需要时间
            println("  finally：资源已释放（NonCancellable 保证完成）")
        }
    }
}

fun main(): Unit = runBlocking {
    println("① withTimeoutOrNull(100ms)：结果 = ${fetchWithDeadline()}（超时返回 null，不抛异常）")

    println("② 协作式取消 + finally 清理：")
    val job = launch { useResource(coroutineContext[Job]!!) }
    job.join()
    println("   job 状态 = ${job.isCancelled}（期望 true）")

    println("③ 对比：取消后直接做挂起清理会被立即中断")
    val badJob = launch {
        try {
            delay(1000)
        } finally {
            delay(50)                             // ❌ 已取消，这里会立刻抛 CancellationException
            println("  这行通常不会执行")
        }
    }
    delay(50)
    badJob.cancelAndJoin()
    println("   结论：清理动作里有挂起调用时，必须包在 withContext(NonCancellable) 里")
}

企业检查清单：

  • [ ] 所有外部调用都有超时（withTimeoutOrNull 或客户端级 timeout）。
  • [ ] finally 里的挂起清理包在 withContext(NonCancellable)。
  • [ ] 长循环每轮 currentCoroutineContext().ensureActive()。
  • [ ] catch (Throwable) 前先重新抛出 CancellationException。
  • [ ] 取消路径有日志与指标（cancelled_total），能区分「用户取消」与「超时」。

⚠️ 事务边界要特别小心：提交放 NonCancellable，回滚不要放在可能被取消的 finally 里；否则会出现「钱扣了但订单没生成」。

D2.5 回调与 Channel：把旧世界接进 Flow ​

callbackFlow 的关键不是 callbackFlow 本身，而是 awaitClose——它定义了「收集结束时如何反注册」。缺了它，就是内存泄漏。

examples/coroutines/CallbackFlowDemo.kt可在线运行
kotlin
// 文件: CallbackFlowDemo.kt —— 用 callbackFlow / channelFlow 把回调与阻塞 API 适配成 Flow
// 配套章节：02-kotlin-advanced.md 2.4「回调适配」、mastery-coroutines-deep-dive.md D2.5
// 依赖：kotlinx-coroutines-core 1.9.0
// 运行：见同目录 README.md

import kotlinx.coroutines.*
import kotlinx.coroutines.channels.awaitClose
import kotlinx.coroutines.flow.*

/** 一个典型的老式回调 API：注册监听、返回取消句柄。 */
private class LegacyTimer {
    private var listener: ((Int) -> Unit)? = null

    fun start(onTick: (Int) -> Unit) {
        listener = onTick
    }

    fun stop() {
        listener = null
    }

    fun tick(value: Int) {
        listener?.invoke(value)
    }
}

/** callbackFlow：把「注册/反注册」型回调变成冷流；awaitClose 保证收集结束一定反注册。 */
private fun timerFlow(timer: LegacyTimer): Flow<Int> = callbackFlow {
    val callback: (Int) -> Unit = { value -> trySend(value) }  // 回调里只能用 trySend / trySendBlocking
    timer.start(callback)
    awaitClose { timer.stop() }                       // 收集者取消或结束时执行清理
}

/** channelFlow：需要并发 emit（多个子协程同时产出）时用它，emit 线程安全。 */
private fun mergedFlow(): Flow<String> = channelFlow {
    launch { send("来自协程 A") }
    launch { send("来自协程 B") }
}

fun main(): Unit = runBlocking {
    val timer = LegacyTimer()

    // 模拟外部驱动：另一个协程给 timer 打点（真实场景是传感器/消息队列回调）
    val tickerJob = launch(Dispatchers.Default) {
        repeat(5) { i ->
            delay(20)
            timer.tick(i)
        }
    }

    // ① callbackFlow：收集 3 个事件后主动结束，awaitClose 会把监听反注册
    val ticks = timerFlow(timer).take(3).toList()
    println("① callbackFlow 收到 3 个事件：$ticks")
    tickerJob.join()

    // ② channelFlow：多个生产者并发发送，顺序不保证但不会丢
    val merged = mergedFlow().toList()
    println("② channelFlow 合并结果：$merged")

    // ③ 关键区别：
    //    callbackFlow 用于「适配回调」，awaitClose 是资源释放的生命线；
    //    channelFlow 用于「构建期并发发送」，内部自带缓冲区与结构化并发。
}

D2.6 互操作：CompletableFuture / Reactor ​

examples/coroutines/InteropDemo.kt可在线运行

// 文件: InteropDemo.kt —— CompletableFuture ↔ suspend 双向互操作（不引入额外 jar）
// 配套章节：02-kotlin-advanced.md 2.4「与 Java 异步 API 互操作」、mastery-coroutines-deep-dive.md D2.6
// 依赖：kotlinx-coroutines-core 1.9.0（JDK8 的 future 扩展在 kotlinx-coroutines-jdk8，本例手写桥接以避免额外依赖）
// 运行：见同目录 README.md

import kotlinx.coroutines.*
import java.util.concurrent.CompletableFuture
import kotlin.coroutines.resume
import kotlin.coroutines.resumeWithException

/** CompletableFuture → suspend：挂起点等 Java 异步结果，取消时同步取消底层任务。 */
suspend fun <T> CompletableFuture<T>.awaitResult(): T = suspendCancellableCoroutine { cont ->
    whenComplete { value, error ->
        if (error == null) cont.resume(value) else cont.resumeWithException(error)
    }
    cont.invokeOnCancellation { cancel(true) }       // 协程被取消 → 底层任务也取消
}

/** suspend → CompletableFuture：把协程结果交给只认 CF 的老代码（如 Servlet 异步、第三方 SDK）。 */
fun <T> CoroutineScope.futureOf(block: suspend CoroutineScope.() -> T): CompletableFuture<T> {
    val result = CompletableFuture<T>()
    launch {
        try {
            result.complete(block())
        } catch (t: Throwable) {
            result.completeExceptionally(t)
        }
    }
    return result
}

// 模拟一个还在用 CompletableFuture 的老 SDK
private fun legacyLookup(id: String): CompletableFuture<String> =
    CompletableFuture.supplyAsync {
        Thread.sleep(80)                            // 阻塞式实现，发生在 ForkJoinPool 线程
        "用户-$id"
    }

private suspend fun loadUser(id: String): String {
    val name = legacyLookup(id).awaitResult()       // 挂起等待，业务代码保持顺序可读
    return "$name（由 ${Thread.currentThread().name} 恢复）"
}

fun main(): Unit = runBlocking {
    // ① CompletableFuture → suspend
    println("① awaitResult：${loadUser("1001")}")

    // ② suspend → CompletableFuture，再挂起等它完成（非协程线程则可用 get()/thenApply）
    val cf = futureOf { loadUser("1002") }
    println("② futureOf + awaitResult：${cf.awaitResult()}")

    // ③ 异常也要能跨边界传递
    val failed = CompletableFuture<String>().apply {
        completeExceptionally(IllegalArgumentException("下游 404"))
    }
    try {
        failed.awaitResult()
    } catch (e: Exception) {
        println("③ 异常透传：${e.message}")
    }

    // ④ 线程提醒：suspend 恢复线程由 CF 的完成线程决定，跨线程访问 UI/ThreadLocal 时必须 withContext
    println("   main 结尾线程：${Thread.currentThread().name}")
}

D2.7 调试：从「线程名」到「协程 dump」 ​

examples/coroutines/DebuggingDemo.kt可在线运行
kotlin
// 文件: DebuggingDemo.kt —— CoroutineName / 调试模式 / 协程结构观察
// 配套章节：02-kotlin-advanced.md 2.3「命名与调试」、mastery-coroutines-deep-dive.md D2.7
// 依赖：kotlinx-coroutines-core 1.9.0
// 运行：见同目录 README.md；建议加 -Dkotlinx.coroutines.debug=on 观察线程名
//       （kotlinc/java 直跑：java -Dkotlinx.coroutines.debug=on -cp ... DebuggingDemoKt）

import kotlinx.coroutines.*

suspend fun stage(name: String, block: suspend () -> Unit) {
    // CoroutineName 会进入协程上下文，调试模式下出现在线程名里，日志里也能取到
    withContext(CoroutineName(name)) {
        println("  当前协程名 = ${coroutineContext[CoroutineName]?.name}，线程 = ${Thread.currentThread().name}")
        block()
    }
}

fun main(): Unit = runBlocking {
    println("① CoroutineName 让日志可读（线程名是否带 @名称 取决于调试模式）")
    stage("拉取用户") { delay(30) }
    stage("拉取订单") { delay(30) }

    println("\n② 协程上下文可以直接打印，Job 的 toString 在调试模式下会包含状态")
    val job = launch(CoroutineName("后台同步")) {
        delay(100)
    }
    println("  job = $job")
    println("  父 Job = ${coroutineContext[Job]}")
    job.join()

    println("\n③ 用 CoroutineStart.LAZY 观察「已创建未启动」状态")
    val lazyJob = launch(start = CoroutineStart.LAZY, context = CoroutineName("懒启动")) {
        println("  懒启动协程真正执行了")
    }
    println("  启动前 isActive = ${lazyJob.isActive}")
    lazyJob.start()
    lazyJob.join()

    println("\n④ 企业排障顺序：先看线程名里的协程名 → 再看 Job 树 → 最后用 -Dkotlinx.coroutines.debug 复现")
    println("   需要完整 dump 时引入 kotlinx-coroutines-debug，调用 DebugProbes.dumpCoroutines()")
}

D2.9 协程 vs 虚拟线程：选型矩阵 ​

场景推荐理由
新 Kotlin 服务（Ktor/Spring WebFlux）协程 + Flow取消、背压、结构化并发一等公民
存量阻塞式 Servlet + JDBC虚拟线程零改造提升吞吐，风险最低
Android协程主线程调度、生命周期感知
CPU 密集计算固定线程池 / limitedParallelism虚拟线程与协程都不提速
需要限流的资源Semaphore + 协程虚拟线程没有池化语义
  • ✅ 两者可以共存：在虚拟线程里调用协程时显式指定 Dispatchers.IO，不要在虚拟线程上再套一层默认调度。
  • ⚠️ 虚拟线程的取消是 interrupt，不具备父子传播；跨边界的取消要自己设计。

D2.10 企业级反模式清单 ​

反模式后果修法
GlobalScope.launch泄漏、无法取消注入受控 CoroutineScope
在 async 内部吞异常await 收不到失败让异常进 Deferred
collectLatest 里写库数据不一致改为普通 collect + buffer
