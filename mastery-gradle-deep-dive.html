Gradle 精通：Provider API / BuildService / Worker API / TestKit / 远程构建缓存 ​

面向读者：已经能写 build.gradle.kts、维护多模块工程，但一遇到「配置缓存报错、插件没法测、构建慢」就靠猜的工程师。

  • 配置阶段只应该「登记意图」：任务叫什么、输入输出是什么、值从哪里来。
  • 执行阶段才「取值/读写」：Provider 在这里 get()，文件在这里创建。
  • 配置缓存（Configuration Cache）缓存的正是配置阶段的产物；一旦执行阶段回头访问 Project，缓存就无法序列化。

一句话：Provider 是配置阶段写给执行阶段的「提货单」。

D1.1 Provider / Property API：把「值」变成可延迟、可追踪的对象 ​

为什么需要 Provider ​

传统写法在配置阶段就把值算死：

kotlin
// ❌ 立即取值：路径、版本、环境变量都固定了，Gradle 无法延迟解析
val outputDir = File(project.buildDir, "generated")
tasks.register("generate") {
    doLast { outputDir.mkdirs() }
}

Provider 写法只登记「怎么算」，真正取值推迟到执行阶段：

kotlin
// ✅ 延迟取值：配置缓存可序列化，输入变化可被 Gradle 追踪
val outputDir = layout.buildDirectory.dir("generated")
tasks.register("generate") {
    val dir = outputDir
    outputs.dir(dir)
    doLast {
        dir.get().asFile.mkdirs()
    }
}

五个最常用的 Provider 入口 ​

API用途示例
providers.gradleProperty("x")读取 -Px=... / gradle.properties版本号、开关
providers.environmentVariable("CI")读取环境变量，并作为可追踪输入CI 判断

layout.projectDirectory.file("x")延迟解析源码/配置路径输入文件

组合：map / flatMap / orElse / conventions ​

kotlin
val version = providers.gradleProperty("app.version").orElse("0.0.0")
val isSnapshot = version.map { it.endsWith("-SNAPSHOT") }
val artifactName = version.map { "demo-$it.jar" }

val reportDir = layout.buildDirectory.dir("reports")
val reportFile = reportDir.flatMap { it.file("summary.txt") }

操作语义常见误用
map对值做纯转换，不关心来源在 lambda 里访问 project，配置缓存失败
flatMap值本身也是一个 Provider用 map 返回 Provider，得到嵌套 Provider
orElse提供默认值默认值里做 IO/网络
conventions设置「约定值」，可被显式值覆盖与 orElse 混用导致优先级混乱
get()立即取值在配置阶段对未知值调用，触发提前解析

插件本体：用 providers.gradleProperty 读取参数，用 tasks.register 延迟注册任务。

// 文件: build-logic/convention/src/main/kotlin/shop/HelloPlugin.kt
// 最小自定义插件：用于演示 TestKit / GradleRunner 单测（正文 3.8 与专题 D1）
package shop

import org.gradle.api.Plugin
import org.gradle.api.Project

class HelloPlugin : Plugin<Project> {
    override fun apply(target: Project) {
        target.tasks.register("hello") {
            group = "shop"
            description = "打印问候语，验证插件被正确加载"

            // Provider API：值在配置阶段登记、执行阶段才取，兼容配置缓存
            val message = target.providers
                .gradleProperty("hello.message")
                .orElse("Hello from shop.hello")

            doLast {
                println(message.get())
            }
        }
    }
}

跨任务共享状态：任务只持有 Property<BuildSummaryService>，真正的计数器在 BuildService 里。

examples/gradle-demo/build-logic/convention/src/main/kotlin/shop/BuildSummaryService.kt

// 文件: build-logic/convention/src/main/kotlin/shop/BuildSummaryService.kt
// BuildService 示例：跨任务共享状态，构建结束时统一输出（兼容配置缓存）
package shop

import org.gradle.api.DefaultTask
import org.gradle.api.provider.Property
import org.gradle.api.services.BuildService
import org.gradle.api.services.BuildServiceParameters
import org.gradle.api.tasks.Internal
import org.gradle.api.tasks.TaskAction
import java.util.concurrent.atomic.AtomicInteger

interface BuildSummaryParameters : BuildServiceParameters {
    val prefix: Property<String>
}

abstract class BuildSummaryService : BuildService<BuildSummaryParameters>, AutoCloseable {
    private val recorded = AtomicInteger(0)

    fun record(taskPath: String) {
        val total = recorded.incrementAndGet()
        println("[${parameters.prefix.get()}] recorded $taskPath (total=$total)")
    }

    override fun close() {
        println("[${parameters.prefix.get()}] build summary: ${recorded.get()} task(s)")
    }
}

abstract class BuildSummaryTask : DefaultTask() {

    // BuildService 不是任务输入，必须标 @Internal，避免被当作文件/属性快照
    @get:Internal
    abstract val summary: Property<BuildSummaryService>

    @TaskAction
    fun printSummary() {
        val service = summary.get()
        service.record(path)
        logger.lifecycle("BuildService 已记录 $path；构建结束时输出汇总")
    }
}

D1.2 BuildService：跨任务共享状态，而不是全局变量 ​

它解决什么问题 ​

有些状态必须跨任务共享：统计构建指标、维护数据库连接池、限制并发下载。用 object 单例在 Gradle 里有三个问题：

  1. 类加载器隔离，多个构建可能拿到不同实例。
  2. 配置缓存无法感知生命周期。
  3. 没有统一的关闭钩子，资源容易泄漏。

BuildService 是 Gradle 官方的「构建级共享服务」：

  • 由 Gradle 管理生命周期；
  • 支持参数（BuildServiceParameters）；
  • 支持并发限制（maxParallelUsages）；
  • 构建结束时自动 close()；
  • 可以被任务通过 Provider 引用，兼容配置缓存。

参数、并发与生命周期 ​

能力写法说明
参数interface Params : BuildServiceParameters { val prefix: Property<String> }注册时 parameters.prefix.set(...)
限制并发registerIfAbsent(..., maxParallelUsages = 1)适合数据库连接、限流器

取消感知实现 OperationCompletionListener构建取消时清理

⚠️ BuildService 不是「任务间传值」的捷径。它适合共享基础设施（连接池、计数器、限流器），不适合传递业务数据；业务数据应该走任务输入/输出。

D1.3 Worker API：把重活从任务动作里搬出去 ​

为什么不在 doLast 里直接干 ​

直接在任务动作里做 CPU/IO 重活有三个问题：

  1. 阻塞任务执行线程，并行度上不去。
  2. 难以控制隔离级别（类加载、进程、内存）。
  3. 配置缓存/增量构建无法感知工作单元。

Worker API 把工作提交给 Gradle 的 Worker 执行器，由 Gradle 统一调度：

隔离级别 ​

级别API隔离内容适用场景
无隔离noIsolation()只隔离线程工作类已在构建类路径，追求最低开销
类加载器隔离classLoaderIsolation()独立 ClassLoader需要不同依赖版本的工具
进程隔离processIsolation()独立 JVM 进程需要隔离内存/系统属性/崩溃风险

最小实现 ​

examples/gradle-demo/build-logic/convention/src/main/kotlin/shop/SourceDigestTask.kt
kotlin
// 文件: build-logic/convention/src/main/kotlin/shop/SourceDigestTask.kt
// Worker API 示例：把 CPU/IO 工作提交到 Gradle Worker，隔离任务执行与线程管理
package shop

import org.gradle.api.DefaultTask
import org.gradle.api.file.ConfigurableFileCollection
import org.gradle.api.file.RegularFileProperty
import org.gradle.api.tasks.InputFiles
import org.gradle.api.tasks.OutputFile
import org.gradle.api.tasks.PathSensitive
import org.gradle.api.tasks.PathSensitivity
import org.gradle.api.tasks.TaskAction
import org.gradle.workers.WorkAction
import org.gradle.workers.WorkParameters
import org.gradle.workers.WorkerExecutor
import java.security.MessageDigest
import javax.inject.Inject

abstract class SourceDigestTask : DefaultTask() {

    @get:InputFiles
    @get:PathSensitive(PathSensitivity.RELATIVE)
    abstract val sources: ConfigurableFileCollection

    @get:OutputFile
    abstract val digestFile: RegularFileProperty

    @get:Inject
    abstract val workers: WorkerExecutor

    @TaskAction
    fun submit() {
        // 不要在任务动作里直接做重活：提交给 Worker，由 Gradle 管理隔离与并行
        workers.noIsolation().submit(DigestWork::class.java) {
            files.from(sources)
            output.set(digestFile)
        }
    }
}

interface DigestParameters : WorkParameters {
    val files: ConfigurableFileCollection
    val output: RegularFileProperty
}

abstract class DigestWork : WorkAction<DigestParameters> {
    override fun execute() {
        val digest = MessageDigest.getInstance("SHA-256")
        parameters.files.files
            .filter { it.isFile }
            .sortedBy { it.name }
            .forEach { file ->
                digest.update(file.name.toByteArray())
                digest.update(file.readBytes())
            }
        val hash = digest.digest().joinToString("") { "%02x".format(it) }
        val out = parameters.output.get().asFile
        out.parentFile.mkdirs()
        out.writeText(hash)
    }
}

关键点：

  1. WorkParameters 里只放 ConfigurableFileCollection、Property、RegularFileProperty 等可序列化类型。
  2. WorkAction 里不要访问 Project/Task，只通过 parameters 读。

// 文件: build-logic/convention/src/test/kotlin/shop/HelloPluginTest.kt
// TestKit 单测：在临时工程里真实执行 Gradle，验证插件行为而不是只测普通函数
package shop

import org.gradle.testkit.runner.GradleRunner
import org.gradle.testkit.runner.TaskOutcome
import org.junit.jupiter.api.Assertions.assertEquals
import org.junit.jupiter.api.Assertions.assertTrue
import org.junit.jupiter.api.Test
import org.junit.jupiter.api.io.TempDir
import java.io.File

class HelloPluginTest {

    @TempDir
    lateinit var projectDir: File

    private fun writeBuild(script: String) {
        File(projectDir, "settings.gradle.kts").writeText("rootProject.name = \"hello-plugin-test\"")
        File(projectDir, "build.gradle.kts").writeText(script)
    }

    @Test
    fun `hello task prints default message`() {
        writeBuild("plugins { id(\"shop.hello\") }")

        val result = GradleRunner.create()
            .withProjectDir(projectDir)
            .withArguments("hello", "--stacktrace")
            .withPluginClasspath()
            .build()

        assertEquals(TaskOutcome.SUCCESS, result.task(":hello")?.outcome)
        assertTrue(result.output.contains("Hello from shop.hello"))
    }

    @Test
    fun `hello task reads gradle property via Provider API`() {
        writeBuild("plugins { id(\"shop.hello\") }")

        val result = GradleRunner.create()
            .withProjectDir(projectDir)
            // Tooling API 不接受自定义 --option，项目属性统一用 -P 传递
            .withArguments("-Phello.message=Bonjour Gradle", "hello", "--stacktrace")
            .withPluginClasspath()
            .build()

        assertEquals(TaskOutcome.SUCCESS, result.task(":hello")?.outcome)
        assertTrue(result.output.contains("Bonjour Gradle"))
    }
}

层级测什么工具

D1.5 远程构建缓存：跨机器复用任务输出 ​

与「挂载 caches 目录」的区别 ​

维度挂载 ~/.gradle/caches远程构建缓存
共享范围同一 runner / 同一路径跨机器、跨 CI job、跨开发者
复用对象依赖 jar、wrapper、本地缓存任务输出（class、jar、测试结果）

命中率上不去，先查这五件事 ​

  1. 输入不稳定：时间戳、随机数、绝对路径、未声明的环境变量。
  2. 路径敏感度：跨机器路径不同，必须用 PathSensitivity.RELATIVE/NAME_ONLY。
  3. JDK 不一致：编译任务缓存键包含 JDK 版本，统一工具链。
  4. 依赖版本漂移：动态版本 1.+ 每次解析结果不同。
  5. 缓存键包含构建目录：把绝对路径写进输入，换机器必 miss。

安全红线 ​

  • 禁止把 fork PR / 未审阅分支的输出推送到共享缓存，防止缓存投毒。
  • 缓存服务必须 HTTPS + 认证；凭据走密钥管理，不进仓库。
  • 设置保留策略与容量上限，定期清理。
  • 监控命中率与缓存体积；命中率低于 30% 先查输入稳定性。

D1.7 企业落地检查清单 ​

  • [ ] 所有自定义任务使用 abstract val + Property/文件属性，不持有 Project。
  • [ ] 配置阶段不做网络/文件 IO；必须做时用 ValueSource 并缓存。
  • [ ] 插件有 TestKit 功能测试，覆盖「能应用」与「关键任务产物正确」。
  • [ ] 插件版本独立 SemVer，维护 Gradle/Kotlin/AGP 兼容矩阵。
  • [ ] CI 开启 --configuration-cache，问题清单清零后再 fail。
  • [ ] 远程构建缓存启用认证与 HTTPS，PR 构建不推送。
  • [ ] Build Scan 作为排障入口，关键路径与缓存命中率有基线。
  • [ ] 所有豁免（notCompatibleWithConfigurationCache、doNotCacheIf）有 owner 与到期时间。

现象先查常见修法
Configuration cache entry discarded报告里的第一个 problem修执行期 project 访问；升级插件

BuildService 不关闭是否实现 AutoCloseable在 close() 里释放资源

D1.9 实践任务 ​

  1. ★ 给 HelloPlugin 增加一个 helloFile 任务，把问候语写到 build/hello.txt，要求有 @OutputFile 且第二次执行 UP-TO-DATE。
  2. ★★ 给 SourceDigestTask 增加 classLoaderIsolation() 版本，说明什么场景必须用它。
  3. ★★ 为 shop.kotlin.jvm 写一个 TestKit 用例：临时工程应用插件后，断言 test 任务存在且使用 JUnit Platform。
  4. ★★★ 设计一套 CI 缓存策略：本地目录缓存 + 远程构建缓存 + TestKit 测试，写出各步骤命令与失败回滚方案。
参考答案（点击展开）
  1. 用 @get:OutputFile abstract val output: RegularFileProperty，在 @TaskAction 里 output.get().asFile.writeText(...)；Gradle 会基于输出快照判定 UP-TO-DATE。
  2. 需要加载不同版本依赖（例如同时支持两套 ASM/分析工具）时用 classLoaderIsolation()；进程隔离用于需要独立 JVM 内存/系统属性的场景。
  3. 用 GradleRunner.withPluginClasspath().withArguments("tasks", "--all")，断言输出包含 test；再断言 Test 任务配置了 useJUnitPlatform()（可通过自定义任务输出或测试执行结果验证）。
  4. 先挂载依赖目录缓存，再配置远程构建缓存并限制 PR 不推送；CI 先跑 check 再跑 TestKit；失败时保留缓存命中率与 Build Scan 链接，回滚到上一版缓存配置。
