D11 · 消息驱动与一致性 ​

第二部「精通专题」第十一篇。目标：把「业务写完、消息没发」和「消息发了、业务回滚」这两类事故， 变成结构上不可能发生，并用测试证明。示例工程：examples/backend-service。

D11.0 谁该读，解决什么问题 ​

读者典型痛点读完能做什么
后端架构师订单建了、库存没扣；对账天天对不上用 Outbox 把「业务 + 事件」放进同一个本地事务
中间件/消息团队消费者重复扣款、消息乱序用去重键 + 分区键设计幂等与顺序
值班同学死信堆积没人管，重放靠改库用状态机 + 重放接口 + 指标把处置流程固化
测试故障场景无法复现，「应该不会丢」用可控 Transport 注入失败并断言补发不重复

一句话：分布式事务没有银弹；能落地的是「本地事务保证不丢 + 至少一次投递 + 消费端幂等」， 三者组合后效果上等价于恰好一次。

失败模式现象根因解法
业务成功、消息丢失订单存在，下游永远收不到「先写库再发消息」，发消息失败后被忽略Outbox：事件与业务同事务落库，再由独立轮询补发
消息先发、业务回滚下游收到不存在的事件在事务内直接 kafkaTemplate.send禁止在事务内直发；只写 outbox
重复投递下游重复扣库存/发券至少一次语义 + 重试消费端 (consumer, event_id) 去重表
消息乱序取消事件先于创建事件多分区 / 并发消费用业务主键（orderId）作为 Kafka key，保证同键同分区

⚠️ 「在事务提交后 afterCommit 里发消息」仍有窗口：提交成功后进程崩溃，消息就没了。 Outbox 的价值是把「发送」从业务事务里挪出来，同时不丢事件。

要点：

  • event_id 唯一：事件身份只生成一次，重发复用同一个 id，消费端才有稳定的去重键。
  • idx_outbox_ready：轮询只扫 status='PENDING' AND next_attempt_at<=now，避免全表扫描。
  • DEAD 是一等状态：死信不是「删掉重来」，而是保留现场（last_error、attempts）等待人工或自动重放。
  • 真实项目再加 schema_version / trace_id 字段：前者用于 payload 演进，后者用于跨系统排障。

D11.3 同事务写入：强约束比约定可靠 ​

业务层只依赖 OrderEventPublisher 接口，实现类用 check 把「必须处于事务中」变成运行时硬约束：

// 文件: outbox/OrderEventPublisher.kt —— 事件模型 + Outbox 写入实现
// D8 只留接口；D11 用 Outbox 实现，业务层调用点不变。
package com.example.backend.outbox

import org.slf4j.LoggerFactory
import org.springframework.stereotype.Component
import org.springframework.transaction.support.TransactionSynchronizationManager
import com.example.backend.observability.TraceContextPropagation
import java.time.OffsetDateTime
import java.util.UUID

data class OrderEvent(
    val orderId: Long,
    val type: String,
    val occurredAt: OffsetDateTime,
    val payload: Map<String, String> = emptyMap(),
)

interface OrderEventPublisher {
    /** @return eventId，供消费端去重与排障关联 */
    fun publish(event: OrderEvent): String
}

@Component
class OutboxOrderEventPublisher(
    private val repository: OutboxRepository,
    private val properties: OutboxProperties,
) : OrderEventPublisher {

    private val log = LoggerFactory.getLogger(javaClass)

    override fun publish(event: OrderEvent): String {
        val eventId = UUID.randomUUID().toString()
        if (!properties.enabled) {
            log.info("outbox 未启用，事件仅记录 eventId={} type={} orderId={}", eventId, event.type, event.orderId)
            return eventId
        }
        // 强约束：必须与业务写在同一事务中，否则失去「业务提交必带事件」的原子性
        check(TransactionSynchronizationManager.isActualTransactionActive()) {
            "OrderEventPublisher.publish 必须在事务内调用：请把业务写入与 outbox 写入放进同一 TransactionTemplate"
        }
        // 业务事务内抓取当前 span 的 traceparent：事件投递后仍能把消费端接回同一条 trace
        val traceParent = TraceContextPropagation.currentTraceParent()
        repository.append(eventId, event, traceParent)
        log.info(
            "outbox 已落库（与业务同事务）eventId={} type={} orderId={} traceParent={}",
            eventId,
            event.type,
            event.orderId,
            traceParent,
        )
        return eventId
    }
}

    suspend fun create(command: CreateOrderCommand, channel: Channel): CreateOrderResult =
        observed("order.create", mapOf("idempotency.key" to command.idempotencyKey), channel) {
            repository.findByIdempotencyKey(command.idempotencyKey)?.let { existing ->
                return@observed CreateOrderResult(existing, replayed = true)
            }
            val id = try {
                transactionTemplate.execute {
                    val newId = repository.insert(command)
                    // D11：业务行与 outbox 行在同一事务提交——业务成功则事件必在，回滚则事件必不在
                    val now = OffsetDateTime.now(ZoneOffset.UTC)
                    eventPublisher.publish(
                        OrderEvent(
                            orderId = newId,
                            type = "ORDER_CREATED",
                            occurredAt = now,
                            payload = mapOf(
                                "customerId" to command.customerId,
                                "amountCents" to command.amountCents.toString(),
                            ),
                        ),
                    )
                    newId
                } ?: throw IllegalStateException("事务未返回主键")
            } catch (e: DuplicateKeyException) {
                // 另一个并发请求已经写入同一幂等键：事务已回滚，回读即可
                val existing = repository.findByIdempotencyKey(command.idempotencyKey)
                    ?: throw e
                return@observed CreateOrderResult(existing, replayed = true)
            }
            val created = repository.findById(id) ?: throw IllegalStateException("订单写入后不可见：$id")
            CreateOrderResult(created, replayed = false)
        }

    /** 取消订单：状态机 + 乐观并发（version 自增）；已取消返回 409 而不是静默成功。 */
    suspend fun cancel(id: Long, channel: Channel): Order =
        observed("order.cancel", mapOf("order.id" to id.toString()), channel) {
            val cancelled = transactionTemplate.execute {
                if (repository.cancel(id) == 0) {
                    val current = repository.findById(id) ?: throw OrderNotFoundException(id)
                    throw OrderStateConflictException(
                        if (current.status == OrderStatus.CANCELLED) "订单已取消：$id"
                        else "订单当前状态不允许取消：${current.status}",
                    )
                }
                val current = repository.findById(id) ?: throw OrderNotFoundException(id)
                // 取消事件同样与状态变更同事务写入 outbox
                eventPublisher.publish(
                    OrderEvent(
                        orderId = current.id,
                        type = "ORDER_CANCELLED",
                        occurredAt = current.updatedAt,
                        payload = mapOf("status" to current.status.name, "version" to current.version.toString()),
                    ),
                )
                current
            }
            cancelled ?: throw OrderNotFoundException(id)
        }

D11.4 轮询发布器：至少一次 + 指数退避 ​

examples/backend-service/src/main/kotlin/com/example/backend/outbox/OutboxRelay.kt可在线运行
kotlin
// 文件: outbox/OutboxRelay.kt —— 轮询发布器：至少一次投递 + 指数退避 + 死信
package com.example.backend.outbox

import io.micrometer.core.instrument.Counter
import io.micrometer.core.instrument.MeterRegistry
import io.opentelemetry.api.trace.Tracer
import org.slf4j.LoggerFactory
import org.springframework.scheduling.annotation.Scheduled
import org.springframework.stereotype.Component
import com.example.backend.observability.TraceContextPropagation
import java.time.OffsetDateTime
import java.time.ZoneOffset

@Component
class OutboxRelay(
    private val repository: OutboxRepository,
    private val transport: OrderEventTransport,
    private val properties: OutboxProperties,
    private val tracer: Tracer,
    meterRegistry: MeterRegistry,
) {
    private val log = LoggerFactory.getLogger(javaClass)
    private val published: Counter = meterRegistry.counter("shop_outbox_published_total")
    private val failed: Counter = meterRegistry.counter("shop_outbox_failed_total")
    private val dead: Counter = meterRegistry.counter("shop_outbox_dead_total")

    /**
     * 单轮投递。可被调度器调用，也可在测试里手动调用（确定性，不依赖 sleep）。
     * 「至少一次」：发送成功但标记失败（进程崩溃）会导致下一轮重发；
     * 消费端用 processed_events 去重，从而在效果上等价于「恰好一次」。
     */
    fun relayOnce(now: OffsetDateTime = OffsetDateTime.now(ZoneOffset.UTC)): Int {
        if (!properties.enabled) return 0
        val ready = repository.findReady(now, properties.batchSize)
        var success = 0
        for (event in ready) {
            try {
                sendWithTrace(event)
                if (repository.markPublished(event.id, now) > 0) published.increment()
                success++
            } catch (ex: Exception) {
                val attempts = event.attempts + 1
                val isDead = attempts >= properties.maxAttempts
                val next = if (isDead) now else now.plusNanos(backoffMillis(attempts) * 1_000_000)
                repository.markFailure(
                    id = event.id,
                    attempts = attempts,
                    nextAttemptAt = next,
                    error = ex.message,
                    status = if (isDead) OutboxStatus.DEAD else OutboxStatus.PENDING,
                )
                failed.increment()
                if (isDead) {
                    dead.increment()
                    log.error("事件进入死信 eventId={} attempts={} error={}", event.eventId, attempts, ex.message)
                } else {
                    log.warn(
                        "事件投递失败，将在 {} ms 后重试 eventId={} attempts={} error={}",
                        backoffMillis(attempts),
                        event.eventId,
                        attempts,
                        ex.message,
                    )
                }
            }
        }
        if (ready.isNotEmpty()) log.info("outbox 轮询：待发 {}，成功 {}", ready.size, success)
        return success
    }

    /** 发布端 span：父上下文来自落库时保存的 traceparent，与 HTTP 请求保持同一条 trace。 */
    private fun sendWithTrace(event: OutboxEvent) {
        val parent = TraceContextPropagation.extract(event.traceParent)
        val span = tracer.spanBuilder("outbox.publish")
            .setParent(parent)
            .setAttribute("event.id", event.eventId)
            .setAttribute("event.type", event.type)
            .setAttribute("order.id", event.orderId)
            .startSpan()
        try {
            transport.send(event)
        } finally {
            span.end()
        }
    }

    /** 指数退避：base * 2^(attempts-1)，封顶 backoffMaxMs，避免故障时打爆下游。 */
    internal fun backoffMillis(attempts: Int): Long {
        val exp = (attempts - 1).coerceIn(0, 20)
        val raw = properties.backoffBaseMs * (1L shl exp)
        return raw.coerceAtMost(properties.backoffMaxMs)
    }

    /** 死信重放：重置为 PENDING，下一轮 relay 补发。 */
    fun replayNow(id: Long) {
        val now = OffsetDateTime.now(ZoneOffset.UTC)
        if (repository.replay(id, now) == 0) {
            throw OutboxStateConflictException("重放失败：事件不是 DEAD 或不存在 id=$id")
        }
        log.info("死信已重置为待发 id={}", id)
    }

    @Scheduled(fixedDelayString = "\${shop.outbox.poll-interval-ms:500}")
    fun scheduledRelay() {
        if (properties.relayEnabled) relayOnce()
    }
}

    fun findReady(now: OffsetDateTime, limit: Int): List<OutboxEvent> =
        jdbc.query(
            """
            $SELECT_OUTBOX
            WHERE status = ? AND next_attempt_at <= ?
            ORDER BY id
            LIMIT ?
            """.trimIndent(),
            mapper,
            OutboxStatus.PENDING.name,
            now,
            limit,
        )

    fun findById(id: Long): OutboxEvent? =
        jdbc.query("$SELECT_OUTBOX WHERE id = ?", mapper, id).firstOrNull()

    fun list(status: OutboxStatus?, limit: Int): List<OutboxEvent> =
        if (status == null) {
            jdbc.query("$SELECT_OUTBOX ORDER BY id DESC LIMIT ?", mapper, limit)
        } else {
            jdbc.query("$SELECT_OUTBOX WHERE status = ? ORDER BY id DESC LIMIT ?", mapper, status.name, limit)
        }

    /** 幂等：只有仍为 PENDING 的行才能标记成功，重复轮询不会覆盖已发布时间。 */
    fun markPublished(id: Long, now: OffsetDateTime): Int =
        jdbc.update(
            "UPDATE outbox SET status = ?, published_at = ?, last_error = NULL WHERE id = ? AND status = ?",
            OutboxStatus.PUBLISHED.name,
            now,
            id,
            OutboxStatus.PENDING.name,
        )

    fun markFailure(
        id: Long,
        attempts: Int,
        nextAttemptAt: OffsetDateTime,
        error: String?,
        status: OutboxStatus,
    ): Int =
        jdbc.update(
            "UPDATE outbox SET status = ?, attempts = ?, next_attempt_at = ?, last_error = ? WHERE id = ? AND status = ?",
            status.name,
            attempts,
            nextAttemptAt,
            error?.take(500),
            id,
            OutboxStatus.PENDING.name,
        )

    /** 只允许重放 DEAD；重置次数与时间后由下一轮轮询补发。 */
    fun replay(id: Long, now: OffsetDateTime): Int =
        jdbc.update(
            "UPDATE outbox SET status = ?, attempts = 0, next_attempt_at = ?, last_error = NULL WHERE id = ? AND status = ?",
            OutboxStatus.PENDING.name,
            now,
            id,
            OutboxStatus.DEAD.name,

设计要点：

  1. 投递语义是至少一次：transport.send 成功、markPublished 之前进程崩溃 → 下一轮会重发。 这不是 bug，而是刻意选择；去重责任在消费端。
  2. 条件更新防重复标记：markPublished 带 AND status='PENDING'，并发/重复轮询不会把 published_at 反复覆盖。
  3. 退避：base * 2^(attempts-1)，封顶 backoffMaxMs。故障时避免把下游打挂，也避免把日志刷爆。
  4. 吞吐：LIMIT batchSize；单实例 @Scheduled(fixedDelay) 足够中小流量，高流量用多实例 + 行锁 （SELECT ... FOR UPDATE SKIP LOCKED）或独立的 relay 服务。
  5. 指标：shop_outbox_published_total / failed_total / dead_total，死信增长必须接告警。

真实 Kafka 场景的等价写法：把 transport.send 换成 KafkaTemplate.send(topic, orderId.toString(), payload)， 并 get(timeout) 等 broker ack；broker 不可用时抛异常 → 走同一套退避/死信逻辑。

D11.5 幂等消费：去重键放在事务里 ​

// 文件: outbox/OrderEventConsumerService.kt —— 幂等消费：processed_events 去重键
package com.example.backend.outbox

import com.example.backend.observability.TraceContextPropagation
import io.opentelemetry.api.trace.Tracer
import org.slf4j.LoggerFactory
import org.springframework.dao.DuplicateKeyException
import org.springframework.jdbc.core.JdbcTemplate
import org.springframework.stereotype.Service
import org.springframework.transaction.annotation.Transactional
import java.time.OffsetDateTime
import java.time.ZoneOffset

@Service
class OrderEventConsumerService(
    private val jdbc: JdbcTemplate,
    private val properties: OutboxProperties,
    private val tracer: Tracer,
) {
    private val log = LoggerFactory.getLogger(javaClass)

    /**
     * 至少一次投递下，同一事件可能到达多次；先用 (consumer, event_id) 主键占位，
     * 插入成功才执行业务处理。处理抛异常会连同去重行一起回滚，下一轮可重试。
     *
     * @return true=首次处理，false=重复投递已跳过
     */
    @Transactional
    fun consume(eventId: String, traceParent: String? = null, handler: () -> Unit): Boolean {
        val parent = TraceContextPropagation.extract(traceParent)
        val span = tracer.spanBuilder("event.consume")
            .setParent(parent)
            .setAttribute("event.id", eventId)
            .setAttribute("consumer", properties.consumerName)
            .startSpan()
        try {
            val inserted = try {
                jdbc.update(
                    "INSERT INTO processed_events (consumer, event_id, processed_at) VALUES (?, ?, ?)",
                    properties.consumerName,
                    eventId,
                    OffsetDateTime.now(ZoneOffset.UTC),
                ) > 0
            } catch (_: DuplicateKeyException) {
                false
            }
            if (!inserted) {
                log.info("重复事件已跳过 eventId={} consumer={}", eventId, properties.consumerName)
                return false
            }
            handler()
            return true
        } finally {
            span.end()
        }
    }
}

import com.fasterxml.jackson.databind.ObjectMapper

/**
 * 默认传输：追加 JSON Lines 到本地文件。
 * 为什么它是「可运行降级」：没有 Kafka broker 时仍能验证 Outbox → 发布 → 消费的完整链路；
 * 差异见 mastery-messaging-consistency.md：无分区、无副本、无消费组位点，仅适合单机演示。
 */
@Component
@ConditionalOnProperty(prefix = "shop.outbox", name = ["transport"], havingValue = "file", matchIfMissing = true)
class FileOrderEventTransport(private val properties: OutboxProperties) : OrderEventTransport {

    private val log = LoggerFactory.getLogger(javaClass)
    private val mapper = ObjectMapper()
    private val lock = Any()

    override fun send(event: OutboxEvent) {
        val path = Path.of(properties.filePath).toAbsolutePath()
        path.parent?.let { Files.createDirectories(it) }
        val line = mapper.writeValueAsString(
            mapOf(
                "eventId" to event.eventId,
                "orderId" to event.orderId,
                "type" to event.type,
                "payload" to event.payload,
                "traceParent" to event.traceParent,
                "sentAt" to java.time.OffsetDateTime.now().toString(),
            ),
        )
        synchronized(lock) {
            Files.writeString(path, line + System.lineSeparator(), StandardOpenOption.CREATE, StandardOpenOption.APPEND)
        }
        log.info("事件已写入文件总线 eventId={} path={}", event.eventId, path)
    }
}

    class ControllableTransport : OrderEventTransport {
        @Volatile
        var fail: Boolean = false
        val sent = CopyOnWriteArrayList<OutboxEvent>()

        override fun send(event: OutboxEvent) {
            if (fail) error("模拟事件总线不可用")
            sent += event

    @Autowired private lateinit var service: OrderService
    @Autowired private lateinit var relay: OutboxRelay
    @Autowired private lateinit var consumer: OrderEventConsumerService

        jdbc.update("DELETE FROM outbox")
        jdbc.update("DELETE FROM processed_events")
        jdbc.update("DELETE FROM orders")

    @Test
    fun `业务提交与 outbox 同事务写入，发布失败后补发且不重复`() = runBlocking {
        val created = service.create(
            CreateOrderCommand("cust-1", "book", 1000, "key-outbox-1"),
            Channel.WEB,
        )
        assertEquals(1, outbox.list(OutboxStatus.PENDING, 50).size, "业务成功后必须有一条待发事件")

        transport.fail = true

        assertEquals(0, relay.relayOnce(failedAt))
        val pending = outbox.list(OutboxStatus.PENDING, 50).single()

        assertNotNull(orders.findById(created.order.id), "投递失败不能影响已提交的业务数据")

        transport.fail = false
        val later = failedAt.plusSeconds(60)
        assertEquals(1, relay.relayOnce(later))
        val published = outbox.list(OutboxStatus.PUBLISHED, 50).single()
        assertEquals(OutboxStatus.PUBLISHED, published.status)
        assertNotNull(published.publishedAt)
        assertEquals(1, transport.sent.size)

        // 「发布器崩溃后再跑一轮」：markPublished 是条件更新，不会重复发送
        assertEquals(0, relay.relayOnce(later.plusSeconds(60)))
        assertEquals(1, transport.sent.size)

            Channel.WEB,

        assertEquals(OutboxStatus.PUBLISHED, outbox.findById(dead.id)?.status)
        assertEquals(1, transport.sent.size)
    }

    @Test
    fun `业务事务回滚时 outbox 事件一并回滚`() {
        val key = "key-outbox-rollback"
        runCatching {
            transactionTemplate.execute<Long> {

                        type = "ORDER_CREATED",

        assertEquals(0, jdbc.queryForObject("SELECT count(*) FROM outbox", Int::class.java))
    }

import jakarta.validation.constraints.Max

import org.springframework.web.bind.annotation.RequestMapping
import org.springframework.web.bind.annotation.RequestParam
import org.springframework.web.bind.annotation.RestController

data class OutboxResponse(
    val id: Long,
    val eventId: String,
    val orderId: Long,
    val type: String,
    val status: String,
    val attempts: Int,
    val nextAttemptAt: String,
    val lastError: String?,
    val publishedAt: String?,
    val traceParent: String?,
) {
    companion object {
        fun of(event: OutboxEvent) = OutboxResponse(
            id = event.id,
            eventId = event.eventId,
            orderId = event.orderId,
            type = event.type,
            status = event.status.name,
            attempts = event.attempts,
            nextAttemptAt = event.nextAttemptAt.toString(),
            lastError = event.lastError,
            publishedAt = event.publishedAt?.toString(),
            traceParent = event.traceParent,
        )
    }
}

@Validated
@RestController
@RequestMapping("/api/orders/outbox")
class OutboxController(
    private val repository: OutboxRepository,
    private val relay: OutboxRelay,
    private val reconciliation: OutboxReconciliationService,
) {

    /** 生产应仅对运维角色开放；这里沿用 orders:read scope，演示接口级授权。 */
    @GetMapping
    fun list(
        @RequestParam(required = false) status: OutboxStatus?,
        @RequestParam(defaultValue = "20") @Min(1) @Max(100) limit: Int,
    ): List<OutboxResponse> = repository.list(status, limit).map(OutboxResponse::of)

    /** 对账快照：积压量、最老 PENDING 年龄、DEAD、重复与消费缺口。 */
    @GetMapping("/reconciliation")
    fun reconciliation(): ReconciliationReport = reconciliation.report()

    /** 死信重放：只允许 DEAD → PENDING，下一轮轮询自动补发。 */
    @PostMapping("/{id}/replay")
    fun replay(@PathVariable id: Long): OutboxResponse {
        val event = repository.findById(id) ?: throw OutboxNotFoundException(id)
        if (event.status != OutboxStatus.DEAD) {
            throw OutboxStateConflictException("只有 DEAD 事件可以重放，当前状态=${event.status}")
        }
        relay.replayNow(id)
        return OutboxResponse.of(requireNotNull(repository.findById(id)))
    }
}

D11.8.1 对账任务与死信告警 ​

「发布成功」日志不能证明一致，还需要定期比对 outbox 状态与消费记录。OutboxReconciliationJob 默认每 30 秒输出一组指标，并提供按需查询接口：

指标 / 字段含义异常判定
shop.outbox.backlog / pendingCountPENDING 数量持续增长
shop.outbox.oldest.pending.age / oldestPendingAgeSeconds最老 PENDING 年龄（秒）> 300s → NOT_PUBLISHED、STUCK_PENDING
shop.outbox.dead.count / deadCountDEAD 数量> 0 → DEAD_LETTER
shop.outbox.consumed.gap / publishedNotConsumed已发布但无消费记录> 0 → MISSING_CONSUMPTION
shop.outbox.duplicate.events / duplicateEventGroups同 order_id + event_type 重复> 0 → DUPLICATE_EVENT
orphanConsumed消费记录指向不存在事件> 0 → ORPHAN_CONSUMPTION

三类异常对应关系：

  • 漏发 / 卡死：PENDING 超过阈值仍未发布 → NOT_PUBLISHED + STUCK_PENDING。
  • 重复：同一订单同一事件类型出现多条 → DUPLICATE_EVENT。
  • 消费缺口：已发布但消费端无记录，或消费记录找不到对应事件 → MISSING_CONSUMPTION / ORPHAN_CONSUMPTION。

// 文件: outbox/OutboxReconciliationService.kt —— D11 补全：Outbox 与消费记录对账
// 目标：用一组可查询的指标发现「漏发 / 重复 / 卡死 / 消费漏」四类一致性问题。
package com.example.backend.outbox

import org.springframework.jdbc.core.JdbcTemplate
import org.springframework.stereotype.Service
import java.time.Duration
import java.time.OffsetDateTime
import java.time.ZoneOffset

data class ReconciliationReport(
    val generatedAt: OffsetDateTime,
    val pendingCount: Long,
    /** 最老 PENDING 事件的年龄（秒）；没有 PENDING 时为 null。 */
    val oldestPendingAgeSeconds: Long?,
    val deadCount: Long,
    val publishedCount: Long,
    val consumedCount: Long,
    /** 已发布但消费端没有处理记录（消息丢失或消费端未启动）。 */
    val publishedNotConsumed: Long,
    /** 消费记录指向不存在的事件（脏数据或跨环境复用事件 ID）。 */
    val orphanConsumed: Long,
    /** 同一 order + eventType 出现多条事件（重复产生/重复发布）。 */
    val duplicateEventGroups: Long,
    val anomalies: List<String>,
) {
    val healthy: Boolean get() = anomalies.isEmpty()
}

@Service
class OutboxReconciliationService(
    private val jdbc: JdbcTemplate,
    private val properties: OutboxProperties,
) {

    fun report(now: OffsetDateTime = OffsetDateTime.now(ZoneOffset.UTC)): ReconciliationReport {
        val pendingCount = count("SELECT COUNT(*) FROM outbox WHERE status = ?", OutboxStatus.PENDING.name)
        val deadCount = count("SELECT COUNT(*) FROM outbox WHERE status = ?", OutboxStatus.DEAD.name)
        val publishedCount = count("SELECT COUNT(*) FROM outbox WHERE status = ?", OutboxStatus.PUBLISHED.name)
        val consumedCount = count(
            "SELECT COUNT(*) FROM processed_events WHERE consumer = ?",
            properties.consumerName,
        )

        val oldest = jdbc.query(
            "SELECT MIN(created_at) AS oldest FROM outbox WHERE status = ?",
            { rs, _ -> rs.getObject("oldest", OffsetDateTime::class.java) },
            OutboxStatus.PENDING.name,
        ).firstOrNull()
        val oldestAge = oldest?.let { Duration.between(it, now).seconds.coerceAtLeast(0) }

        val publishedNotConsumed = count(
            """
            SELECT COUNT(*) FROM outbox o
            WHERE o.status = ?
              AND NOT EXISTS (
                SELECT 1 FROM processed_events p
                WHERE p.consumer = ? AND p.event_id = o.event_id
              )
            """.trimIndent(),
            OutboxStatus.PUBLISHED.name,
            properties.consumerName,
        )

        val orphanConsumed = count(
            """
            SELECT COUNT(*) FROM processed_events p
            WHERE p.consumer = ?
              AND NOT EXISTS (SELECT 1 FROM outbox o WHERE o.event_id = p.event_id)
            """.trimIndent(),
            properties.consumerName,
        )

        val duplicateEventGroups = count(
            """
            SELECT COUNT(*) FROM (
              SELECT order_id, event_type
              FROM outbox
              GROUP BY order_id, event_type
              HAVING COUNT(*) > 1
            ) duplicates
            """.trimIndent(),
        )

        val anomalies = buildList {
            if (pendingCount > 0 && oldestAge != null && oldestAge > properties.stuckPendingAfterSeconds) {
                add("NOT_PUBLISHED")
                add("STUCK_PENDING")
            }
            if (deadCount > 0) add("DEAD_LETTER")
            if (publishedNotConsumed > 0) add("MISSING_CONSUMPTION")
            if (orphanConsumed > 0) add("ORPHAN_CONSUMPTION")
            if (duplicateEventGroups > 0) add("DUPLICATE_EVENT")
        }

        return ReconciliationReport(
            generatedAt = now,
            pendingCount = pendingCount,
            oldestPendingAgeSeconds = oldestAge,
            deadCount = deadCount,
            publishedCount = publishedCount,
            consumedCount = consumedCount,
            publishedNotConsumed = publishedNotConsumed,
            orphanConsumed = orphanConsumed,
            duplicateEventGroups = duplicateEventGroups,
            anomalies = anomalies,
        )
    }

    private fun count(sql: String, vararg args: Any): Long =
        jdbc.queryForObject(sql, Long::class.java, *args) ?: 0
}

// 文件: outbox/DeadLetterAlerter.kt —— 死信告警：Webhook 优先，失败降级本地日志 + 指标
package com.example.backend.outbox

import io.micrometer.core.instrument.Counter
import io.micrometer.core.instrument.MeterRegistry
import org.slf4j.LoggerFactory
import org.springframework.http.MediaType
import org.springframework.stereotype.Component
import org.springframework.web.client.RestClient

@Component
class DeadLetterAlerter(
    private val properties: OutboxProperties,
    meterRegistry: MeterRegistry,
) {

    private val log = LoggerFactory.getLogger(javaClass)
    private val restClient: RestClient = RestClient.builder().build()

    private val webhookOk: Counter = Counter.builder("shop.outbox.dead.alerts")
        .tag("channel", "webhook")
        .description("死信告警成功投递到 webhook 的次数")
        .register(meterRegistry)

    private val localFallback: Counter = Counter.builder("shop.outbox.dead.alerts")
        .tag("channel", "local-log")
        .description("死信告警降级为本地日志的次数")
        .register(meterRegistry)

    private val failures: Counter = Counter.builder("shop.outbox.dead.alert.failures")
        .description("死信告警投递失败次数")
        .register(meterRegistry)

    fun alert(report: ReconciliationReport) {
        val payload = linkedMapOf(
            "event" to "shop.outbox.dead_letter",
            "generatedAt" to report.generatedAt.toString(),
            "deadCount" to report.deadCount,
            "pendingCount" to report.pendingCount,
            "oldestPendingAgeSeconds" to report.oldestPendingAgeSeconds,
            "anomalies" to report.anomalies,
        )

        val webhook = properties.alertWebhookUrl?.takeIf { it.isNotBlank() }
        if (webhook == null) {
            log.warn(
                "死信告警（降级：本地日志通道）dead={} pending={} anomalies={} payload={}",
                report.deadCount,
                report.pendingCount,
                report.anomalies,
                payload,
            )
            localFallback.increment()
            return
        }

        try {
            restClient.post()
                .uri(webhook)
                .contentType(MediaType.APPLICATION_JSON)
                .body(payload)
                .retrieve()
                .toBodilessEntity()
            webhookOk.increment()
            log.info("死信告警已发送 webhook dead={}", report.deadCount)
        } catch (e: Exception) {
            failures.increment()
            localFallback.increment()
            log.warn(
                "死信 webhook 不可达，已降级为本地日志 dead={} url={} error={} payload={}",
                report.deadCount,
                webhook,
                e.message,
                payload,
            )
        }
    }
}

D11.10 企业级取舍 ​

决策选项建议
事务性发件箱 vs 事务消息RocketMQ 事务消息 / Kafka + Outbox已有 Kafka 用 Outbox；用 RocketMQ 可用半消息，但别两套混用
轮询间隔100ms ~ 5s延迟敏感 100~500ms；注意 DB 压力与 SKIP LOCKED
事件体格式自定义 JSON / Avro / Protobuf跨团队用 Schema Registry；至少带 eventId/type/version/occurredAt
去重位置消费端 / 网关 / DB 唯一键消费端去重表最通用；DB 唯一键是最后防线
死信处理自动重放 / 人工平台先自动有限次重试，再进死信 + 告警 + 人工重放
顺序保证全局有序 / 同键有序只承诺同 orderId 有序，全局有序代价极高

小结与自测 ​

要点回顾：Outbox 解决「业务与事件」的原子性；至少一次投递不可避免；幂等消费把重复变成无害； 死信与重放是运维的一等公民；没有 broker 时用 Transport SPI 降级，但必须显式失败而不是静默丢消息。

自测题：

  1. 为什么「事务提交后在 afterCommit 发消息」仍可能丢事件？
  2. Outbox 的 markPublished 为什么要带 AND status='PENDING'？
  3. 至少一次投递下，消费端去重为什么必须和处理逻辑在同一事务？
  4. Kafka 场景为什么用 orderId 而不是随机 UUID 作为消息 key？
  5. DEAD 状态为什么不能直接删除记录后重发？
参考答案（点击展开）
  1. 提交成功后、发送前进程崩溃或网络失败，事件没有任何持久化记录，无法补发。
  2. 防止并发/重复轮询把同一条事件重复标记成功，覆盖 published_at，也避免已发布事件被再次处理。
  3. 若先去重后处理且处理失败，去重行已提交，消息重试时会被判为重复而永远不再执行，造成业务丢失。
  4. 同一 key 进入同一分区，分区内有序，才能保证同一订单的创建/取消/支付事件按发生顺序消费。
  5. 删除会丢失 attempts/last_error 现场，也无法审计；保留 DEAD 记录才能复盘并对账，重放也应走状态机。
