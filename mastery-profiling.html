D5 · 性能剖析方法论 ​

性能优化不是「猜哪里慢」，而是「用证据定位、用基准验证、用指标确认」。本篇以 JVM 服务端为主线、Android 为补充，给出一套可复现的采集—分析—验证闭环。

  • 配套正文：第 6 章 性能优化与安全（6.2 / 6.3）
  • 上游依赖：D3 生产可观测性（业务指标基线）
  • 可运行示例：examples/profiling/（JFR + jcmd + JMH，含真实报告）

D5.0 目标读者与前置 ​

读者收益
后端工程师能独立定位 CPU、分配、锁、内存、死锁五类问题
Android 工程师能把「卡顿」拆成帧时间、系统调度与重组三类证据
技术负责人能设计「指标告警 → 剖析 → 回归」的性能治理流程

前置：会用 jcmd/jstack，理解 JVM 堆与线程状态；Android 部分需了解 Choreographer 与 Baseline Profile（第 6 章 6.3）。

D5.1 三层证据模型：不要用火焰图回答业务问题 ​

层次数据源回答时间粒度
业务Micrometer shop.orders.duration 直方图哪条链路、哪个渠道变慢，影响多少请求分钟级聚合
运行时JFR（CPU/分配/锁/GC）慢在计算、分配、等待还是 GC毫秒级采样
方法JMH这段代码单次到底多少 μs纳秒~微秒级

正确顺序是业务指标发现问题 → JFR 定位方向 → JMH 验证改动。反过来做，很容易优化了火焰图里最宽、但对 P99 毫无贡献的函数。

D3 留下的基线在这里发挥作用：ShopMetrics.timed() 用 publishPercentileHistogram() 产出 _bucket，任何优化都必须让对应直方图的 P99 回落，否则视为无效优化。

examples/backend-service/src/main/kotlin/com/example/backend/ShopMetrics.kt:22-47可在线运行
kotlin
    suspend fun <T> timed(channel: Channel, block: suspend () -> T): T {
        val sample = Timer.start(registry)
        try {
            val value = block()
            registry.counter(
                "shop.orders.requests",
                "result", CallResult.SUCCESS.tag,
                "channel", channel.tag,
            ).increment()
            return value
        } catch (e: Throwable) {
            registry.counter(
                "shop.orders.requests",
                "result", CallResult.FAILURE.tag,
                "channel", channel.tag,
            ).increment()
            throw e
        } finally {
            sample.stop(
                Timer.builder("shop.orders.duration")
                    .tag("channel", channel.tag)
                    .publishPercentileHistogram()          // Prometheus 侧生成 _bucket，支持 P99 计算
                    .register(registry),
            )
        }
    }

D5.3 CPU 火焰图：采集、折叠与读图 ​

采集 ​

bash
cd examples/profiling
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./scripts/collect.sh cpu 15
# 产物：reports/cpu/{cpu.json,cpu-folded.txt,cpu-flamegraph.svg,jfr-summary.txt}
1
2
3

脚本内部的关键动作：启动负载 → 轮询 PID → jcmd JFR.start settings=profile duration=8s → jfr print --stack-depth 64 --json → 折叠并渲染。

⚠️ 两个必踩的坑：

  1. jfr print 默认只打印 5 层栈，必须 --stack-depth 64，否则只剩叶子帧。
  2. JFR 的 frames 是「栈顶 → 栈底」，折叠前要 reverse，否则火焰图上下颠倒。

折叠算法 ​

把每个样本的栈拼成 root;...;leaf 字符串并计数，相同前缀自然聚合；渲染时父节点宽度 = 子节点宽度之和。

本机真实结果 ​

示例 CPU 负载轮转 4 个热点函数，8 秒采集到 610 个样本：

分支样本占比
cpuIteration29147.7%
sortWork → DualPivotQuicksort28045.9%
hashWork396.4%
matrixWork10.2%

读图结论：排序占了近一半 CPU，且与代码作者的直觉相反（原以为位运算是大头）。火焰图的价值就是纠正直觉。

cd examples/profiling
./scripts/get-async-profiler.sh          # Maven Central 下载 4.0 并解压 native 库
./scripts/collect-asprof.sh cpu 10 4     # reports/cpu-asprof/{cpu.html,cpu.collapsed}

同一份 CPU 负载、同样 10ms 周期、cstack=fp 采集 1018 个样本：

叶子帧async-profiler（1018）JFR（610，8s）

两种采样器在 Java 帧上的排序结论一致，说明 JFR 降级路径足以定位热点。差异只有一处： async-profiler 额外采到 zero_blocks（0.9%）、__getattrlist（0.6%）等 native 帧， 来自 JVM 的内存映射与文件元数据路径——这是 ExecutionSample 只采 Java 帧时必然丢失的部分。

操作细节：agent 模式的 file= 只认最后一个参数，想要 html + collapsed 两种产物必须跑两次 （脚本已封装）；cstack=fp 是 native 帧能出现的前提。

D5.4 分配剖析：速率与存活集要分开看 ​

bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./scripts/collect.sh alloc 15
# reports/alloc/{alloc-top.txt,heap-histogram.txt}
1
2

本机真实数据（15 秒负载，2390 个采样）：

指标数值含义
[B 估算分配量60405.7 MB累计分配速率（JFR 抽样放大）
[B 实时直方图1.09 MB / 15561 实例当前存活集
StringBuilder3.7 MB / 1 次单次大对象

结论：分配速率 60GB 但存活仅 1MB，属于「短命对象多」，优化方向是减少临时数组/复用缓冲区，而不是查泄漏。若直方图持续增长，才转 D5.6。

D5.5 锁竞争：阈值、状态与聚合 ​

bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./scripts/collect.sh lock 15 6
# reports/lock/{lock-contention.txt,thread-dump.txt}
1
2

本机真实数据（6 线程抢同一把锁，8 秒）：

阻塞点事件数累计阻塞
Workloads.lockIteration9061114.2 ms
JFR PlatformRecorder（噪声）11.9 ms

读法：

  • JavaMonitorEnter 只记录进入监视器前的等待，默认阈值 20ms；调成 1ms 才能看到微竞争。
  • BLOCKED 对应 synchronized；WAITING 多半是 park/await，应查 jdk.ThreadPark。
  • 14% 墙钟时间在等锁时，加线程只会放大争用；先缩小临界区或分片。

D5.6 堆与泄漏：直方图差分 + 老对象分配栈 ​

bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./scripts/collect.sh leak 20
# reports/leak/{heap-histogram-before/after.txt,heap-old-objects.txt,heap.hprof}
1
2

本机真实数据：

指标数值
[B 直方图（前 → 后）68.2 MB → 86.0 MB（6 秒 +17.8 MB）
OldObjectSample81 个 1MB 数组，共 81 MB，最大年龄 9.96s
最大样本分配栈MainKt.main → Workloads.leak
heap dump 体积89 MB

四步法：

  1. 确认增长：间隔取两次 GC.class_histogram，看同一类型实例数与字节数是否单调上升。
  2. 抓快照：jcmd GC.heap_dump，同时记录时间点与业务操作。
  3. 定位分配点：JFR OldObjectSample 的 stackTrace 直接给分配栈。
  4. 找持有者：attach 模式 path-to-gc-roots 可能为 null，用 Eclipse MAT 的 Path to GC Roots / OQL 补引用链。
sql
-- MAT OQL：找出大于 1MB 的 ArrayList 元素数组与其持有者
SELECT OBJECTS s FROM java.util.ArrayList s WHERE s.elementData.length > 1
1
2

常见误判：把「分配速率高」当成泄漏；把「堆大」当成泄漏（可能只是缓存未设上限）。判断标准只有一条：多次 Full GC 后存活集是否仍增长。

真实输出：

text

预防优于排查：

  • 全局锁顺序（按对象 ID/业务主键排序后加锁）。
  • tryLock(timeout) 超时后放弃并记录，避免无限等待。
  • 监控侧用 ThreadMXBean.findDeadlockedThreads() 定期探测并告警。

D5.8 JMH：把微基准跑对 ​

bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) GRADLE_USER_HOME=/tmp/gradle-home-prof \
  ./gradlew jmh --no-daemon --console=plain
1
2

本机基线（avgt，μs/op，2 预热 + 3 测量，单 fork，耗时 2m44s）：

BenchmarkScoreError
allocIteration46.341±3.957
cpuIteration15.655±1.116
lockIteration0.006±0.001

三条纪律：

  1. 结果必须消费（返回/写入 Blackhole），否则 JIT 会删掉整段代码。
  2. 参数用 @Param 覆盖边界值，别只测「好数据」。
  3. 短跑只做相对比较；对外数字至少 10 迭代 + 3 fork，并固定环境。

D5.9 生产环境常驻采集 ​

  • 启动参数常驻环形录制：-XX:StartFlightRecording=disk=true,maxsize=512m,dumponexit=true,filename=/var/log/app.jfr。
  • 事故时按需 dump：jcmd <pid> JFR.dump name=default filename=/tmp/incident.jfr。
  • 容器内注意：JFR 文件写挂载卷；jcmd 需与目标进程同 UID/同命名空间；堆 dump 预留磁盘配额。
  • 采样开销：settings=profile 通常 <2%，但 path-to-gc-roots、堆 dump 会 STW，禁止在高负载时段无条件触发。
  • 产物统一归档：JFR、thread dump、heap dump、直方图、业务指标截图，缺一不可。

现象首选证据常见根因

GC 频繁、延迟抖动JFR GC + 分配采样短命大对象、日志字符串拼接

D5.12 实践任务 ​

  1. ★ 跑通 collect.sh cpu/alloc/lock/leak/deadlock，用自己的话解释每张报告的第一行结论。
  2. ★★ 修改 sortWork（如数组减半或改用插入排序），重跑 CPU 火焰图与 JMH，记录样本占比与分数变化。
  3. ★★ 把 lockIteration 改为 LongAdder，对比锁事件数与累计阻塞时间。
  4. ★★★ 构造一个真实的 static Map 缓存泄漏，用直方图差分 + MAT 找出持有链并修复。
  5. ★★★ 为团队写一份「性能事故取证清单」，覆盖 JFR、thread dump、heap dump 与业务指标四类产物。

D5.13 自测题 ​

  1. 为什么 jfr print 不加 --stack-depth 会得到错误的火焰图？
  2. 分配采样 weight 很大但直方图很小，说明什么？
  3. JavaMonitorEnter 默认采不到微秒级竞争，如何调整？调低阈值有什么代价？
  4. attach 模式拿不到 GC 根路径时，如何继续定位泄漏持有者？
  5. JMH 的 lockIteration 只有 6ns，为什么不能据此认为「生产锁竞争不是问题」？
  6. Android 上「帧耗时正常但滑动卡」应该先看重组还是先看 Perfetto？为什么？

参考答案要点：1）默认 5 层截断，叶子帧丢失根因；2）分配速率高、存活集小；3）jdk.JavaMonitorEnter#threshold=1ms，代价是事件量增大；4）MAT Path to GC Roots/OQL；5）无竞争单线程不代表多线程争用；6）先 Compose Compiler Metrics/重组计数，再 Perfetto 验证调度与主线程阻塞。

D5.14 小结 ​

  • 先有业务指标，再有剖析数据；先定位链路，再定位代码。
  • 火焰图纠正直觉，JMH 验证收益，直方图确认回落，三者缺一不可。
  • 工具可以降级，证据链不能缺失；每个降级点都要写清楚补足路径。
