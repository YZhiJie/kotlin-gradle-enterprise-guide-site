精通专题 · 测试工程化 ​

专题定位：把「能写测试」升级为「能设计测试体系」。关心的是反馈时间、有效性、稳定性、可维护性四个指标，而不是测试数量。

前置阅读：第 7 章 测试策略与质量保障 7.1~7.8（金字塔、MockK、runTest、UI 测试基础）。

D6.0 目标读者与痛点 ​

角色典型痛点
测试负责人覆盖率 85% 但线上仍出问题，不知道测试有效性的度量方式
Tech LeadCI 测试 40 分钟，PR 排队；flaky 用例靠重跑，没人敢删
平台工程师测试数据跨模块复制，一改字段十几个模块编译失败
架构师模块边界写在文档里，半年后依赖图变成蜘蛛网

本专题的交付物不是更多测试，而是四类可执行机制：

  1. 快慢分层（test / integrationTest）——控制反馈路径；
  2. 复用（test fixtures）——消灭测试数据漂移；
  3. 有效性（变异测试 + ArchUnit）——让测试真的能拦住缺陷；
  4. 稳定性（flaky 隔离 + 分片并行）——把「重跑到绿」变成可度量问题。

D6.1 测试成本模型：先算账，再设计 ​

把一条测试的生命周期成本拆成四项：

text
单用例成本 = 编写成本 + 执行成本 × 每日执行次数 + 维护成本 × 变更频率 + 失败排查成本
1
  • 执行成本差异是数量级的：纯函数单测 ~1ms，Spring 上下文测试 ~3s，设备 UI 测试 ~10s+；
  • 失败排查成本由稳定性决定：flaky 用例每次失败平均消耗 30 分钟以上，且会训练团队忽略红灯；
  • 维护成本由耦合度决定：断言实现细节 > 断言行为 > 断言契约。

由此得到分层预算（与金字塔同源，但更关注时间）：

层目标占比单用例预算触发时机工具
纯逻辑单测60%~70%< 10ms每次保存/commitJUnit 5 + Kotest property
框架切片15%~20%< 500ms每次 PR@WebFluxTest / @DataR2dbcTest
集成（容器/契约）10%~15%1~30spush 后 / nightlyTestcontainers、Pact
设备 / E2E< 5%10s~分钟nightly / release 前GMD、Espresso、Compose Test

经验法则：PR 反馈预算 10 分钟，主干合并预算 30 分钟。超预算时先分层、再并行、最后才考虑删测试。

D6.3 Testcontainers：真实依赖，真实方言 ​

Mock 数据库能验证业务分支，但验证不了方言、事务、约束、驱动兼容性。Testcontainers 用真实容器补齐这一层：

}

工程化建议：

  • 容器共享：同一测试类的容器放在 companion object，避免每个用例启停一次；
  • 镜像固定：postgres:17 而非 postgres:latest，否则缓存与行为都会漂移；
  • 启动探测：CI runner 必须预装 Docker 或使用 ubuntu-latest（自带）；本地开发在 README 写明 docker info 检查；
  • 超时与重试：镜像拉取受网络影响，withStartupTimeoutSeconds(120) 可减少误报；
  • 数据隔离：每个用例事务回滚，或每个类独立 schema，避免用例间隐式依赖。

D6.4 并行与分片：把墙钟时间拆开 ​

两个不同维度的并行：

手段粒度收益风险
maxParallelForks=N多 JVM 进程隔离彻底，适合 CPU 型测试内存 × N，CI runner 需 ≥ 4GB
JUnit parallel.enabled单 JVM 多线程启动快，适合 IO 型测试共享状态会互相污染
CI 分片（matrix）多 runner墙钟时间近似线性下降分片不均会产生长尾
Test Distribution（Develocity）动态分配自动均衡商业组件

Gradle 侧只需一行开关：

kotlin
// 文件: examples/backend-service/build.gradle.kts（节选）
tasks.withType<Test>().configureEach {
    maxParallelForks = providers.gradleProperty("testForks").orNull
        ?.toIntOrNull()?.coerceIn(1, 8) ?: 1
}

D6.5 flaky 治理：度量、隔离、修复、删除 ​

定义与度量 ​

text
flake rate = 同一 commit 下「重跑才通过」的用例数 / 总用例数
重跑率     = 触发重跑的 pipeline 数 / 总 pipeline 数
1
2
  • 健康水位：flake rate < 1%，重跑率 < 5%；
  • 超过水位说明测试环境或测试设计有问题，加机器只会掩盖。

四步闭环 ​

  1. 识别：CI 记录每个用例的首次失败与重跑结果，按用例名聚合；
  2. 隔离：@Tag("flaky") + 独立任务，默认流水线排除：
kotlin
// 文件: examples/backend-service/build.gradle.kts（节选）
tasks.test { useJUnitPlatform { excludeTags("flaky") } }
tasks.register<Test>("flakyTest") {
    useJUnitPlatform { includeTags("flaky") }
}
1
2
3
4
5
  1. 修复：优先修根因（时间断言、端口冲突、共享状态、外部依赖不稳定）；
  2. 删除：24 小时未修复则删除用例并记录，禁止长期挂 @Disabled。
kotlin
// 文件: examples/backend-service/src/test/kotlin/com/example/backend/FlakyQuarantineDemoTest.kt
@Tag("flaky")
class FlakyQuarantineDemoTest {
    @Test
    fun `十次模拟查询必须在一秒内完成`() { /* 依赖机器负载的时间断言，典型 flaky */ }
}
1
2
3
4
5
6

实测：默认 test 任务不包含该用例（15 个用例全绿）；./gradlew flakyTest 单独执行通过。隔离机制生效，且没有让主流水线依赖它。

重试策略的正确用法 ​

  • 只对已知外部依赖（容器启动、第三方 HTTP）限次重试 1~2 次；
  • 每次重试必须上报指标（org.gradle.test-retry 会输出重试次数到测试报告）；
  • 重试后仍失败 → 按真实失败处理；重试后通过 → 自动打标签进修复池。

D6.8 ArchUnit：架构约束即测试 ​

可落地的四类规则：

  1. 命名：*Controller / *Service / *Repository；
  2. 分层：Controller 只能调 Service，Service 不得依赖 Web 注解；
  3. 模块边界：demo.core 不得依赖 demo.app（多模块反向依赖）；
  4. 技术栈隔离：生产代码不得依赖测试库、不得依赖内部实验包。

实测踩坑：一开始未加 DoNotIncludeTests，测试类自身依赖 JUnit，被「生产代码不得依赖测试库」规则判为违规。过滤测试类后 4 条规则全部通过。这类假阳性也是规则上线前必须本地跑一次的原因。

D6.10 排障路径 ​

现象先查再查
测试突然变慢--profile 找长尾任务；JUnit XML 的 time是否引入了 Spring 全量上下文；容器是否每类重启
覆盖率下降jacocoTestReport 的包级明细新代码是否有分支未覆盖；是否误把生成代码算入
变异体存活PIT HTML 报告的 SURVIVED 行号断言是否只看类型不看值；边界是否遗漏
flaky 增多失败用例的共同依赖（时间/端口/网络）CI 资源是否超卖；是否共享静态状态
Pact 验证失败差异字段（body/header/status）消费者是否用了过严的 equalTo；提供方是否改了序列化

D6.11 实践任务 ​

  1. ★★ 在现有工程拆出 integrationTest suite，确保 test 不加载 Testcontainers。
  2. ★★ 为 2 个核心模块建 test fixtures，删除下游复制粘贴的测试数据。
  3. ★★★ 给一个核心包接入 PIT，阈值设 70%，补断言把存活变异体清零。
  4. ★★★ 用 scripts/test-shards.mjs 在 CI matrix 切 4 片，记录并行前后墙钟时间。
  5. ★★★ 选一个跨团队接口，补齐消费者 + 提供方 Pact，并写出接入 Broker 的迁移清单。

D6.12 自测题 ​

  1. 为什么「先分层再并行」比「先并行再分层」更有效？
  2. java-test-fixtures 与 testImplementation(project(":other")) 的本质区别？
  3. Testcontainers 用例如何避免「每次用例都重启容器」？
  4. 分片为什么用类名哈希而不是随机分配？
  5. flaky 用例加自动重试后仍然失败率 2%，下一步做什么？
  6. can-i-deploy 检查的是什么？它和提供方 Pact 测试有何不同？
  7. PIT 报「Test strength 100%」是否等于「测试质量完美」？
参考答案（点击展开）
  1. 分层先削减进入主反馈路径的测试数量与单测成本，并行只是在剩余集合上做除法；顺序反了会把慢测试也复制到每个分片，资源争抢更严重。
  2. fixtures 是独立编译变体，只发布测试辅助代码；直接依赖 project 会把对方生产代码与全部测试依赖带进 classpath，破坏隔离。
  3. 容器声明在 companion object 并加 @Container，JUnit 5 按类共享；或使用单例容器模式（static singleton + 手动启动）。
  4. 稳定哈希保证同一类永远落在同一片：失败可复现、构建缓存键稳定、分片负载可预测；随机分配会导致同一类在不同 run 落入不同片。
  5. 说明重试掩盖了真实缺陷或环境问题：先按用例聚合失败原因（时间/端口/共享状态），修复根因；仍无法修复则删除用例，禁止无限重试。
  6. 检查「某版本的应用是否与目标环境中所有已部署的消费方/提供方契约兼容」，基于 Broker 历史版本；提供方测试只验证当前契约文件，缺少跨版本与环境映射。
  7. 不等于。Test strength 只反映被覆盖代码的变异被杀比例；未覆盖代码、Kotlin 专属变异算子缺失、断言之外的逻辑错误都不在内。
