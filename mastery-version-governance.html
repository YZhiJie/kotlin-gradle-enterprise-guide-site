附录：版本策略与内容维护（D12） ​

目标读者：教程维护者、团队文档负责人、构建/平台工程师。

这篇附录解决一个常被忽视的问题：文档写得再好，版本一漂移就变成误导。本仓库把「版本」当作代码来治理：单一事实来源、自动汇总、季度升级、锚点校验，全部可执行。

D12.1 为什么版本治理是精通的一部分 ​

零基础读者看到 Kotlin 2.0.x 能照着跑；企业团队看到的是另一组问题：

  • 示例里的 Kotlin 是 2.0.21，正文却写 2.0.x，读者升级到 2.2 后 API 变了，文档没有迁移提示。
  • 同一个仓库三份 libs.versions.toml，升级时漏改一份，CI 绿、线上红。
  • 手写锚点 #14-空安全体系 看起来合理，实际 VitePress 生成的 id 是 #_1-4-空安全体系，点进去 404。
  • 升级没有节奏，谁顺手谁升，升级记录散落在 commit 里，无法复盘。

精通的标志不是「知道版本号」，而是「让版本号不可能写错」。本附录的机制如下：

D12.2 单一事实来源：每个示例只留一份版本目录 ​

规则 ​

  1. 每个 Gradle 示例工程有且只有一份 gradle/libs.versions.toml，放在 examples/<project>/gradle/ 下。
  2. 业务模块与根工程一律通过类型安全访问器 libs.* 读取版本，禁止在 build.gradle.kts 里再写死版本号。
  3. Gradle 自身版本只写在 gradle/wrapper/gradle-wrapper.properties；wrapper jar 与脚本必须提交。
  4. 正文不再维护「Kotlin 2.0.x / Gradle 8.x」这类模糊区间；需要具体版本时，链接到示例 catalog 或 README 的自动汇总表。
  5. 升级时只改 catalog / wrapper，然后运行回写命令，让文档自动跟上。

本仓库的落地形态 ​

为什么不在根目录放一份「全局 catalog」 ​

Gradle 的 Version Catalog 作用域是单个构建。build-logic 是 composite build，默认看不到主工程 catalog，必须在自己的 settings.gradle.kts 里显式导入同一份文件：

kotlin
// 文件: examples/gradle-demo/build-logic/settings.gradle.kts（节选）
dependencyResolutionManagement {
    versionCatalogs {
        create("libs") {
            from(files("../gradle/libs.versions.toml"))
        }
    }
}

因此「每个示例一份」比「全仓库一份」更现实：它既保证示例可独立复制，又让跨模块的 build-logic 有明确导入点。跨示例的一致性由 check:versions 校验，而不是靠共享文件强绑。

两条命令：

bash
npm run check:versions              # 校验：不一致就失败，CI 用这条
npm run check:versions -- --write   # 回写：升级后让 README 自动跟上
1
2

脚本的校验项：

  1. catalog 位置合规：必须位于 examples/<project>/gradle/libs.versions.toml。
  2. 每工程一份：发现多份直接失败，避免「升级漏改」。
  3. 跨示例一致性：kotlin、coroutines、junit、detekt、springBoot 同名键必须一致。
  4. wrapper 一致：所有 Gradle 工程的 distributionUrl 版本必须一致。
  5. README 汇总一致：生成区块与当前 catalog 不一致时失败，提示运行 --write。

✅ 企业实践：把「版本升级」拆成两步 PR——第一步只改 catalog 与代码，第二步运行 --write 提交 README/文档变更。两步都能被 review，且不会出现文档与代码在同一 PR 里互相掩盖错误。

D12.4 锚点校验：手写链接不再靠人眼 ​

VitePress 的标题 id 由 markdown-it-anchor 的 slug 规则生成，和直觉并不一致：

标题直觉写法真实 id
## 1.4 空安全体系#14-空安全体系#_1-4-空安全体系
## 1.6 类、数据类、密封类、接口与对象声明#16-类数据类...#_1-6-类、数据类、密封类、接口与对象声明
## 2.4 Channel 与 Flow 家族#24-channel-与-flow-家族#_2-4-channel-与-flow-家族
## stateIn/shareIn 实操#stateinsharein-实操#statein-sharein-实操
## Spring 测试切片（WebFlux / R2DBC）#spring-测试切片webflux--r2dbc#spring-测试切片-webflux-r2dbc

规则摘要（与 VitePress 完全一致）：

  1. Unicode NFKD 归一化，去掉组合音标与控制字符。
  2. 空格与 ASCII 标点（~ ` !@#$%^&*()-_+=[]{}|\;:"'“”‘’<>,.?/）折叠为 -。
  3. 连续 - 合并，首尾 - 去掉。
  4. 以数字开头时前缀 _，最后转小写。
  5. 中文顿号 、、中文括号等不在替换集合内，会原样保留。

check:versions 会解析 cheatsheet.md 中所有 ](./NN-*.md#anchor) 链接，提取目标文件的真实标题 slug 并比对；失效时给出最接近的真实锚点。首次运行曾一次性抓出 25 个失效锚点——这正是「人眼不可靠」的证据。

⚠️ VitePress 的 ignoreDeadLinks: true 会让构建通过，但读者点击仍然 404。锚点校验必须独立于站点构建存在。

D12.5 编译冒烟：文档里的代码必须真的能编 ​

scripts/check-code-source.mjs 有两层：

模式命令内容
静态校验npm run check:code-sourcesrc= 路径、语言标签、range 行号、反向未引用清单
编译冒烟npm run check:code-source:build静态校验 + 按示例探测构建命令并真实执行

编译冒烟的探测规则：

  1. Gradle 工程：存在 gradlew + settings.gradle.kts 时，执行 ./gradlew test（Android 工程执行 :app:assembleDebug）。
  2. JDK 探测：优先 JAVA_HOME（要求 17~23），否则尝试 /usr/libexec/java_home -v 21，再否则降级。
  3. Android SDK 探测：ANDROID_HOME / ANDROID_SDK_ROOT 或 local.properties；缺失则降级为静态校验。
  4. kotlinc 示例：有 kotlinc 时编译 stdlib-only 文件；需要第三方 jar 的示例标记为「需手工 classpath」并降级。
  5. 降级必须可见：报告里明确打印 DEGRADED 与原因，绝不写成「已通过」。
  6. 代码错误不算降级：构建返回非零一律 FAILED，退出码非 0。

✅ 本机若存在全局 ~/.gradle/init.gradle 注入仓库，可能与工程的 FAIL_ON_PROJECT_REPOS 冲突。脚本检测到该错误后，会用临时 GRADLE_USER_HOME（软链本机 caches/wrapper）重试一次，并在报告中标注「隔离 Gradle Home 重试」。

D12.6 双轨版本：Baseline 与 Latest ​

轨道定位选择标准升级节奏谁用
Baseline教学与 CI 的稳定基线已发布 ≥ 1 个 patch、生态兼容、示例可构建每季度评估，通常只升 patch读者、CI 门禁、示例
Latest前沿验证轨道当前稳定大版本的最新 patch每月巡检，季度合并维护者、平台团队

Baseline 不是「最旧」，而是「最稳」：它要保证零基础读者照着文档能跑通，也要保证企业团队复制示例后不会踩到刚发布的回归。

当前 Baseline ​

具体版本以 README 的自动汇总表为准，核心组合：

  • Kotlin 2.0.21、Gradle 8.10、JDK 21（Android 编译目标 17）
  • Spring Boot 3.3.5、JUnit 5.11.3、coroutines 1.9.0、detekt 1.23.7
  • Android：AGP 8.7.2、compileSdk 35、minSdk 26、Compose BOM 2024.12.01

D12.7 内容维护制度 ​

角色与 SLA ​

角色职责SLA
专题 Owner维护专题正确性、示例可构建、版本同步季度升级后 1 周内确认
构建 Owner维护 wrapper、catalog、编译冒烟依赖漏洞/构建失败 24h 内响应
文档 Reviewer检查锚点、链接、示例映射PR 24h 内首响

文档变更的四个必查项 ​

  1. 可运行：新增代码块优先 src="examples/..."，禁止「文档一份、示例一份」。
  2. 可回链：速查卡与 README 的站内链接必须通过锚点校验。
  3. 可升级：版本只出现在 catalog/wrapper，正文不写死。
  4. 可降级：环境限制导致的未验证项必须在文档与报告中写明原因。

弃用与迁移 ​

  • 正文出现弃用 API 时，用「⚠️ 已弃用（版本 X 起）」标注，并给出替代写法。
  • 大版本升级前，先在 Latest 轨道验证一个季度，再合并进 Baseline。
  • 删除既有正文/漫画属于关键决策，必须先确认，不可直接覆盖。

D12.9 自测与实践 ​

  1. ★ 修改 examples/gradle-demo/gradle/libs.versions.toml 中 coroutines 版本，运行 npm run check:versions，观察哪些示例被判定不一致。
  2. ★★ 故意把 cheatsheet.md 的一个锚点改成 #14-空安全体系，运行校验，观察脚本给出的最接近真实锚点。
  3. ★★ 在 examples/backend-service 删除 gradle/libs.versions.toml，运行 check:versions，解释为什么这是「版本治理失败」而不是「少一个文件」。
  4. ★★★ 设计一次季度升级：写出升级顺序、每步验证命令、回滚点，以及需要同步的文档位置。
参考答案（点击展开）
  1. check:versions 会报「版本键 coroutines 跨示例不一致」，因为 android-app 与 gradle-demo 都定义了该键；修复方式是在所有相关 catalog 同步升级，或只保留一处定义。
  2. 脚本会提示真实锚点为 #_1-4-空安全体系，因为 1.4 中的点被替换为 -，且标题以数字开头会加 _ 前缀。
  3. 删除 catalog 后，build.gradle.kts 中的 libs.* 访问器全部失效，版本重新散落到脚本里；治理机制退化为「靠人记」，升级必然漏改。
  4. 顺序：冻结 → 依赖报告 → wrapper → Kotlin → Spring Boot/AGP → 测试/静态检查 → 全量门禁 → 回写 README 与升级日志；每步失败只回滚单步，并保留升级记录。
